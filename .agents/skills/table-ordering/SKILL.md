# 人工排序开发入口

按具体任务实现“用户可见 order＋隐藏 sortIndex”。使用本仓库代码与已完成样例，控制每次需要重新决定的事项。此 Skill 提供开发流程，不扩大当前任务范围；活动人员名单的首个实现已落在 `apps/server/src/modules/member/` 和对应页面，可作为当前基线。

## 先确定任务与代码状态

活动人员名单任务优先阅读 [活动人员名单执行方案](../../../docs/activity-member-ordering-model-plan.md) 的第 4 节业务绑定与本次 AM 任务。它是当前首个实际消费者，已有 AM01—AM05 的实现与验收记录；原议程样例仍是归档材料，也不能因此把活动名单当作第二个消费者提前抽取 shared。

其他任务阅读 [任务卡](../../../docs/table-ordering-tasks.md) 的任务状态、实施基线和本次指定任务。核对实际文件、依赖与检查证据，不能仅凭“完成”字样跳过前置核查。

先用 `rg -n '^##'` 定位文档章节，再读取任务要求的段落；不把全部任务卡、实施方案和研究报告一起载入上下文。

- 首次实施：活动人员名单按 AM00—AM05 当前指定项工作；用户另行指定议程试点时才使用 T01—T06。通用规则读取 [实施方案](../../../docs/table-ordering-implementation-plan.md) 第 4—5 节。
- 新表接入：使用 T07 的已填写业务绑定；没有真实范围、对象 ID 或读写出口时先调查，不能自行套用议程的 activityId。
- 缺陷修复：先重现相关 A／I／U 用例，检查排序规则、模块保存或拖拽适配中哪一层出错，再改对应层。

无需默认重读整份 [研究报告](../../../docs/table-ordering-research.md)；只有需求改变数字含义、筛选规则或算法取舍时才读取相关背景。

## 接入时的关键边界

实施方案第 4 节是行为契约，第 5 节是算法接口。用户的 order 是实际数值；隐藏 sortIndex 只确定同值组内先后。拖拽库的渲染 index 不能保存成数据库 sortIndex。

前端提交稳定记录 ID 和目标前／后意图；后端按完整业务范围验证并保存。普通编辑只发送实际修改字段。其他行仅隐藏重编号时，检查 ORM 的自动更新时间行为。

一个使用方时按页面／模块本地存放；第二个真实使用方接入时按实施方案第 3 节抽取纯算法和稳定交互。业务事务、权限、API、缓存与业务列保持各自归属。不要从其他路由的 `-` 目录引用，也不要复制第二份正式算法。

**"第二个使用方"指第二张有人工排序的表，不是第二处读取。** 2026-09-11 把 agenda／trip／seating／resource／invitation 的活动人员读取出口统一到 `modules/member/activity-member-order-by.ts`，那只是复用同一张表的顺序，没有产生第二张排序表——`plan-manual-order.ts` 仍留在 member 本地，别据此搬进 `shared/`。读取侧的规则、已接线出口和护栏范围见[执行记录](../../../docs/activity-member-ordering-execution.md#读取出口统一2026-09-11)。

后续接入沿用活动人员样例已验证的 `@dnd-kit/react@0.5.0` 和 API。只有计划升级依赖时才按 T05 重新验证，不混用不同代包名与事件。共用 UI 只认 props 和 DOM，不 import 服务端业务类型或调用业务 API。

## 验证与交接

执行本任务的检查和用例，分别报告自动测试、真实数据库和浏览器证据。类型检查、Mock 和 SQL 字符串检查不能代替事务或实机拖拽验收。按任务卡更新自己的完成记录与确实变化的基线；未验证项明确保留。

规则与目标业务冲突时，给出最小反例和受影响范围，回到实施方案评估；不要通过放宽测试、增加未定策略或复制实现消除报错。普通接线和类型问题在本任务内修复。
