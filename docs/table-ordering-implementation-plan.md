## 1. 为什么不只写 Skill，也不先造通用框架

对完全由 AI 开发的项目，成本不能只看“这次能少写多少代码”。还包括每次重新理解规则的上下文、修错的往返、模型之间交接的解释，以及一处规则修改需要检查多少实现。以下是针对当前仓库的工程判断，并非低成本模型的实测跑分。

| 方案 | 开发时的负担 | 维护时的负担 | 结论 |
| --- | --- | --- | --- |
| 仅写 Skill，各表复制实现 | 每个 agent 都要把自然语言重新翻译成算法、事件和事务 | 修一个重号问题，要查找并修正多份近似实现；测试也容易各自降低要求 | 单个试点可接受，多模块长期使用不合适 |
| 先开发万能排序框架 | 需要设计配置、数据库适配器、权限回调、扩展点和大量类型参数 | 修改一项策略时，要理解框架与每个配置的组合影响 | 当前成本过高，容易变成 AI 也难排查的间接调用 |
| 小范围代码复用＋Skill | 接入者主要填写真实业务映射，复用已验证规则 | 算法修复集中生效；模块差异仍在本地可见 | 推荐 |

Skill 负责“找到正确的代码与规范、按任务接入”，共用函数负责“实际执行同一条规则”，测试负责“自动发现规则被破坏”。三者承担不同职责，不能相互替代。

Skill 的按需加载结构有助于控制重复上下文；官方资料将指引、参考资料和可执行代码分开组织。[S1](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview) 但加载了指引不等于运行结果正确，也不能据此承诺降低多少费用或保证某个模型一次完成。

**给低成本模型减少的是每个任务中的未决问题。** 不要交给它“设计一个通用排序系统”，而应交给它“实现已定的两个操作，满足编号用例，修改指定模块”。模型仍可选择循环写法、局部变量名等普通实现细节，无需把所有编码动作写成模板。

## 3. 复用边界和抽取时机

### 3.1 应复用的能力

**排序计划函数。** 只接收 `{id, order, sortIndex}` 和操作意图，返回排序字段更新计划。它不知道数据库、活动、表名、权限、React、HTTP。这部分规则必须始终只有一份正式实现。

**拖拽行为适配。** 将选定拖拽库的事件转换为 `{sourceId, targetId, placement}`；处理稳定 ID、取消、无效落点、手柄和拖动反馈。它不知道活动 ID、查询 key 和具体 API。接口不应直接暴露第三方库的事件对象给每个业务页面。

**验收规则。** 排序性质由算法测试集中保护；模块测试验证它确实调用了正确规则、范围和查询出口。不要在每张表复制同一份算法测试后允许它们各自变更。

### 3.2 保留在业务模块的能力

数据库表和字段映射、查询范围、不可移动行、数字范围、事务执行、权限校验、查询缓存刷新、表格业务列、导入复制以及读取出口，都由业务模块负责。允许少量清晰的接口编排重复；把这些差异全部抽进回调和配置，通常比重复十几行显式代码更难维护。

首版不创建 `OrderingService<TTable, TScope, TPolicy>`、表名注册中心、跨模块统一排序 endpoint、策略插件系统、独立 workspace package 或代码生成器。

### 3.3 文件归属分两阶段

下列路径记录首个业务实现与第二个消费者的抽取边界；原议程 T01—T06 仍是归档任务，不要据此创建 agenda 实现。

| 内容 | 单个业务使用方（当前活动人员） | 第二个实际使用方接入时 |
| --- | --- | --- |
| 纯算法 | `apps/server/src/modules/member/plan-manual-order.ts`，测试同目录 | 搬到 `apps/server/src/shared/plan-manual-order.ts`，迁移测试；原文件删除，两个模块直接引用共享文件 |
| 活动人员事务编排 | `apps/server/src/modules/member/activity-member-ordering.ts` | 继续留在 member，第二个模块写自己的业务编排 |
| 拖拽与键盘适配 | 活动人员页面 `-components/activity-member-ordering.tsx` | 若事件到锚点的纯适配确实相同，搬到 `apps/web/src/shared/` |

## 4. 实施时固定的行为契约

本节是实施规则的集中入口。任务卡只引用规则编号，不再各自改写一份。

| 编号 | 规则 |
| --- | --- |
| R01 | `order` 是用户实际填写的整数，越小越靠前；不是最终行号。现有业务字段名 `sortOrder` 可以保留，只在纯函数边界映射成 `order` |
| R02 | 普通可移动记录按 `order ASC, sortIndex ASC, id ASC` 排列。固定行在模块外层处理，不进入普通序列 |
| R03 | 手填新值后进入该同值组末尾；重复提交当前值保持位置和隐藏值，无写入 |
| R04 | 移到目标前／后，源行采用目标的 order，再通过隐藏编号放到目标指定一侧 |
| R05 | 先计算目标 ID 序列。若序列未变，则移动为无操作，不因跨值边界而额外改源行的 order；移动到自己也无操作 |
| R06 | 未移动记录彼此相对顺序不变；除源行以外，其他记录可见 order 不变；普通业务字段不变 |
| R07 | 真实移动可将目标同值组的隐藏编号重编为 1…K；只写实际变化项，旧组允许留空洞。允许写多条数据库记录 |
| R08 | 筛选生效时首版禁用拖拽和前／后移动按钮，手填数字仍可用。判定看已应用筛选，不看尚未查询的草稿 |
| R09 | 分页不是排序范围。后端按完整业务范围计算；页内拖拽只表达相对某行前／后。首版不做跨页拖拽，不把本页第一行解释为全局第一行 |
| R10 | 非人工顺序视图、保存中、当前显示页加载未完成或失败、存在未保存行编辑时，禁用移动；保留明确原因和后续操作入口。正常分页不要求浏览器加载整个业务范围，后端仍须完整计算 |
| R11 | 新增未指定 order 时追加完整可移动范围末尾：采用末行 order 并追加同值组；空范围默认 0。指定 order 则进入对应组末尾 |
| R12 | 删除不重编其余记录；普通字段编辑不提交未修改的 order。导入、复制、恢复须显式定义如何分配同值组位置 |
| R13 | 每次业务保存使用数据库事务。失败不留下部分编号。对同一浏览器连续操作进行 pending 禁用；不引入多人版本锁、CRDT 或协作冲突策略 |
| R14 | 数字列不公开隐藏编号；普通客户端不提交或维护 sortIndex。隐藏值是否返回读取 API 由需要决定，议程样例不新增该投影 |

R11 采用末行的数值，避免 `max(order)+1` 在现有 999 上限处失败，也避免“行数＋1”落在已有 99 前面。该默认与用户显式输入 0 是两种情况，校验层不能先把缺省输入变成 0 再判断。

活动人员名单采用本规则的可空变体覆盖上述默认：未设置 order 保存为 `NULL`，按 `NULLS LAST` 排在明确数字之后；新关系进入未设置组末尾，输入 0 才会明确进入数字排序空间。其他业务模块若需要区分缺省值与显式 0，也应采用同样的可空语义并在业务绑定中写清楚。

上移、下移也采用锚点接口；在某行之后和下一行之前可能导致源行采用不同数字，因此界面表达必须一致。鼠标插入线统一以移除源行后的右侧行作为 `before` 锚点，只有尾部使用左侧行的 `after`。若没有可用锚点，不提交移动。

## 5. 排序计划函数的确定接口

### 5.1 类型和返回值

以下是首个 member 模块已经采用的契约。项目 ID 当前用 number，无需预先泛化为多种 ID 类型。

```ts
type ManualOrderRow = Readonly<{
  id: number;
  order: number;
  sortIndex: number;
}>;

type ManualOrderOperation =
  | { type: "set"; sourceId: number; order: number }
  | {
      type: "move";
      sourceId: number;
      targetId: number;
      placement: "before" | "after";
    };

type ManualOrderPlan =
  | {
      ok: true;
      orderedIds: number[];
      updates: Array<{ id: number; order: number; sortIndex: number }>;
    }
  | {
      ok: false;
      reason:
        | "INVALID_ROWS"
        | "INVALID_ORDER"
        | "SOURCE_NOT_FOUND"
        | "TARGET_NOT_FOUND"
        | "SORT_INDEX_EXHAUSTED";
    };

// 一个主导出；相关类型可在本文件导出，不创建单独 types.ts。
declare function planManualOrder(
  rows: readonly ManualOrderRow[],
  operation: ManualOrderOperation,
): ManualOrderPlan;
```

`updates` 只含排序字段确实变化的记录，每个 ID 最多一次；成功的无操作返回空数组。`orderedIds` 是纯函数验收和后端核对用，不要求把整个序列返回浏览器。输入数组和原对象不可原地修改。

### 5.2 输入边界

调用方提供**一个完整可移动业务范围**的轻量序列，完成权限、归属和固定行检查。首版全量读取这个范围，暂不增加“仅传相邻两行”的另一种模式。

函数内部复制并按 R02 排成标准顺序。ID 必须为互不重复的正安全整数；order 必须为非负安全整数；sortIndex 允许 0…2,147,483,647 的整数，0 仅作初始化兼容。业务的 0—999 上限由 agenda 校验层负责，不能固化进通用算法。

同 order、同 sortIndex 的遗留记录允许通过 ID 确定顺序；不要因为辅助值重复就拒绝整个列表。非整数、NaN、无穷、负数、重复 ID 或缺失源行／锚点必须返回明确错误。

### 5.3 两个操作的流程

**设置数字：** 源值相同即返回无操作。否则移除源行，在新值对应组尾插入；通常给源行 `max(sortIndex)+1`，其他记录不动。若辅助整数达到上限，先对目标组按现有顺序重编，再追加源行；目标组长度本身超出可表示范围才返回 `SORT_INDEX_EXHAUSTED`。

**移动：** 先在标准 ID 序列中移除源行，再插入锚点前／后；目标序列相同即返回无操作。确有变化时把源行 order 设为锚点 order，按最终 ID 顺序对目标同值组编号 1…K，生成与原值相比的差异。源行离开的旧组保持不变。

禁止用目标行的 ID、当前页面数组下标或浮点中值代替 sortIndex。不要在前端再写一遍业务排序算法；前端预览只移动 ID，服务端决定数值。

### 5.4 可直接转成测试的固定用例

每个用例独立初始化。基础数据为 `A=(id:1, order:99, index:1)`、`B=(2,99,2)`、`C=(3,120,1)`，输入可打乱，标准序列为 A、B、C。

| 编号 | 操作 | 必须得到 |
| --- | --- | --- |
| A01 | C before B | A(99,1)、C(99,2)、B(99,3)；A／B 的可见值不变 |
| A02 | C set 99 | A、B、C，C=(99,3)，其他两行无更新 |
| A03 | A set 99 | 原位置、原字段不变，updates 为空 |
| A04 | B before C | 原序列不变，B 仍为 99，updates 为空 |
| A05 | A after C | B(99,2)、C(120,1)、A(120,2)；B 允许保留编号空洞 |
| A06 | B before A | B(99,1)、A(99,2)、C(120,1) |
| A07 | C set 100 | A、B、C，C=(100,1)，其他行不变 |
| A08 | A before A | 无操作，不改变任何字段 |
| A09 | 锚点不存在 | TARGET_NOT_FOUND；输入不变 |
| A10 | 同值同隐藏值遗留数据 | 起始按 ID 确定顺序；真实移动后位置正确 |
| A11 | 目标组 maxIndex 为整数上限 | set 新成员时重编目标组成功，保持组内原相对顺序 |
| A12 | 非法数字／重复 ID／源行不存在 | 对应错误，无部分更新 |

除固定用例外，枚举小序列和操作，独立用“删除 ID、插入锚点”的简单列表模型检查目标序列；不可用待测函数计算期望值。比较更新后的三项排序结果，同时断言输入不可变、成员集合不变及 R06。

| 分页／筛选 | 此管理弹窗完整展示全部线路，无分页；主页面对环节的筛选不等于线路列表被筛选 |
| 读取出口 | `/list` 返回线路顺序，弹窗和时间轴均沿用；本次不改环节按开始时间排序 |

已有主线懒创建在 `segment-write.ts`、`segment-config.ts` 两处，保持其现有增量保存、写入顺序及业务限制，不把主线纳入新排序函数。

### 6.1 迁移与种子

生成版本化迁移，在新迁移内回填并行线隐藏编号：按 `(activity_id, line_type, sort_order)` 分组，按旧 id 顺序分配 `row_number()`。不改已有 sort_order，不改业务审计字段，不改既有迁移文件。

```sql
-- 加列由 drizzle-kit 生成；以下为该新迁移中的数据回填部分。
WITH ranked AS (
  SELECT id,
    row_number() OVER (
      PARTITION BY activity_id, line_type, sort_order ORDER BY id
    )::integer AS position
  FROM activity_agenda_line
  WHERE line_type = 'parallel'
)
UPDATE activity_agenda_line AS line
SET sort_index = ranked.position
FROM ranked
WHERE line.id = ranked.id;
```

同一新迁移中建立 `(activity_id, line_type, sort_order, sort_index, id)` 普通查询索引，不加全局唯一约束。保留主线已有唯一索引和复合外键。新增隐藏列的默认值不能替代创建接口的编号分配。

更新 `dev-seed/30-agenda.ts`：现有主线为 0、并行线填合法隐藏值；补充同一活动的 99、99、120 三条无环节并行线用于验收。保留已有固定 ID 和时间冲突样例，新条目可使用自动生成 ID。

迁移检查应覆盖已有数据升级。新临时库建成后再灌种子不能证明历史 99 重号的回填正确，必须单独在一次性库验证迁移前后的 ID 序列与数值。

## 7. 后端实施与保存边界

### 7.1 接口目标

```ts
// POST /api/agenda/moveLine
{ activityId, id, targetId, placement: "before" | "after" }
// 成功 data
{ id, sortOrder, changed: boolean }
```

不接受客户端提交 sortIndex、完整页内 ID 数组或表名。依现有 Hono 链式注册、`jsonBody`、`ok()`／`err()` 约定实现，业务结果继续用 code 判断。

对源和目标查存在性、归属与类型；两个 ID 必须属于声明活动且都是并行线。查不到／跨范围返回对应的现有业务错误，无写入。不新增任何放宽权限的旁路。

`createLine` 的 sortOrder 改成可选且不设校验默认值；缺省时按 R11 从数据库求尾部位置，显式传值时按同值组追加。仍返回已有线路字段。

新增记录的组内分配：目标组为空时隐藏值为 1，否则取最大隐藏值加 1；达到辅助整数上限时，在同一事务中按现有三项排序重编该组后追加，不能改其他行可见值。把这段分配放在模块内一处纯计算 helper，由创建编排调用；第二模块需要它时与排序计划一起抽取，不在多个路由中内联复制。

`updateLine` 保留一个入口，但改为实际字段修改：sortOrder 可选且无默认值；name 可选，显式 null 代表清空，遗漏代表不改。主线允许清空名字，并行线拒绝空名字。旧调用显式传 sortOrder 仍表示修改意图；新前端只提交确实编辑过的字段。主线传排序 0 可兼容为无操作，非 0 拒绝。无任何修改字段的请求拒绝。

名称与排序同时修改时，一个事务内完成；只有名称变更不调用编号逻辑，只有隐藏值变更不写名称。名称、可见值和实际位置均未变化时不刷新更新时间。`deleteLine` 保持原删除约束，不补齐编号。

### 7.2 模块内编排

`line-order.ts` 只认识 agenda 表与事务，是模块内部保存逻辑，不能提升成通用数据库操作器。函数调用链控制为“路由校验 → 本模块读写 → 纯计划函数”，避免继续加 service、repository、adapter 多层转发。

在同一个事务中读取完整可移动范围、计算计划、写入更新。小规模议程线首版可以 `for...of` 逐条 await 类型化更新，清晰且容易检查；不需要先编写通用批量 SQL 生成器。若测到实际性能问题，再在本模块优化 SQL，纯函数契约保持不变。

所有业务拒绝条件应在写入前判断；写入中断、更新数量异常等失败必须抛出并使事务回滚。不能在已经写了一半之后仅 `return err(...)`，那可能让事务正常提交。Drizzle 的事务接口及显式回滚能力见 [S3](https://orm.drizzle.team/docs/transactions)。

### 7.3 隐藏更新不能伪装成业务编辑

源行真实发生移动或字段修改时，正常更新其审计信息。其他行仅重编号时，保留 updatedBy、updatedAt 与所有业务字段。

源行真实换了位置时，其数字偶尔可能恰巧不用修改，而是由邻居隐藏编号变化实现新位置。不能仅凭源 ID 是否出现在 updates 中判断“用户有没有移动它”；操作是否变化与源行审计按完整计划判断。

当前 schema 的 `$onUpdate` 在未显式提供值时会执行；因此仅省略 updatedAt 不够。[S4](https://orm.drizzle.team/docs/column-types) 邻居更新可显式使用 `updatedAt: agendaLine.updatedAt` 保持数据库原值，updatedBy 不赋值；验收时比较真实写入前后的时间戳。这是需要集中保存在模块写入代码里的具体约束，不能只留在 Skill 提醒里。

## 8. 前端实施与交互状态

### 8.1 先打通按钮移动，再接拖拽

T04 先完成数字编辑、上移／下移及保存刷新，通过相同 moveLine 接口验证真实顺序；T05 接入拖拽，只增加另一种产生相同移动意图的交互。这样排错时能够区分业务保存错误与拖拽库事件错误，也为不使用拖拽的用户提供操作入口。

首版上移以当前序列前一行为 `before`，下移以后一个行为 `after`；第一条和最后一条禁用对应按钮。主线不进入这个序列。不要把主线作为“移到最上面”的目标。

### 8.2 行编辑与请求状态

保留输入草稿字符串，不在每次按键时重排。显式保存时验证空串、整数与范围，禁止 `Number(value) || 0` 把无效输入吞成 0。仅提交与最新基线确实不同的字段；成功后清除此行草稿，失败保留草稿。

有任何未保存的已有行编辑时，统一禁用移动并提示先保存或取消编辑。首版可以提供“取消本行修改”按钮，不自动丢弃草稿来换取拖拽可用。新增名称草稿与已有行编辑分开处理。

```text
就绪 → 拖动预览 → 保存中 → 使用服务端结果刷新 → 就绪
         ↓取消         ↓失败／结果不确定
       就绪          丢弃临时预览 → 重读服务端 → 就绪或读取失败
```

首版不修改全局查询缓存做乐观重排。拖动中的视觉反馈由本地状态和库处理；松手后 pending 禁用再次移动和写入。请求成功后 await 对应活动查询的刷新；请求返回成功但刷新失败，要提示“排序已保存，列表刷新失败”，不能假装数据库已回滚。

网络超时无法仅凭前端判断是否提交。清除临时预览、重读服务端后恢复操作；不自动补发相反移动作为撤销。无需因此设计多人并发或历史命令系统。

### 8.3 拖拽适配目标

首个活动人员实现已核实并固定 `@dnd-kit/react@0.5.0`；后续模块必须复用这一依赖与事件模型，不能每次重新选库或升级。原 T05 的验证步骤仍作为迁移检查表保留。

组件对业务页面只暴露行 ID、当前可移动 ID 序列、disabled 状态、可读的行名称及 `onMove({sourceId,targetId,placement})`。表格业务单元格由页面提供，API 与 query key 保留在页面。禁止为了包装第三方库而重建一个带列配置、筛选器和分页器的万能 Table。

dnd-kit 的 `useSortable.index` 是当前渲染位置。[S2](https://dndkit.com/react/hooks/use-sortable/) 本项目的 sortIndex 是同值组持久编号，两者不可映射。事件应先转为移除源行后的目标 ID 序列，再按 R04／R05 得出一个锚点意图。

拖动开始时保留已确认的 ID 序列，结束后与这个起始序列比较。不要拿拖拽库已经重排的临时数组作“原顺序”，否则真实移动可能被误判成无操作。

保持 `<tbody>` 的直接子项是合法 `<tr>`。行组件内调用 Hook，避免在 `.map()` 回调中直接调用 Hook。手柄使用按钮，具有名称和键盘焦点；拖动不抢占文本输入、选中文本或保存按钮。若使用 overlay，提供合法表格结构和稳定列宽，避免复制交互控件的重复 ID。

### 8.4 首版暂不扩展的模式

筛选后重排、跨页拖拽、多选拖动、树形跨父节点、按权限隐藏了部分记录的全局移动、虚拟滚动和不同字段排序模式，需要具体模块另给行为任务。不能只打开拖拽库的某个开关便视为支持。

普通分页表在后端按完整范围保存，前端可做页内相对锚点移动。存在未展示记录的复杂范围，需要任务卡声明完整性与隐藏记录规则；不能默认把当前页面当完整数据。

## 11. 派发原则与故障升级

一次交付一个任务 ID，给出前置任务完成证据、相关契约、文件范围、确定用例和检查命令。不要要求每个执行者重新读原始聊天、全部研究文档或重新评估三种库。

首版算法和首个拖拽库接入存在相对集中的判断工作，任务已单独拆开；可以由低成本模型执行，但需要按证据验收。复用样例形成后，后续模型的主要工作应是业务范围映射、少量接口编排和页面接线。

遇到下列情况，执行者提交最小反例与已尝试结果，交回方案任务处理：原规则无法满足目标业务、同一 ID 对应多个视觉行、无法界定完整排序范围、必须突破现有数值语义、需要多人并发或跨父节点移动。不要自行加入新策略参数掩盖未决规则。

普通类型报错、已知 API 差异、缺少 import、样式问题和范围内测试失败由执行者继续修复，不属于需要重新设计的事项。核心失败不能通过放宽测试或复制第二份算法解决。
