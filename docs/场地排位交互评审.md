## 1. 评审者需要先知道的三件事

不了解这三条，下面的问题会看不出为什么是问题。

### 1.1 三层，每层职责不同，中间层是拷贝不是引用

```
场地库 venue                 跨活动复用的物理底图，不知道任何活动
   │  「从场地库引用」= 整份拷贝（名称/区域/平面图），拷完就断开
   ▼
活动场地空间 activityVenue    本活动用哪些空间、每块派什么用途
   │  「选择区域」= 再拷一份座位快照给这个环节
   ▼
环节排位 seating              本环节谁坐哪个位置 + 确认/退回状态机
```

**每一层往下都是拷贝，不是活引用。** 上游改了不会自动流到下游——这是刻意的
（否则已确认的排位会静默变形），代价是需要一个显式的"重新同步"动作。
**那个动作现在不存在**，见 §3.8。

### 1.2 两条写路径，共享状态机但互不调用

| 写路径 | 改什么 | 提交方式 |
| --- | --- | --- |
| 画布保存 `saveLayout` | 有哪些区域/位置、在哪、长什么样 | 攒在本地，点「保存」 |
| 人员分配 `assign`/`unassign` | 谁坐哪 | **即时提交**，没有保存按钮 |

这条分离是整个设计的承重墙（旧系统把两条揉成一条，后果是每拖一个座位都在重写
全部人员绑定）。它带来一个**交互后果**：同一个页面里有两种提交语义。目前的处理
是让排位画布**整体只读几何**，于是那一页只剩即时提交一种语义——这是上一轮修正
的结果，方向是对的。但活动空间编辑页仍然两种语义并存，见 §3.3。

### 1.3 编辑权限按层划分

| 页面 | 能改几何吗 | 能排人吗 |
| --- | --- | --- |
| 场地库画布 `/venue/$id/layout` | ✅ 全功能 | — |
| 活动空间画布 `/…/venue/$activityVenueId` | ✅ 全功能（复用同一套组件） | — |
| 环节排位画布 `/…/seating/$planId` | ❌ 只能选中 | ✅ |

## 3. 发现的问题

按"用户会不会撞上、撞上有多疼"排序。每条标注**引入时机**，方便评审者判断这是
设计缺陷还是实施疏漏。

---

### P0 · 用户会撞上的硬故障

#### 3.1 移除已排座的人员 → 500「服务器内部错误」

**现象**：活动人员页移除一个人，弹窗提示"该人员已关联 N 个环节，请确认是否一并
解除"，点确认 → 服务器内部错误。人没移除掉，也没告诉用户为什么。

**已复现**（在回滚事务里验证，未改动数据）：

```
DELETE FROM segment_member WHERE activity_member_id = 13;
ERROR: update or delete on table "segment_member" violates foreign key
       constraint "fk_seat_assignment_member" on table "seat_assignment"
DETAIL: Key (id, segment_id)=(11, 8) is still referenced from table "seat_assignment".
```

**根因**：`member/routes.relation.ts` 的 `activityMember/remove` 走 cascade 分支时
会 `DELETE FROM segment_member`，但 `seat_assignment → segment_member` 的外键
没有 cascade。member 模块**为 `resourceMemberBinding` 显式处理过同一个坑**
（那里有注释："绑定表上的复合外键没有 cascade，所以这里必须显式删——否则移除
活动人员会撞上外键约束报 500"），排位模块建得更晚，没人回头补这一笔。

**这是实施疏漏，不是设计缺陷**——[底层设计 §8](场地排位底层设计.md) 早就写明
"从活动移除人员 → member 侧发起级联，seating 提供'查引用 + 批量解绑'两个接口"。
那两个接口**一个都没建**。

**影响**：任何"这个人不来了"的日常操作，只要他被排过座，就走不通。而排过座的人
恰恰是最可能需要临时调整的那批。

**建议**：seating 补两个接口——`countAssignmentsByActivityMember`（供 member 的
`/impact` 汇总）和 `revokeByActivityMember`（供 cascade 调用）；member 的 remove
在删 `segment_member` 之前先调后者。二次确认的文案要把"将解除 N 个座位分配"
列进去，跟现有的"N 个环节、N 项资源服务安排"并列。

---

#### 3.2 删除已被排位引用的区域 → 整批保存失败，且看不出是哪个区域

**现象**：在活动空间画布上删掉一块区域，点「保存」→ 服务器内部错误。这一次
编辑会话里改的**其它内容也一起没保存**（事务整体回滚）。用户不知道是哪块区域
出的问题，也不知道该去哪解决。

**根因**：`applyActivityLayout` 的删除分支直接 `DELETE FROM activity_venue_zone`，
撞上 `fk_seating_plan_zone` 外键。venue 模块看不见 seating（单向依赖），拦不住。
代码注释里承认了这点并写着"前端在删除前应该先提示确认"——**那个提示没做**。

**影响**：跟 3.1 同一类——正常操作撞上不可读的错误。区别是这里还会连累同批次的
其它改动。

**建议**：两选一，倾向前者。
- **A（推荐）**：`activityVenue/saveLayout` 增加一个前置检查——前端在保存前先调
  `seating/zoneUsage`（这个接口已经有了，概览页正在用），把要删除的区域跟被引用
  的区域比对，命中就在前端拦住并指名道姓："区域 3 正被「开幕式」排位引用，
  请先作废那份方案"。不需要新接口，也不违反依赖方向（前端拼两个模块的数据是
  允许的，概览页的"引用环节"列已经是这么做的）。
- B：服务端捕获外键错误翻译成人话。能解决报错可读性，但解决不了"整批回滚"。

---

#### 3.3 区域名称有两个入口、两种保存语义，后者会静默覆盖前者

**现象**：在活动空间画布页，同一块区域的名称可以在两个地方改：

| 入口 | 位置 | 保存语义 |
| --- | --- | --- |
| 右侧属性面板「名称」 | 画布页右栏 | 进画布文档，**要点「保存」** |
| 「活动用途 / 可用点位」弹窗里的「活动区域名称」 | 同一页，按钮就在下面一行 | **点弹窗的「保存」立即写库** |

两者写的是同一列 `activity_venue_zone.name`。于是：用弹窗改名 → 立即生效 →
再在画布上动任何东西 → 点「保存」→ `applyActivityLayout` 拿画布里那份**还没
更新的旧名字**覆盖回去。**用户刚改的名字被静默还原，没有任何提示。**

**根因**：`ActivityZoneDialog` 是概览页的组件，被原样复用到画布页时没有裁掉
`name` 字段——而画布页的属性面板本来就管这个字段。两个来源、两种时机，必然打架。

**引入时机**：上一轮"活动空间应该可以复用编辑器"的改造里我引入的。概览页单独用
这个弹窗时没问题（那一页没有画布属性面板）。

**影响**：静默数据丢失。用户不会收到任何错误，只会发现"我明明改过名字"。

**建议**：画布页打开这个弹窗时**隐藏 `name` 字段**（加一个 `hideName` prop，或
拆成两个组件）。名称在画布页只有属性面板一个入口，其余业务字段（用途/点位/
状态/说明）走弹窗即时保存——职责就不重叠了。概览页保持现状不变。

### P1 · 功能做了但走不通 / 到不了用户手里

#### 3.4 关掉环节的排位开关，已有方案彻底失联

**现象**：环节 A 已经排好位（待确认），有人在议程页把这个环节的「开启排位管理」
开关关掉。此后：

- 排位列表页**看不到这一行了**（`listPlans` 硬过滤 `seatingEnabled = true`）
- 但方案行还在库里，还占着"一个环节最多一个有效方案"的唯一索引位
- 场地空间页的「引用环节」列**照样显示它**（`zoneUsage` 不看这个开关）
- 那块区域因此**仍然删不掉**（3.2 的外键）

用户看到的是："场地空间说区域 3 被开幕式引用着，可是排位页根本没有开幕式这一行，
我怎么解掉它？" —— **没有出口。**

**根因**：`listPlans` 把"开关开着"当成了列表的过滤条件，而不是当成一种状态来
显示。开关和方案是两个独立的事实，用前者过滤后者就会漏。

**建议**：`listPlans` 去掉 `seatingEnabled = true` 这个 where 条件，改成
**"开关开着 **或** 已经有非作废方案"** 都要出现在列表里；开关是关的那一行加一个
「排位开关已关闭」的状态芯片和「作废此方案」的出口。接口本来就已经把
`seatingEnabled` 查出来返回了，前端只是没用。

#### 3.5 环节作废后，它的排位方案在列表里仍是一行正常记录

**现象**：环节被作废（`status = voided`）之后，它的排位方案在排位页看起来跟正常
环节没有区别，「确认」按钮照样能点。

**根因**：`createPlan` 检查了 `segment.status === "voided"` 禁止**新建**，但已存在
的方案不受影响；`listPlans` 把 `segmentStatus` 查出来返回了，**前端一个字都没用**。

**依据**：[业务梳理 §6](场地排位模块.md) 明确写了"环节作废的连锁：作废后不进入
新排位、不进入座位通知（BR-DEV-003B）"。现在前半句做了，后半句没有落点。

**建议**：前端消费 `segmentStatus`——作废环节的行整行降级显示，禁掉「确认」，只留
「查看」和「作废」。服务端 `confirm` 也应该拒绝作废环节的方案（一行判断）。

#### 3.6 场地空间的「排位」按钮不带任何区域上下文

**现象**：区域表格每一行都有「排位」按钮，点下去只是跳到排位列表页——不筛选、
不预选、不建方案。用户点的是"给**这块区域**排位"，得到的是"排位页面首页"，
还得自己再找环节、再选一遍这块区域。

**根因**：实现时留的占位链接：

```tsx
<Link to="/project/$projectId/activity/$activityId/seating" params={{ projectId, activityId }}>
  排位
</Link>
```

原型 `activity-space.html` 里这个按钮是指向排位画布的。

**建议**：要么带上 `?zoneId=` 让排位页据此高亮/预选（选环节这一步无法省略——
方案是按环节建的，一块区域可以被多个环节引用），要么**直接去掉这个按钮**。
现在这个"点了等于没点"的状态最糟：它承诺了一个它给不了的动作。

#### 3.7 座位对调（swap）后端做完了，没有入口

**现象**：`seating/swap` 接口完整实现（含"只有一边有人时退化成移座"的语义、
一人一座唯一索引的正确处理），前端 `swapSeats()` 包装函数也写了，
**零个组件调用它**。

**依据**：[业务梳理 §5.4](场地排位模块.md) 把本期范围定为"人工绑定/调整/解除/
**对调**"——对调是列进本期的。

**建议**：排位画布支持选中 A 座 → 点 B 座 → 对调（或右键菜单）。工作量不大，
后端是现成的。**如果评审认为对调本期不做，那就把接口一起删掉**——留着一个没人
调的写接口，比没有它更糟（它会被当成"已支持"）。

#### 3.8 上游改了几何，下游方案没有任何"已过期"提示，也没有重新同步入口

**现象**：活动空间的区域被改小了 / 座位重新排布了，已经建好的排位方案**完全不
受影响**（这是设计意图，快照隔离）。但用户在排位画布上看到的还是旧几何，**页面
上没有任何地方告诉他"这份排位的底图已经跟活动空间不一致了"**，也没有"重新从
活动空间同步"的按钮。

**根因**：[底层设计 §2.2](场地排位底层设计.md) 明确要求"上游变了，环节侧显式提供
一个'重新从场地模板同步'的动作，二次确认后才覆盖"（旧系统的 `handleResyncTemplate`
就是这个）。**没做。** `segment_seat.sourceExternalId` 这一列是专门为这个动作留的
对齐键——它被写入、被传来传去，但**没有任何一处读它做判断**，目前是一列死数据。

**建议**：本期至少做到**能看出来**——`getPlan` 顺带返回活动空间那份 blob 的
`updatedAt`，比方案的 `savedAt` 新就在画布页顶部挂一条提示"活动空间的平面图在
你之后改过，这份排位仍是建立时的快照"。真正的「重新同步」（整份覆盖 + 二次确认 +
已排人员的处置规则）是个独立特性，建议单独排期，不要塞进本期。

### P2 · 高风险操作的交互防护不一致

#### 3.9「确认」单击即执行，「作废」反而有二次确认

**现象**：

| 操作 | 后果 | 当前防护 |
| --- | --- | --- |
| **确认** | 排位对外生效、`version` +1、**生成座位通知**（文档定义为高风险操作） | **无，单击即执行** |
| 退回 | 打回待确认 | 弹窗填原因 ✅ |
| 作废 | 解除全部分配 + 终态 | `window.confirm` ✅ |

**依据**：[业务梳理 §1](场地排位模块.md) 的对照表里，开发版文档对确认/退回的定性
就是"有，**属高风险操作**"；原型 `seating-confirm.html` 的确认是走弹窗的，还带
"是否生成通知"的选项。

**建议**：确认加二次确认弹窗，把这次要发布的事实摆出来——"将发布 N 个座位、
M 人已排位，确认后会生成座位通知"。**顺带解决 3.10**。

#### 3.10 允许确认一份 0 人已排的方案

**现象**：一个座位都没排的方案，点「确认」直接通过，`assigned: 0`。

**根因**：`confirm` 的校验是"逐条检查已有分配指向的位置是否仍有效"——分配列表为空
时这个校验天然通过。校验的是"已排的对不对"，没有校验"排没排"。

**建议**：不做硬拦截（可能真有"这个环节自由入座、方案只用来固化座位表"的场景），
但 3.9 的二次确认弹窗里必须显著提示"当前 0 人已排位"。

#### 3.11 二次确认用原生 `window.confirm`，与仓库主流不一致

**现象**：移除场地、作废方案两处用 `window.confirm`；仓库里已有 5 个页面
（人员、项目、邀请函模板、供应商报价等）用的是样式统一的 `AlertDialog`。

**说明**：议程页也有一处 `window.confirm`（既有代码，不是本次引入），所以仓库
现状是混用。这条是一致性问题，不影响正确性。

**建议**：跟 3.9 的确认弹窗一起，统一换成 `AlertDialog`。优先级最低。

### P3 · 信息可信度与文案

#### 3.12「可用点位」是一个没人维护的手填数字，却被当成判据

**现象**：`activity_venue_zone.capacity` 在场地空间页占了一整张统计卡（"可用点位
144"），还是确认时"超出提示"的比较基准。但它的实际维护情况是：

- 导入场地时按源区域的座位数填一个初值
- 之后**只能手填**——在活动空间画布上增删座位**不会更新它**
- 于是画布里有 200 个座位、`capacity` 还写着 96，是完全可能的常态

**设计上它确实是"规划数字不是权威集合"**（[§3.3](场地排位底层设计.md) 有完整论证，
这条判断我认为是对的，不建议推翻）。问题在**交互**：一个会漂的数字被放在统计卡
最显眼的位置，且没有任何地方说明它是"计划值"而不是"实际值"。弹窗里那句
"规划数字，不限制排位实际能放几个位置"藏在编辑表单里，看统计卡的人看不到。

**建议**（按成本递增，选一个）：
- A：统计卡副标题从"仅统计启用区域"改成"规划值，与实际座位数可能不同"
- B：统计卡同时显示两个数——"可用点位 96 / 实际座位 200"，不一致时标黄
- C：去掉手填，`capacity` 改成从 blob 实时算的派生值（**这会推翻 §3.3 的设计判断，
  需要业务确认 capacity 到底是不是一个独立于实际座位的规划意图**）

#### 3.13 排位画布的停用提示指错了地方

**现象**：选中一个已停用的座位，右侧显示"这个位置本环节停用了，要排人先**在画布上**
把它重新启用"。但启用按钮就在**同一个右侧面板的下方**，画布上没有这个操作。

**引入时机**：上一轮把启用/停用从画布保存改成右侧面板即时按钮时，文案没跟着改。

**建议**：改成"…请先用下方的「本环节启用此位置」把它打开"。一行文案。

#### 3.14 候选人列表硬上限 200，超出静默截断

**现象**：`listCandidates` 是 `limit(200)`，没有分页也没有"还有更多"的提示。活动
人员超过 200 人时，排在后面的人**在搜索框里搜得到**（服务端搜索），但不搜索时
直接看列表是看不到的，也没有任何提示说明列表被截断了。

**建议**：列表底部在命中上限时显示"仅显示前 200 人，用搜索找具体的人"。不建议
本期做分页——排人的正常动线本来就是搜索，不是翻页。

## 5. 一条本轮新增的观察：并发不是假想问题

"不做并发控制"这条结论建立在"内部运营工具、几个操作员、同时编同一个环节排位的
概率极低"这个前提上。

**实测期间这个前提被打破了一次**：验证功能时发现同一个开发库上有另一个会话正在
操作同一个活动的排位（相隔 90 秒的 assign/unassign 日志，同一个账号）。虽然是开发
环境的巧合，但它说明"同一份排位被两处同时改"在真实使用里不是不可能——尤其
排人是即时提交的，两个人各自点几下，谁也不会收到任何提示。

**不建议因此就上并发控制**（成本仍然不划算），但建议：
- 排位画布在 `assign`/`unassign` 成功后已经会 invalidate 重新拉取，这一条要保持
- 评审时确认一下运营的真实工作方式：排位是不是一个人独占完成的？如果实际是
  多人分区域并行排，这条结论要重算。
