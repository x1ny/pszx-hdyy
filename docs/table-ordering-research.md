# 可填写 order 与拖拽排序研究方案

本方案研究同一套人工排序的两种操作：用户直接填写 `order` 数字，也能拖拽一行改变先后。`order=99` 表示实际保存的排序值，不是“移动到第 99 行”。本轮不展开多人并发。

**推荐保留一个用户可见、可编辑的 `order`，另加一个隐藏的整数 `sortIndex`，用于同值记录的先后。** 按 `order ASC, sortIndex ASC, id ASC` 排列。拖拽可以改变被拖动行的 order，但不自动改变其他行可见的 order；必要时调整同值组的隐藏编号。这样兼顾自由输入、同值间精确拖动和较简单的实现。

如果业务需要区分“用户明确输入 0”和“从未设置”，`order` 可以采用可空整数：`NULL` 作为未设置，并在读取时使用 `order ASC NULLS LAST`。这是一种业务变体，不改变 `sortIndex` 只负责同值组内顺序的原则；活动人员名单采用此变体。

单字段自动重编号能实现正确排序，但会改变其他行手填的数字，因此保留为备选，不作为默认体验。这里区分“可能写入多条数据库记录”和“改变多行用户可见排序值”：采用辅助字段后，前者仍可能发生，后者可以避免。

资料核验日期为 2026-09-10，项目现状基于提交 `00e4c24`。外部事实附官方来源；具体交互和算法是设计建议。本文未修改应用代码或现行项目约定。

面向 coding agent 的代码复用边界、确定接口与逐项验收见 [实施方案](table-ordering-implementation-plan.md)；具体派发入口见 [任务卡](table-ordering-tasks.md)。本报告保留产品取舍背景，普通开发任务按实施方案读取相关章节即可。

## 1. 为什么一个字段会发生体验冲突

假设 A、B 的 order 都为 99，C 为 120，并且 C 的 ID 大于 A、B。把 C 拖到 A 与 B 之间，如果只允许改 C 的一个数字：

| C 的新 order | 结果 |
| --- | --- |
| 小于 99 | 在 A 前面 |
| 大于 99 | 在 B 后面 |
| 等于 99，仍用 ID 兜底 | 在 A、B 后面 |
| 99.5 | 仍在两个 99 后面，不能解决相等边界 |

两个相同数字之间没有严格的中间值。ID 恰好位于 A、B 之间时可能碰巧成功，但不能作为任意拖动的保证。

因此，“只有一个决定顺序的字段”“其他行数字绝对不改”“同值间可以任意插入”三个条件不能普遍同时满足。需要在数据模型或可见数字变化上作取舍。

将 A、C、B 重编为 10、20、30 在逻辑上正确，但用户只移动 C，却发现 A、B 的手填数字也变了。如果名单很长，改动还可能扩展到其他页。数字既然允许用户填写和查看，就不能把全量修改当作没有体验成本的内部优化。

## 2. 三种方案的取舍

| 方案 | 用户看到的变化 | 实现成本 | 建议 |
| --- | --- | --- | --- |
| 单 order，必要时整名单重编号 | 一次拖动可能改变整份名单的数字 | 最低 | 只适合明确接受自动整理数字的简单清单 |
| 单 order，必要时只改邻近区域 | 通常改变附近几行，最坏仍可能扩展很远 | 中等，边界较多 | 若坚持只存一个字段，可考虑 |
| 可见 order＋隐藏 sortIndex | 只可能改变被拖动行的可见 order，其他行手填值保留 | 增加一列和同值组编号逻辑 | 当前推荐 |

第三种方案无需新增用户操作，也不必引入小数、字符串分数索引或 LexoRank。两个字段可以都是整数；用户只看见原来要求的那一列。

它付出的成本不是零：需要定义输入重复值时落在组内哪里、拖到另一个值附近时被拖动行的新 order，以及同值组内的隐藏编号规则。下面给出一套完整、确定的默认规则。

## 3. 推荐模型：order 决定数值先后，sortIndex 决定同值先后

以两个 99 之间插入为例：

| 记录 | 拖动前可见 order | 拖动前隐藏 sortIndex | 拖动后可见 order | 拖动后隐藏 sortIndex |
| --- | --- | --- | --- | --- |
| A | 99 | 1 | 99 | 1 |
| C | 120 | 1 | 99 | 2 |
| B | 99 | 2 | 99 | 3 |

最终顺序是 A、C、B。A、B 仍显示原来的 99；C 被用户移入 99 所在的位置，其 order 改为 99。B 的辅助编号发生了变化，但这不需要展示或让用户维护。

数据库读取规则：

```text
同一个业务排序范围内：
ORDER BY sort_order ASC NULLS LAST, sort_index ASC, id ASC
```

`sortIndex` 可以在不同 order 组中重复，例如 order=10 的组和 order=99 的组都从 1 开始。最后的 ID 是确定性兜底；正常移动逻辑应生成能够准确表达目标顺序的组内编号，不能靠 ID 碰巧插对。

界面只需要一句说明：“数值越小越靠前；相同数值的记录可通过拖动调整先后。”不用显示第二列，也不用把它命名为业务优先级。

## 4. 两种操作如何统一

### 4.1 手动输入数字

用户将一行的 order 改为 v：

1. 校验整数范围，实际保存 v，不将它解释为行号。
2. 将该行放在 v 同值组的末尾，辅助编号取该组当前最大值加 1。
3. 原同值组可以留下辅助编号空洞，不必立即补齐。
4. 其他行可见的 order 不变。
5. 如果输入值没有变化，保持原组内位置，作为无变化操作。

“同值组末尾”是本方案推荐的确定规则，也可选开头，但全站应统一。这里不再用 ID 决定新进入同值组的位置，否则拖拽建立的顺序可能难以保持。

例如 C 从 120 改成 99，先进入 99 组末尾；如果用户想精确放进 A、B 中间，再拖一次即可。同一表格既支持数值赋值，也支持精确相对移动，两者不会互相覆盖成两套前端状态。

### 4.2 拖动到某行之前／之后

为保持实现简单，建议以目标行作为锚点：

- “放到 B 之前”：被拖动行采用 B 的 order，在 B 的同值组中插到 B 前面。
- “放到 A 之后”：被拖动行采用 A 的 order，在 A 的同值组中插到 A 后面。
- 完整名单开头／末尾：采用实际首行／末行的 order，排在对应同值组的开头／末尾。
- 最终 ID 顺序未变化：不修改任何数字。

这样不需要为 99 与 100 之间寻找一个整数。把 C 放到 B(100) 前面，就让 C 也使用 100，再用隐藏编号排在 B 前面。

例如 `A(10)、B(20)、C(30)`，将 C 放到 B 之前，得到 `A(10)、C(20)、B(20)`。无需把 A 或 B 改成别的数字。C 的数字会变化，必须在保存后同步显示，因为它是用户主动移动的对象。

前端普通插入线可统一表达为“放到下一行之前”；最后一个可见行后则表达为“放到该行之后”。这两种关系对应确定的新 order，提示与实际执行一致。不要采用“向上拖选上一行数值、向下拖选下一行数值”等依赖拖动方向的隐性规则。

### 4.3 同值组的隐藏编号

首版可以采用最直观的做法：构造目标同值组的最终 ID 序列，按 1、2、3……给 sortIndex 编号，只写实际发生变化的记录。跨值移动时，无需整理原同值组的空洞。

这可能更新多行 sortIndex，但不会改其他行的可见 order。一次操作中，源行的 order 变更与组内编号更新整体保存，失败就整体回滚。

若同值组非常大、重排很频繁，再考虑给隐藏编号预留间隙或局部重编号。并发暂不考虑时，没有必要首先引入更复杂的排序编码。

## 5. 筛选后的规则

**筛选后仍可直接填写 order；首版建议关闭直接拖拽。** 数字赋值的语义确定，落点则可能受隐藏行影响。增加辅助字段解决了同值插入与可见数字变化，没有消除隐藏行的位置歧义。

```text
完整顺序：A → H1 → B → H2 → C → D
筛选结果：A → B → C → D
操作：将 D 拖到可见 A、B 之间
```

| 解释 | 完整顺序 |
| --- | --- |
| 紧挨 B 前面 | A → H1 → D → B → H2 → C |
| 紧挨 A 后面 | A → D → H1 → B → H2 → C |
| 隐藏行保持绝对槽位，仅重排可见项 | A → H1 → D → H2 → B → C |

三种结果筛选后都一样，但完整名单不同。第三种还改变了 B 与 H2 的相对关系，并不等价于普通单行移动。

首版提供“进入完整名单调整”入口，保留原查询条件，进入同一业务范围的完整列表并定位目标。可以使用只高亮、不隐藏记录的查找功能。筛选资格以已应用查询为准，而不是输入框的草稿值。

如果以后需要筛选内移动，可以开放明确的“移到 B 前面”命令：服务端查 B 所在范围的真实同值组与邻居，插入结果作用于完整名单。不要把可见邻居当成数据库相邻行。筛选结果首条之前也不自动代表整个名单开头。

AG Grid 的 managed row dragging 对筛选、分页有限制，并允许使用 unmanaged 模式自行处理；这属于组件的模式边界，不代表业务上永远不能实现。[1](https://www.ag-grid.com/javascript-data-grid/row-dragging-managed/)

## 6. 范围、分页与显示序号

排序范围应绑定真实业务归属。例如人员在两个活动中可以有不同位置，两个字段应放在活动人员关系上，而不是全局人员主档。活动范围选择不等于范围内临时筛选。

未筛选时可以支持页内拖拽，前端发送源记录和目标记录 ID，后端查完整范围的真实同值组。不能把本页的 sortIndex 从 1 重编后直接保存，忽略相同 order 组可能跨多页。

跨页第一版不用实现拖着鼠标自动翻页；通过输入 order 大致定位，或“移动到某记录之前／之后”精确定位。另加“移动到第 N 位”也可以，但必须与填写 order 的含义分开。

若表格保留序号列，它是当前位置；order 是实际保存的数字；sortIndex 是不展示的同值顺序。当前第 3 行显示 order=99 是正常的，不要为了显示序号连续而修改 order。

查询应在数据库按 `(order,sortIndex,id)` 排序后分页。PostgreSQL 官方文档要求分页查询有确定的完整顺序。[2](https://www.postgresql.org/docs/16/queries-limit.html) 改序后刷新相应列表缓存，尤其目标同值组跨页时，不能只更新源行的前端位置。

有行级权限裁剪时，不能借清空筛选展示无权查看的记录；重排可能调整整个目标同值组的内部顺序，相关业务授权应覆盖该操作范围。固定主线、合计行、不可移动区域等边界同样要由后端验证。

## 7. 接口与保存流程

数字赋值与位置移动分为两个明确动作，放在拥有名单的业务模块：

```json
{
  "activityId": 18,
  "id": 305,
  "sortOrder": 99
}
```

上述是 setOrder：实际赋值 99，并进入对应同值组末尾。

```json
{
  "activityId": 18,
  "id": 305,
  "target": { "kind": "before", "anchorId": 202 }
}
```

上述是 move：根据锚点确定源行新的 order 与同值组内位置。不要接受客户端直接指定 sortIndex，也不要用当前页数组下标作为保存协议。关系名单中的 ID 是成员关系 ID，不是姓名、手机号或主档 ID。

移动流程为：校验权限与归属；逻辑上移除源行；构造目标 ID 顺序；无变化则结束；确定源行 order；计算目标同值组内部编号；一次事务写入；返回源行的新 order 和受影响记录数；前端重新读取。

字段默认建议使用整数；若产品需要区分“未设置”和明确的 0，则使用可空整数并固定 `NULLS LAST` 语义。order 允许重复，sortIndex 在不同 order 组可以重复；可建立 `(scope,order,sortIndex,id)` 对应的查询索引。不要给 order 加唯一约束，也不能把 sortIndex 单独设成全局唯一。最终内部编号必须能准确表达目标顺序。

输入范围建议先采用非负整数和与数据库类型一致的明确上限。新增可用最大 order 加默认步长；超上限时追加到当前最大 order 的同值组末尾，不需要因此改掉其他行的可见数字。辅助编号接近上限时，仅整理对应同值组的内部编号。

沿用本项目 `jsonBody()`、`ok()`／`err()`、链式 Hono 路由、HTTP 200 业务信封与权限路径登记。本轮不加入并发版本、协同冲突或分布式锁设计。

## 8. 用户体验细节

| 场景 | 建议 |
| --- | --- |
| 手填数字 | 回车或点击保存才提交；空草稿不自动转成 0；非法输入明确提示 |
| 拖动后数字变化 | 同步显示源行新 order，并高亮该行；其他行可见 order 保留 |
| 操作说明 | “数值越小越靠前；相同数值可拖动调整先后” |
| 拖拽误触 | 使用独立手柄，不干扰文字选择、链接、复选框和数字输入 |
| 无变化与取消 | 放回原位置、目标为自身、Escape 取消均不写入 |
| 保存中 | 暂停下一次排序操作，结果确认后再继续 |
| 明确失败 | 重新读取或恢复服务端确认的顺序，避免残留未保存动画 |
| 网络超时 | 结果可能已保存，先查询确认，不能直接宣称未保存 |
| 非拖拽替代 | 上移、下移、移到某行前后调用同一 move 逻辑；只提供数字输入不总能精确插入同值组 |
| 焦点 | 使用稳定行 ID，操作后恢复合理焦点并反馈对象的新位置 |
| 撤销 | 首版可不做；若做，记录此次源行可见值与内部顺序改动，单次整体恢复；后续写入或切换范围后清除资格 |

WCAG 2.2 对拖动功能要求有无需拖动的单指针替代方式；纯键盘等价操作与这项要求分别评估。[3](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) Atlassian 的指南同样强调替代操作、结果反馈与焦点恢复。[4](https://atlassian.design/components/pragmatic-drag-and-drop/accessibility-guidelines/)

## 9. 业务边界与遗漏入口

| 场景 | 规则 |
| --- | --- |
| 普通编辑 | 改名称、备注、状态不重写 order 或 sortIndex；避免整个旧表单把拖拽结果覆盖回去 |
| 新增 | 未设置 order 时追加完整范围末尾；允许指定 order 时进入该同值组末尾 |
| 删除 | 保留其他 order 和辅助编号空洞，无需每次重新编号 |
| 停用／启用 | 默认保留两项顺序；完整调整视图显示停用项及状态，避免隐藏行歧义 |
| 重新加入 | 默认作为新成员追加；若恢复旧 order，则进入该同值组末尾，不盲目复用旧辅助编号 |
| 复制单条 | 明确追加或复制到原记录后；重新计算辅助编号 |
| 复制整个名单 | 保留 order 数字及完整相对顺序，目标范围的辅助编号可重新生成 |
| 导入 | 保留合法输入的 order；同值导入记录按文件行次序追加，未提供 order 的按规则追加 |
| 批量输入重号 | 合法；两个 99 是两次数值赋值，不是两个记录同时要求第 99 位 |
| 历史重复数字 | 按旧 `(order,id)` 得到确定顺序，分组回填辅助编号，保持可见数字与显示顺序 |
| 固定行 | 固定主线、汇总行等排除在普通移动与组内编号之外 |
| 分组视图 | 真正独立组才有独立范围；临时投影仍需考虑隐藏行 |
| 树形 | 默认仅同父节点兄弟项重排，跨父节点是另一种业务操作 |
| 时间轴 | 不用 order 自动修改开始时间，顺序与排期分别处理 |
| 多行移动 | 后续再做，选中项保持原相对顺序；必须定义多条进入目标同值组的规则 |
| 联表重复行 | 每个可移动对象仅一条，汇总行和重复视觉副本不作为独立成员 |
| 导出／打印／H5 | 已声明消费人工顺序的出口同时使用 order、sortIndex，遗漏辅助字段会让拖拽结果丢失 |
| 已生成文件 | 不自动更新旧 Word／PDF，按产品规则重新生成 |
| updatedAt | 内部组内编号变化不应让其他行显示为刚刚被业务编辑；可单独记录排序操作 |

拖动开始后，所有未移动记录彼此的相对顺序应该保持。允许修改隐藏编号，不代表允许顺便重新排列别的同值记录。

## 10. 当前项目的实施建议

议程线已有可填写的 sortOrder，读取规则是主线优先、sortOrder、ID，主线强制为 0。它最接近本需求：可以保留数字输入，为可调整的并行线补充辅助编号；主线不参与普通组内重排。现有 0—999 校验是该模块的具体规则，不能照搬为全站统一上限。[代码 C1]

供应商等没有人工字段的列表当前按 ID 倒序。首次初始化时应保持旧 ID 序列；可以按当前顺序赋予 order，也可以给同一默认 order 并按旧序列填充辅助编号，选定一种且保持一致。不要因加排序功能而让整个名单首次反转。[代码 C2]

活动媒体已有活动内 sortOrder，H5 仍按 sortOrder、ID 读取；若该模块采用辅助字段，读取端必须同步接入，否则同值拖拽在 H5 看不到。[代码 C3]

本项目筛选控件先改草稿、点击查询才生效。判断是否允许拖拽应看已应用状态，而不是输入框当前是否为空。[代码 C4]

前端沿用当前表格与交互组件；数据库写入与归属校验在名单所属模块。schema 变更同步生成迁移并更新 typed seed，新增路由登记权限。方案不要求为其他字段增加升降序排序，也不要求更换表格库。

建议先在一个范围可控的表格实现：手填值保存→后端移动逻辑→拖拽手势→筛选限制和刷新→导入复制等入口→实际读取出口。不要先实现多行拖拽、复杂树形或全站通用排序服务。

## 11. 性能与验收

同值组重编号最多修改该组 K 行，复杂度与同值组大小有关。若大多数记录都填 0，则该组可能覆盖整个名单，因此辅助字段解决的是可见数字变化，不保证数据库只写一行。

首版在范围可控、操作低频的后台表格，可以读取轻量 `{id,order,sortIndex}` 序列并批量写入实际变化项。若组很大或保存明显变慢，再让隐藏 sortIndex 使用间隔整数、局部调整或其他索引编码。优化内部字段不会改变用户输入的 order 含义。

| 验收 | 预期 |
| --- | --- |
| 输入 order=99 | 实际保存 99，不解释为第 99 行 |
| 改成已有数字 | 进入对应同值组末尾，其他可见数字不变 |
| 再次提交同一个数字 | 原位置不变 |
| 两个 99 之间插入 | 准确位于中间，A、B 仍是 99 |
| 两个相邻整数之间插入 | 可采用目标行数值并用辅助编号表达先后，无需小数 |
| 跨值拖拽 | 仅源行的可见 order 可能变化，位置与锚点关系准确 |
| 开头、末尾、源行自身 | 正确处理真实范围边界；无变化不写入 |
| 同值组跨页 | 后端按完整组计算，翻页和刷新后顺序一致 |
| 筛选后手填／拖动 | 手填可用；拖拽首版关闭并给出完整名单入口 |
| 源行从组内移出 | 旧组其他记录相对顺序保持，无须补齐内部空洞 |
| 普通编辑、删除、停用 | 不意外修改顺序字段 |
| 导入、复制、恢复 | 相同 order 下的内部位置明确，避免复用冲突辅助编号 |
| 保存失败／网络超时 | 完整事务结果可确认，没有半份编号 |
| 固定主线、跨活动目标 | 前后端均执行业务限制 |
| 打印、导出、H5 | 所有指定出口使用完整三项排序规则 |

正确性可以概括为：成员集合不变；未移动记录彼此的相对顺序不变；除源行外的可见 order 不变；最终数据库排序严格符合目标 ID 序列；辅助编号合法；普通业务字段不变。

本轮用纯逻辑枚举验证了 2—6 行、每行 order 取 0／1／2 的组合下，27,882 次“移动到某行之前”的场景：目标顺序正确，且其他记录的可见 order 保持不变。这是算法示例验证，不代表接口、数据库事务或拖拽 UI 已实现或已测试。

## 12. 备选算法与业界参考

**单字段局部改值。** 若最后坚持数据库只能有一个排序字段，可以选择有间隙取中间整数，无间隙时向后调整邻近记录。但 A(99)、B(99) 后若还有 D(100)，改 B 时会继续影响 D；密集区间可能很长，不能承诺只改一两行。

**单字段整表重编。** 实现最短，但会改变用户手填数字；如果采用，应成为明确的“重新整理排序值”动作，或只用于已接受这类行为的特定清单。默认拖拽不应悄悄使用这一路径。

**字符串分数索引。** Figma 2017 年公开文章讨论了任意精度索引，并指出有限精度和相同索引的边界。[5](https://www.figma.com/blog/realtime-editing-of-ordered-sequences/) Rocicorp 的实现提供字符串键生成与比较规则。[6](https://github.com/rocicorp/fractional-indexing) 它们可成为隐藏编号的未来选项，但当前用普通整数即可，不必一开始引入。

**LexoRank。** Atlassian Data Center 的维护文档包含平衡与完整性检查。[7](https://support.atlassian.com/jira/kb/understanding-and-managing-lexorank-in-jira-server/) 它并非没有维护成本的万能解法，当前不需要复制完整体系。

**产品交互参考。** Shopify 集合官方提供拖拽与开头、末尾、指定位置移动。[8](https://help.shopify.com/en/manual/products/collections/collection-layout/) 可以参考其多个操作入口，但官方页面没有说明其内部是否使用本方案的数据结构，不能据此宣称它采用相同字段设计。

没有查到能够证明所有主流产品都采用同一种“可填写整数＋拖拽”规则的官方依据。本文推荐辅助整数，是针对“保留手填数字、精确拖动、实现尽量简单”这几个要求的取舍。

## 13. 库选型与 AI 实现边界

建议采用“成熟拖拽库＋项目自己的排序逻辑”。前端优先评估 dnd-kit，继续使用当前的 Table；后端使用已有 Hono、Drizzle 和数据库事务实现本方案，首版不额外引入排名算法库。AI 可以完成两部分的接入与代码编写，但应按本文明确的规则工作，不能让它自行决定数字输入和拖拽冲突时的产品含义。

### 13.1 哪些交给库，哪些自己实现

| 层次 | 选择 | 责任 |
| --- | --- | --- |
| 拖拽交互 | 使用成熟库，AI 负责接入 | 拖拽手柄、输入传感器、碰撞检测、拖动反馈、取消；业务禁用条件由项目传入 |
| 排序规则 | AI 按规范编写纯逻辑 | 输入数字后进入同值组末尾、根据目标锚点移动、仅修改源行可见值、生成隐藏编号更新计划 |
| 保存与读取 | 使用现有后端与 ORM | 范围与权限校验、事务批量更新、完整排序查询、刷新与错误处理 |
| 体验与验收 | 项目负责定义并验证 | 筛选和分页限制、表格布局、无需拖拽的移动入口、焦点和失败恢复 |

拖拽库产生的是“用户把哪条记录移到了哪里”的交互结果，不会自动理解 order=99 的业务含义，也不会保证数据库刷新后的顺序。库里的数组移动工具同样不能替代后端排序规则。

### 13.2 候选库与推荐顺序

| 候选 | 官方能力依据 | 对本项目的判断 |
| --- | --- | --- |
| **dnd-kit：优先候选** | 当前 React 文档提供 `@dnd-kit/react`、`useSortable`、手柄和禁用配置；仓库说明包含多种输入方式及可访问性支持。[9][10] | 适合在现有 React 表格中加入排序交互；先验证真实表格布局再锁定版本，无需更换整套表格组件 |
| **Pragmatic drag and drop：备选** | 核心为与框架无关的 TypeScript 包，提供元素适配器、目标监听及数组重排工具。[11] | 适合需要较多定制控制时采用；依据其底层 API 形态，预计需要更多项目侧交互组装。核心不自动提供完整无障碍替代操作。[4] |
| **hello-pangea/dnd：列表场景备选** | 官方有语义化表格接入指南，仓库 peerDependencies 声明支持 React 18／19。[12] | 单纯纵向行排序可以评估；需要处理固定列宽或拖动时锁定尺寸，不能因为声明支持 React 19 就跳过本项目验证 |

以上接入成本判断是结合当前项目的推断，不是三套库在本仓库中的实测结论。本次只做选型研究，未安装依赖或完成兼容性验证。

**dnd-kit 必须明确使用哪一代 API。** 当前官方新 React 文档使用 `@dnd-kit/react` 的 `DragDropProvider`，排序 Hook 从 `@dnd-kit/react/sortable` 引入；旧教程使用 `@dnd-kit/core` 的 `DndContext` 与 `@dnd-kit/sortable`。官方提供迁移指南，二者不能混用。[13] 本次查阅的官方更新记录列出了新线 v0.5.0；成熟项目的历史不等于新 API 已有同样长时间的验证积累。[14] 新接入优先验证当前文档对应的版本，验证通过后固定版本与示例来源。

不要为这一项功能更换整套数据表格，也不要因为旧教程常见而新引入已归档的 `react-beautiful-dnd`。[15] 当前已有的画布手势代码也不意味着表格已经具备完整拖拽排序能力。

### 13.3 最容易让 AI 写错的接口边界

**拖拽库的 index 不等于数据库的 sortIndex。** `useSortable` 的 index 表示当前渲染列表的位置。[10] 本方案的 sortIndex 仅在同 order 组内比较，不同组可以重复；分页也会改变当前页面的位置。即使名字相近，也不能把两者直接映射或把拖拽后的页面数组下标全量写回数据库。

前端使用稳定记录 ID 标识行，将一次完成的拖动转换成“源记录＋目标记录＋之前／之后”，由服务端根据真实排序范围计算更新。取消拖动、落点无效、目标序列未变化时不保存。前端传来的页面位置只能用于界面反馈，不能充当数据库排序依据。

建议将“设置数字”和“移动到锚点”各自实现为可独立验证的纯函数：输入当前相关序列和操作意图，输出预期序列与字段更新计划；数据库事务负责应用计划。对于当前两字段的整数方案，这比引入通用排名系统更直接。若未来同值组过大，再评估 fractional-indexing 等隐藏键方案；它只能减少某些重编号需求，仍不能替代范围、数字含义与保存规则。[6]

### 13.4 AI 交付时的检查重点

算法验证应检查结果性质：两个 99 中间插入准确、跨组移动准确、未移动记录相对顺序保持、其他记录可见 order 不变、同值重复提交与无效移动不产生变化。数据库验证应确认事务完整、查询使用全部排序键、刷新和翻页后结果一致。

浏览器验证应使用当前真实 Table：拖动时列宽不跳变，横向滚动后落点正确，手柄不抢占输入框和按钮操作，菜单与弹窗正常，取消与保存失败可恢复；无需拖拽的移动入口能执行等价操作。具有键盘传感器不代表自动满足全部可访问性要求。[3][4]

推荐先完成一个表格的完整保存闭环，再提取被多个页面实际使用的部分。这样既能让 AI 承担实现工作，又有清晰的库能力边界与可验收结果。
