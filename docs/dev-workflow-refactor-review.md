# 开发工作流改造：改动说明（供 review）

这份文档配合 diff 一起读。它不复述代码做了什么——那看代码更快——而是回答代码本身答不了的三个问题：**为什么是这个方案、哪些方案被否掉了、哪些地方我自己也不确定**。

最后一节「请重点看」列了 11 处我认为最值得质疑的地方，每条给了文件行号和判断依据。时间有限的话，读第 2 节（事实基线）和第 6 节（风险清单）就够形成判断。

---

## 1. 这次改动要解决什么

四个需求，来自多 worktree 并行开发（coding agent 各开一个 worktree 写功能，再合回 master）暴露出的具体痛点：

1. 各 worktree 共用一个数据库，互相踩数据
2. 没有种子数据，每个新库都是空的，页面点不动
3. agent 不肯自己登录测试，每次都要人接管
4. 分支合回 master 会产生交叉合并，得每次人工提醒 agent

---

## 2. 事实基线：改动前的实测状态

方案里每个取舍都挂在下面这些实测数据上，不是推测。

**数据库其实从来没隔离过。** `docker-compose.yml` 没写 `name:`，compose 按**目录名**派生 project，于是每个 worktree 各建了一个 postgres 容器：

```
pszx-hdyy-postgres-1                              0.0.0.0:5432->5432   ← 只有它对外通
file-management-module-design-2a97a9-postgres-1   5432/tcp             ← 抢端口失败
table-filter-query-button-fcd1a7-postgres-1       5432/tcp             ← 抢端口失败，已跑 3 天
modal-title-alignment-96f28e-postgres-1           5432/tcp             ← 抢端口失败，已跑 3 天
```

抢输的三个容器端口没发布但继续跑、卷继续涨（共 10 个卷约 490MB，其中 5 个无人引用）。而所有 worktree 的 `.env` 都写死 `localhost:5432`，**实际全部连到同一个库**。

**容器启动比预期便宜得多。** 实测 tmpfs 容器冷启动到可查询 1.5s，`drizzle-kit/api` 的 `pushSchema()` 建完 38 张表 403ms（163 条语句）。这个数字直接推翻了「复用容器省时间」的论证——复用只省约 2 秒。

**没有 migrations，是刻意的。** `drizzle/` 目录为空，`docker-entrypoint.sh` 明写「数据库迁移不在这里做，是有意的」，`docker/README.md` 记了理由和退出条件。所以临时库建表只能走 `pushSchema()`，不引入迁移文件。

**不止一个 agent 工具在用这个仓库。** worktree 列表里有 5 个 `codex/` 分支和 7 个 `claude/` 分支在并行。任何只写进 `.claude/settings.json` 的规则都覆盖不到一半。

**分支很短。** 19 个功能分支里 16 个是 0-ahead（早就合完没删），有活儿的三个分别带 2 / 1 / 1 个 commit。**最大 2 个 commit**——这个数字决定了 rebase 和 squash 的成本差异可以忽略。

**agent 不肯登录不是文档措辞问题。** 「代替用户输入密码进行认证」在 agent 的安全规则里是无条件禁止项，明确规定即使用户显式要求、提供全部凭据、声明授权也依然拒绝。所以在 `AGENTS.md` 里把账号密码写得越清楚，越是正面撞在这条上。唯一可行的方向是让 agent **根本不需要碰密码这个动作**。

## 4. 四块改动的设计取舍

### 4.1 双启动路径

`bun run dev` 给每个 worktree 起一次性 tmpfs 容器（随机端口、`--rm`），建表灌种子后起前后端，退出即销毁。`bun run dev:persist` 保持原行为。

**为什么用 tmpfs 而不是「退出时 DROP DATABASE」**：让「不持久化」成为**物理事实**，而不是一段需要正确执行的清理逻辑。上面那三个跑了三天的僵尸容器，就是「清理逻辑会失效」的现成证据。

**为什么不复用容器（进程级而非 worktree 级）**：复用只省约 2 秒，代价是引入两个新问题——需要一个回收器，以及「schema 改了但容器是旧的」导致在过期表结构上调试。用 2 秒换这两个问题不划算。

**为什么容器内用 TCP 探活而不是 unix socket**（`dev-db.ts:101`）：postgres 官方镜像初始化期间会先起一个只监听 unix socket 的临时实例，走 socket 探活会在初始化没完成时就报 ready。

**连接串发现**（`dev.ts:195` 写入 / 删除）：临时库端口随机，而 `.env` 写死 5432。不解决的话 `bun run db:studio` 会静默连到持久库，agent 在另一个库里看到一堆真实数据，然后得出完全错误的结论。方案是把真实连接串写进 gitignored 的 `apps/server/.dev-db.env`，db 系列脚本按 `.env` → `.dev-db.env` 顺序读。这依赖 bun 的两条行为，均已实测（bun 1.3.14）：后一个 `--env-file` 覆盖前一个；文件不存在时静默忽略（所以 dev 没跑时自动回落到持久库）。

**硬杀路径**（`dev-db.ts:76`）：`--rm` 只在容器正常停止时生效，任务管理器强杀 / 编辑器关掉终端时信号处理器根本没机会跑。容器 label 里记了 worktree 路径，启动时清掉指向已删目录的那些——这对本仓库尤其必要，因为 worktree 是 agent 建了删、删了建的。

### 4.2 种子机制

`apps/server/src/dev-seed/`，数字前缀决定执行顺序，runner 是 glob + sort + 依次 await。

**为什么不做拓扑排序**：初版方案是每个模块 `modules/<名>/seed.ts` 加 `dependsOn` 再拓扑排序。评审时被判定为过度设计——外键依赖只有 10 个模块、最深 4 层，数字前缀足以表达；拓扑排序多一个排序器要维护，且写错 `dependsOn` 时报错是「循环依赖」这种间接信息，不如「外键报错 + 看文件名顺序」直观。

**为什么不用一个集中文件**：这是唯一不能放弃的性质——**新增种子不碰任何已有文件**。5 个 worktree 并行时，任何中心文件都是固定的合并冲突源。序号留了间隔，新种子插空档即可。

**防腐烂的三条机制**（这是「可迭代」的实质）：

1. 种子一律用 drizzle 的 typed insert，**不写裸 SQL**——字段改名、加非空列，`bun run typecheck` 当场报错。实测 8 个 dev-seed 文件全部在 tsc 覆盖内。
2. `bun run dev` 每次都跑全量种子，坏了立刻炸，不需要额外的检查工序。
3. 种子失败 = dev 启动失败（`dev.ts:67`），并指名是哪个文件。在灌了一半的库上调试得出的结论全是错的，比启动失败难查十倍。

**种子不做幂等**：库每次都是全新空库，省掉所有 `onConflictDoNothing` / 先查再插的噪音。

**为什么要重置序列**（`bootstrap.ts:51`）：种子写死了 ID（`context.ts:17` 的 `DEMO`），而 `generated by default as identity` 的序列不会因显式插入而前进——不推一把的话，从界面新增的第一条记录就撞主键。写死 ID 的收益是 `AGENTS.md` 能直接给出可导航的 URL，以及每次报错都可复现。

**故意埋的数据**：议程里两个环节时间重叠且挂同一个人员（`30-agenda.ts` / `50-member.ts`），用来触发「同一人员环节时间冲突」提示；人员灌到 24 条（默认 pageSize=10）让分页真的能翻页；供应商含停用状态和多类目用于筛选。**不灌** `venue_layout` 的画布 JSON 和 `supplier_quote` 的附件——前者形状由前端画布决定、手写等于把内部格式复制进种子，后者要求磁盘上有真实字节。

### 4.3 免密登录

`GET /api/dev/login`（`routes.dev.ts:55`）内部调 `auth.api.signInEmail({ asResponse: true })`，原样透传 Better Auth 签发的 cookie 再 302。

**为什么不是「dev 模式直接跳过认证」**：那样 `_authenticated` 守卫、会话过期、`AGENTS.md` 里专门记过的「登录后必须 `removeQueries(sessionQueryKey)` 否则被弹回登录页」这类坑，在开发环境永远不执行，只会在生产环境露头。现在这条路走的是完整真实链路——真 session、真 cookie、照常过 `sessionMiddleware`。

**为什么种子用 `signUpEmail` 而不是手写 user/account 两张表**（`00-user.ts`）：密码哈希的算法和参数归 Better Auth 管，手写一份必然在某次升级后悄悄失配，而失配的表现是「登录返回 401」这种完全不指向种子的症状。

**生产断言的判据**：初版是「看起来像不像生产」的黑名单（`NODE_ENV === "production" || WEB_DIST_DIR`）。深度评审指出黑名单永远补不全，**已改成开发白名单**：`APP_ENV=development` 与 `DEV_AUTH_BYPASS=1` 两个都对上才挂载，生产特征作为第二层否决；另加回环地址校验。详见 [§8](#8-深度评审的处理结果)。

### 4.4 线性历史

两层，一次 `postinstall` 落地：`merge.ff=only` + `pull.ff=only`，加上版本化的 `.githooks/`。

**为什么是 git config 而不是 `.claude/settings.json` 的 hook**：仓库同时被 Claude Code 和 Codex 的 worktree 使用，只覆盖一个工具的规则等于只防住一半，还会造成「已经防住了」的错觉。实测 `.git/config` 被全部 12 个 worktree 共享（`extensions.worktreeConfig` 虽然开着，但没有任何 worktree 覆盖过 merge 相关配置）。

**为什么要两个钩子**：`git merge` 撞上冲突时**不会**走 `pre-merge-commit`，而是等你解完冲突再 `git commit`——那一步触发的是 `pre-commit`。只装前一个的话，最常见的那条路径（有冲突的合并）是漏的。`pre-commit` 只在存在 `MERGE_HEAD` 时拦，普通提交不受影响。

**为什么挂 `postinstall` 而不是 `bun run setup`**：新 worktree 必然要 `bun install`，所以必然被执行到，不依赖任何人记性。`setup-git.ts:37` 在没有 `.git` 时短路退出，保证不影响镜像构建。

**为什么改推 rebase 而不是 squash**：初版推荐 squash，理由是「把 N 次冲突重放压成 1 次」。实测每个分支只带 1~2 个 commit，这条理由不成立，rebase 更合适且保留提交粒度。

**分工**：agent 自己 `git fetch && git rebase master` 并跑通检查后**停下**，合进 master 由人执行 `git merge --ff-only`。理由是合并不可逆，且并行分支的合并顺序会互相影响；顺带这一步天然是验收关口——`--ff-only` 失败就说明 rebase 没做对。

### 6.1 接口文档曾会泄露后门（已修，但请确认修法）

`export const routes = app.route(...)` 返回的就是 `app` 本身，所以 dev 路由虽然不进 `AppType`（编译期链式类型只包含链上的调用），**运行时 `app.routes` 里却有它**。而 `gen-api-docs.ts` 遍历的正是 `app.routes`，产出的文档挂在 session 中间件之前、任何人不登录就能访问。

现在的修法是在 `gen-api-docs.ts` 的路由遍历里无条件跳过 `/api/dev/`。**请确认这是不是正确的层**——另一种修法是让 dev 路由挂到一个独立的 Hono 实例上，从根上不进 `app.routes`。我选了前者因为改动面小，但它属于「记得在文档生成器里排除」这类需要维护的约定。

### 6.2 生产断言的判据是否覆盖所有部署形态

`routes.dev.ts:29` 判定「生产形态」用的是 `NODE_ENV === "production" || WEB_DIST_DIR`。如果将来出现一种部署既不设 `NODE_ENV` 也不设 `WEB_DIST_DIR`（例如前后端分域名部署、server 不托管前端），这条断言就漏了。请对照实际部署方式确认，或考虑改成白名单式判断（只在显式的开发编排里允许）。

### 6.3 重定向白名单是否够严

`routes.dev.ts:47` 只挡了 `//` 开头。`/\evil.com` 在部分浏览器里也会被当协议相对地址处理。这是开发专用路由、影响面有限，但一行就能一起挡掉，请判断值不值得。

### 6.4 序列重置 SQL 的边界

`bootstrap.ts:51` 的 DO 块只扫 `public` schema 且 `is_identity = 'YES'` 的列。请确认：分区表、非主键的 identity 列、将来可能引入的其它 schema 是否需要覆盖；以及 `setval(seq, greatest(max_id, 1), max_id > 0)` 第三参数（`is_called`）的语义是否符合预期——空表时应该让下一个值取 1。

### 6.5 种子顺序没有机器校验

数字前缀的正确性完全靠人排。两个并行分支各插一个新前缀时，可能出现「新模块依赖的表在它之后才灌」。目前靠外键报错兜底（会当场炸，不会静默），但错误信息是 FK violation，不直接指向「顺序排错了」。请判断是否需要在 runner 里加一层更友好的提示。

### 6.6 对 bun 环境变量优先级的依赖

`dev.ts:67` 依赖「进程环境变量优先于 `--env-file`」这条 bun 行为来注入 `DATABASE_URL`。已在 bun 1.3.14 实测成立，但**没有测试守护**。bun 升级改了语义的话，失败方式是「悄悄连到持久库」——正是这次要消灭的那类问题。请判断要不要加一条断言（例如 bootstrap 启动时校验实际连到的库名是 `app_dev`）。

### 6.7 硬杀后的残留窗口

`dev.ts:195` 的 cleanup 只在正常退出时跑。硬杀之后：容器要等下次 `bun run dev` 被同名顶掉，`.dev-db.env` 会残留并指向一个已死的端口。后者的失败是「连接被拒」这种响亮失败，我判断可接受；请确认这个判断。

### 6.8 tmpfs 上限

`dev-db.ts` 里写死 512MB。当前 38 张表 + 24 条人员远未触及，但种子按需长大后可能撞上，撞上时 postgres 的报错未必指向 tmpfs。请判断是否要调大或加提示。

### 6.9 prune 里的常量耦合

`prune.ts:9` 的 `CANONICAL_COMPOSE_PROJECT` 必须与 `docker-compose.yml` 的 `name:` 保持一致。改了一处忘了另一处，持久库的卷就会出现在删除清单里。默认 dry-run 兜住了这个，但这仍是一个分两处维护的耦合点。

### 6.10 `dev:persist` 下也开着后门

`dev.ts` 对两条路径都设了 `DEV_AUTH_BYPASS=1`。持久库里未必有 `dev@example.com`，此时 `/api/dev/login` 返回带解释文案的 500。这是有意的（两条都是本地开发），但如果认为持久库不该有后门，这里应该收紧。

### 6.11 钩子的绕过路径

`git merge --no-verify` 和 `git commit --no-verify` 可以跳过钩子，报错文案里显式写了这个出口。这是有意保留的逃生舱，请确认可以接受。

另外 `.gitattributes` 新增了 `.githooks/* text eol=lf`：钩子文件没有扩展名，原有的 `*.sh` 规则覆盖不到，checkout 出来变 CRLF 会让 `#!/bin/sh\r` 以完全不提行尾的方式报错——`.gitattributes` 里原本的注释正好记了这个坑。

## 7. 明确没做的事

- **不改写 git 历史**。`AGENTS.md` 里旧项目测试环境的凭据已从当前版本移到本地 `.env`（`.env.example` 只留变量名），但它仍在 git 历史里。清理需要重写历史，会打断所有在飞的 worktree，应当等分支都合完后单独做。
- **不引入 migrations**。仓库已记录这是刻意推迟的决定，退出条件写在 `docker/README.md`。
- **不做 Claude Code 专属的 hook**。覆盖面只有一半，却会造成「已经防住了」的错觉。
- **不执行 `bun run prune --yes`**。它删的是数据库卷，不可逆，留给人决定。当前它列出 5 个孤儿卷和 13 个已合入分支。
- **不修 `docx.test.ts` 的 3 个既有失败**。不在本次范围内。
