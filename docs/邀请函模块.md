# 邀请函模板与生成

> 版式归 Word 文件，系统只负责填空和留档。
>
> 可分享的网页版：<https://claude.ai/code/artifact/99f01d05-4583-406b-94cb-fd2ce675d259>（内容与本文一致，改了要一起改）

---

## 为什么改

原来是用代码画邀请函：一个 `issuer` 枚举决定用哪套 logo、抬头和称谓，正文、落款、联系人各占数据库一列，前端再用 docx 库把它们拼成版面。

拿到业务方三份真实模板之后，这条路走不通了：

- 排版规格细到「固定值 28 磅行距」「首行缩进 2 个字符」「logo 2.4cm × 5.71cm 左上角对齐」「红头下面两条红线，一粗一细」——这些是模板作者以 Word 批注形式逐段标注的
- 标题用方正小标宋简体，商业字体，前端不能分发
- 用代码复刻，既抄不全，抄的过程中还必然失真

更要命的是两套渲染器已经开始漂移：页面预览把「附则」排在落款之后，导出的 Word 却排在联系人之前。同一份邀请函，看到的和下载的版面顺序不一样，而且没人发现。

**结论：不要重建版式。直接拿业务方那份真实的 .docx 当模板，往里填空。**

## 现在的模型

```
模板    一个 .docx 文件 + 它里面有哪些 {{变量}}。全局池，不绑活动。
  ↓     生成时选用一个
批次    一次生成操作。装下这次填的变量取值，以及用的是模板文件的哪个版本。绑活动。
  ↓     一次生成 N 个人
记录    批次里的每一个人，存一份姓名快照。
  ↓     下载时
        按快照现渲染 .docx
```

三条关键性质：

1. **版式只存在于那个 .docx 里**——数据库里没有，代码里也没有
2. **生成时不产文件**——只写快照，下载时才渲染
3. **每批独立留档**——后续再生成不影响已有批次，老批次永远可下载

对应四张表：`invitation_template` / `invitation_batch` / `invitation_record` / `invitation_download_log`。

## 变量

| 类型 | 有哪些 | 谁来填 |
| --- | --- | --- |
| 系统变量 | `{{姓名}}` `{{发函日期}}` | 生成时自动填，用户看不到输入框 |
| 自定义变量 | 其余任何 `{{xxx}}` | 每次生成时在生成页填写 |

**正文不做成变量**，直接写死在模板文件里。正文和版式本来就是一体的，拆开在两个地方维护必然对不上；而且真实模板的正文就是那一场活动的正文，本来就是一次性的。改正文 = 改模板重新上传。

变量清单由服务端解析文件得出，客户端传什么都不作数——它是文件的派生物，让客户端传就等于允许「声明的变量」和「文件里真有的变量」不一致。

## 怎么用

### 业务方：准备模板

1. 在「新增模板」弹窗里点**下载示例模板**——就是商会那份真实模板
2. 用 Word 打开，改文字
3. 把要替换的地方写成 `{{变量名}}`
4. 删掉全部批注（批注会跟着生成的邀请函一起显示出来）
5. 另存为 .docx

### 运营：建模板

上传文件 → 系统自动解析并试渲染 → 页面列出解析到的变量，标明哪些是系统自动填的 → 点「预览样例」看效果 → 保存。

> **上传时会用假数据试渲染一次，渲染不出来直接拒绝保存。**
> 这一步不能省：解析只证明「找得到占位符」，试渲染才证明「改写完还是一份完整的 docx」。不在这里挡住，坏模板要等到某次真的生成 82 份时才炸，而那时用户面对的是一句和上传动作毫无关联的报错。

### 运营：生成邀请函

入口：`活动详情 › 邀请函 › 生成邀请函`

选人（**只能从本活动人员里选**）→ 选模板 → 填变量（自动带出该模板上次填的值）→ 选发函日期 → 预览一份 → 生成。

### 下载

单份下载，或整批打包成 ZIP。文件名规则：

```
活动名称_姓名_证件号码后四位_邀请函_批次号.docx
```

下载是敏感操作，每一次都留审计记录：下载人、时间、活动、人员范围、文件数量、下载结果。

## 几个决定，和它们的理由

| 决定 | 理由 |
| --- | --- |
| 模板全局，生成绑活动 | 三份真实模板是按发函主体（联盟 / 商会 / 专班）分的，不按活动分；而选人只能从活动人员里选，一份邀请函也必须归属某场活动 |
| 每批独立留档 | 曾经做过「一人一函、重新生成即覆盖」。实测不可接受：给同一批人重做一次，上一批就整个变成 0 份、按钮全灰——而那批文件在现实里可能已经发出去了，事后还要能重新下载 |
| 生成时不产文件 | 预生成的唯一正当理由是快照，而**快照是数据快照，不是文件快照**。存了快照之后文件完全可以按需渲染：生成不会失败（就是一次写库事务）、不需要文件存储、不会留下孤儿文件 |
| 文件必须由服务端交付 | 上一版 docx 在客户端生成，服务端根本不知道下载发生过，审计只能靠前端自觉上报——而那是可以绕过的：拿到快照自己渲染，一条日志都不留 |
| 本轮只做 Word | PDF 要装 LibreOffice、改部署形态，还要解决商业字体授权。先把 Word 这条链路跑通，将来接 PDF 时不用推翻任何东西 |

## 几个坑

### Word 会把占位符拆散

`{{姓名}}` 在 XML 里很可能是 `{` `{姓名}` `}` 三段——输入法、拼写检查、rsid 都会造成这种切分。朴素的字符串替换会**静默失配**：模板看着没问题，生成出来的文件里占位符原样躺着。

解析器把同一段落里所有文本拼起来找占位符，再按原始偏移分发回各个片段，所以业务方写模板时不用刻意规避。

替换只改写 `<w:t>` 的内容，绝不碰 `<w:rPr>`——这条有回归测试兜着，破了的话替换进去的人名会掉回默认字体，而那只有打开生成结果才看得见。

### 嵌入的子集化字体

商会模板嵌了 4 个字体，每个 176–270 KB——完整中文字体是 5–20 MB，说明它们是**子集化**的，只含原文档出现过的那些字。后果：替换进去的人名如果含有原文档没出现过的字，在没装对应字体的机器上可能显示不出来。

页面预览已经绕开这个问题（预览不使用嵌入字体）。.docx 输出建议业务方另存时勾选「嵌入所有字符」，或者干脆不嵌入，依赖目标机器自带的仿宋 / 黑体 / 楷体。

### 不支持 .doc

旧版 .doc 是 OLE 二进制格式，不是 zip，解析器读不了。前端在选文件时就会拦下并提示先用 Word 另存为 .docx。

### 批注要清掉

模板作者的排版规格批注会跟着生成的邀请函一起显示出来。三份模板里的两份 .docx 已清理，原件和提取出来的排版规格留档在 [`docs/模板/`](模板/)。

## 与需求文档的偏离

| 偏离 | 原因 |
| --- | --- |
| 文件名末段用批次号而非生成日期 | 文档那条规则是在「一人一函」的假设下定的。改成每批独立留档之后，同一个人同一天生成两批，文件名会完全一样。批次号形如 `YQH20260819000001`，前缀里已经含了生成日期，信息一点没少，还天然唯一 |
| H5 相关全不做 | 项目约定，H5 本期不建 |
| 提醒不做 | 站内信的唯一阅读端是 H5 消息中心，短信文案的落脚点也是 H5。H5 不做的前提下，这条链路两个渠道都指向一个不存在的页面 |

---

## 本期不做

PDF 下载、H5 邀请函展示、生成后的站内信 / 短信提醒。三者都不影响现在这条链路，将来要接也不用推翻已有的模型。
