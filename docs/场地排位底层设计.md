## 1. 分界线

整份设计压在一句话上：

> **核心存"有哪些位置、叫什么、什么性质、谁坐"；编辑器存"长什么样、在哪里"。**

| 归核心（关系表，有主键，可被引用） | 归编辑器（不透明 blob，核心一个字段都不认） |
| --- | --- |
| 区域：id、名称、类型；活动层再加用途、可用点位、启用状态 | 区域的 x/y/宽高/多边形顶点/填充色 |
| 位置：id、编号、种类（座/桌/站位）、等级；方案层再加启用、分组 | 位置的坐标、旋转、尺寸、图标 |
| 分配：谁坐哪个位置 | 布局预设、行列间距、编号规则、家具目录、拖拽手感 |
| 状态、版本、操作留痕 | 底图图片、缩放、图层 |

判据不是"看着像哪类"，是**有没有别的东西引用它**。座位被分配引用，所以座位是核心；座位的坐标没人引用，所以坐标是编辑器的私事。

这条线划对了，换编辑器就是换 blob 的格式 + 重写一个投影函数（§4），核心表、状态机、权限、通知、级联规则全部不动。

## 2. 模块划分与依赖方向

```
modules/venue/      场地库 + 活动场地空间      ← 不 import seating
modules/seating/    环节排位方案 + 座位分配     → 只读 venue / member / agenda
```

**venue 不知道排位存在。** 它是可复用基础数据，加了对 seating 的依赖，场地库就再也不能独立使用了。反向依赖必须单向。

按 `AGENTS.md` 的"一个模块多个子资源拆成多个前缀"：

| 前缀 | 归属模块 | 管什么 |
| --- | --- | --- |
| `/api/venue/*` | venue | 场地库主记录、区域、底图位置、布局保存 |
| `/api/activityVenue/*` | venue | 活动引用场地、活动区域用途 |
| `/api/seating/*` | seating | 排位方案、布局保存、分配、确认/退回/作废 |

### 2.1 前端信息架构：全局菜单只有「场地管理」

**原型的菜单设计不采纳。** 它建了一个「排位管理」一级菜单，下挂场地库、排位方案列表、排位确认三个二级项。正确的划分是：

| 放哪 | 页面 | 为什么 |
| --- | --- | --- |
| 全局菜单（单项，不套分组） | 场地管理 `/venue` + 场地画布 `/venue/$venueId/canvas` | 场地是跨活动复用的基础数据，不属于任何活动 |
| 活动详情标签页 | 场地空间、排位（方案列表 + 确认/退回合一） | 两者都必须带活动上下文才能工作 |

这跟邀请函模块的划分是同一条判据（模板留全局、生成和记录进活动详情）：**需要活动上下文的页面不放全局菜单，否则用户的第一步永远是"先选一个活动"**。

顺带消掉原型的一处冗余：`seating-list.html` 和 `seating-confirm.html` 两页的列几乎完全重合，拆开的唯一理由是它们挂在两个二级菜单下。菜单一收就合成一页，加状态筛选即可满足 BR-DEV-012。

已知代价：没有跨活动的"全平台待确认"视图。若后续证明是真痛点，出口是**工作台加一块待办卡**，不是把菜单加回来。

## 3. 四条不变量

这四条是"稳定"的具体含义。任何实现（包括第一版抄旧系统）都不许违反。

### 3.1 位置是实体，引用它的是主键，不是编号也不是坐标

`seat_assignment` 指向 `segment_seat.id`。**不指 label**（旧系统 `findSeatLabel()` 靠遍历 JSON 比对 label 反查，改一次编号历史就错位），**不指坐标**（拖一下就断）。

分配行上**不存 label 快照**。"发通知那一刻座位叫什么"由确认动作的日志快照负责（§6），因为分配发生在确认之前，分配时抄下来的编号到确认时可能已经改过。

### 3.2 布局和分配是两条正交的写路径

```
布局写路径   saveLayout                 改的是"有哪些位置"
分配写路径   assign / unassign / swap   改的是"谁坐哪"
```

两条路径共享状态机，但**互不调用**。

旧系统把两条揉成一条：一次 `PUT .../operate` 提交整份 `plan_json`，里面既有几何、又有 `assigneeId`、还有操作日志。后果是每次拖动一个座位都在重写全部人员绑定，而且换编辑器时人员绑定逻辑必须跟着重写一遍——它本来跟编辑器毫无关系。

所以：**画布保存的请求体里没有人。**

### 3.3 座位只在两层落行：场地库 → 环节方案

```
venue_seat  ──复制──▶  segment_seat  ◀──引用──  seat_assignment
（物理底图）             （本环节实际用的位置）
```

活动层**只快照区域，不落座位行**。依据是结论单 C-006 的原话：

> 固定座位场馆可维护基础物理座位；**具体哪些座位启用、重要顺序、谁坐哪里由环节排位方案决定**。

所以活动区域上的 `capacity`（可用点位）是一个**规划数字**，不是权威的座位集合。评审提的"活动把 260 改成 236，系统不知道禁用哪 24 个"——按 C-006，活动层本来就不该知道；哪 24 个不用，是环节配排位时在 `segment_seat.enabled` 上表达的。`capacity` 因此**不作为确认时的硬约束**，超出只提示（§7）。

> ⚠️ 这是对开发版 §7.2 字面的一处**刻意偏离**：那里把"座位编号、点位"也写进了活动场地空间配置的维护范围。照字面建，每个座位要存三份拷贝、三处同步规则、活动层再要一套座位编辑界面，而 C-006 已经把启用决策判给了环节层——活动层那份拷贝没有任何人写。原型 `activity-space.html` 也只有区域级的"调整区域用途/禁用区域"，没有座位编辑。

复制而不是活引用，白拿两个性质：

- 同一区域被多个环节引用，各自一套 `segment_seat`，**天然互不覆盖**（AC-DEV-010A 不需要额外写代码保证）
- **底图可以随便改，改不坏任何已确认的排位**——场地库删掉一个座位，已存在的方案毫发无损

代价是上游改动不会自动流下来，需要一个显式的"重新从场地同步"动作（旧系统的 `handleResyncTemplate`），二次确认后才覆盖。这个代价是要的：自动流下来意味着已确认的排位会静默变形。

### 3.4 状态机只认"发生了写操作"，不认写的是什么

`saveLayout` 和 `assign` 都会把方案打回 `pending`。状态机不需要知道调用方是画布还是分配面板——这正是它能在编辑器更换后存活的原因。

## 4. 编辑器契约

前端一个编辑器需要实现的全部接口：

```ts
interface LayoutEditor<TData> {
  /** 存进 layout.rendererKind，用来在渲染时挑实现 */
  readonly kind: string;
  readonly version: number;

  /** jsonb 取出来是 unknown，解不出来就走降级视图。不做版本迁移 */
  safeParse(raw: unknown): TData | null;

  /** 渲染 + 交互，随便怎么实现 */
  render(data: TData, ctx: EditorContext): ReactNode;

  /** 唯一的出口：把编辑器私有格式投影成核心语义 */
  project(data: TData): ProjectedLayout;
}
```

两层的投影产物不一样，分开定义——`enabled` / `groupLabel` 是环节层才有的概念，场地底图不该有（哪些座位这次不用是环节的决定，§3.3）：

```ts
// 场地库编辑器产出
type VenueProjection = {
  zones: { externalId: string; name: string; kind: ZoneKind; ordinal: number }[];
  seats: {
    externalId: string;
    zoneExternalId: string;
    label: string;        // A1 / 3桌2号
    kind: SeatKind;       // seat | standing —— 只有这两种，见下
    rank: SeatRank;       // normal | vip
    ordinal: number;
  }[];
};

// 方案编辑器产出（只有一块区域，没有 zones）
type PlanProjection = {
  seats: {
    externalId: string;
    label: string;
    kind: SeatKind;
    rank: SeatRank;
    enabled: boolean;     // 本环节启不启用（旧系统的 blocked）
    groupLabel?: string;  // 团体相邻用，纯字符串；颜色留在 blob 里
    ordinal: number;
  }[];
};
```

`project()` 是整份设计的枢纽——**编辑器私有格式流向核心语义的唯一通道**。换编辑器 = 换 `kind` + `safeParse` + `render` + `project`，别的地方一行不改。

> **只投影"能分配给人的位置"。** 圆桌、长桌、舞台、讲台、绿植、屏风——没有任何东西会引用一张桌子，`seat_assignment` 也永远不会指向一个舞台。按 §1 那条判据（有没有别的东西引用它），它们纯粹是"长什么样"，留在 blob 里由渲染器画出来，一行都不进核心表。
>
> 所以 `SeatKind` 只有 `seat | standing` 两个值。结论单 C-006 说的"桌位"是**桌子旁边的一个座位**（label 形如「3桌2号」），不是桌子本身。
>
> 旧系统把 12 种家具塞进同一个 `SeatItem[]`，再用 `seatWeight()` 在统计时把桌台的权重算成 0——等于用一个运行时函数维护"哪些是真座位"，而这件事靠"根本不入库"就表达完了。顺带修掉旧模型一处不自洽：它给沙发记 2 个座位的容量，但 `assigneeId` 只有一个，实际只能坐 1 人。核心里**一个位置就是一个位置，容量恒为 1**，沙发要坐两人就投影成两个位置。于是"可用点位数"就是 `count(*)`，不需要任何权重函数。

服务端契约：

```
POST /api/venue/saveLayout                                        ← 已实现
  in : { venueId, layout: { rendererKind, rendererVersion, data }, zones, seats }
  out: ok({ zones: { added, updated, removed },
            seats: { added, updated, removed } })

POST /api/seating/saveLayout                                      ← 待实现（§12 第 4 步）
  in : { planId, layout: {...}, seats }
  out: ok({ applied: true,  seats: { added, updated, removed } })
     | ok({ applied: false, blocked: [{ seatId, label, memberName, reason }] })
```

场地库那条**没有** `applied` 字段：只有方案层才可能因为"位置上有人"被拒（§5），在场地库层它会恒为 true，加一个恒真的字段只是噪音。

**服务端不校验也不解析 `data`。** 它只校验投影出来的语义：名称非空、同区域内 label 唯一、`zoneExternalId` 有对应区域。`data` 对服务端是一团字节。

被拦下时返回 `ok({ applied: false, blocked })` 而不是 `err(...)`——`shared/result.ts` 的 `ApiError` 只有 `code + message`，塞不下结构化清单；而且这不是错误，是一个正常的业务结果（"这次没保存，因为这些位置上有人"）。为它扩信封会污染所有模块的返回类型。

### rendererKind 一经建立不可变

一个 venue 或一个 plan 的 `rendererKind` 写下之后不再更换。**换编辑器只影响新建的对象**：老对象要么保留老渲染器的代码继续看，要么走降级视图（§9）。

这条把评审指出的矛盾消掉了：新编辑器生成的 `externalId` 跟老的完全不同，如果允许用新编辑器重开老方案，归并时会被判成"删掉全部旧位置"，有分配就整次保存被拒。既然不允许重开，`externalId` 就可以一直保持编辑器私有，不需要引入一套编辑器无关的位置标识体系。

`externalId` 只在**一次保存内部**用来做归并。它有一条硬要求：**同一份 `data` 两次 `project()` 出的 `externalId` 必须一致**，否则每次保存都成全删全增。这是编辑器实现方的责任，需要一条单测守住。

## 5. 归并规则（saveLayout 做什么）

按 `external_id` 三路归并：

| 情况 | 动作 |
| --- | --- |
| 请求里有、库里没有 | insert |
| 两边都有 | update 名称/编号/种类/等级/启用/顺序/分组 |
| 库里有、请求里没有 | 见下 |

### 位置消失时

- **场地库层（`venue_seat`）**：**物理删除**。没有任何分配指向它（§3.3），删了不会坏任何东西；方案层引用的是 `sourceExternalId`（文本快照）而不是外键，也不会悬空。原先设计成软删 + "同 externalId 再出现就复活原行"，实现时改掉了——物理删除让"再出现"退化成一次普通 insert，省掉复活分支和 partial unique index，也符合仓库"软删除默认不加"的规矩。
- **方案层（`segment_seat`）**：先查有没有生效分配。无分配 → 软删（那里的行被 `seat_assignment` 引用，不能物理删）；**有分配 → 整次保存被拒**，返回 `blocked` 清单。

拒绝而不是级联解绑，理由很实在：删座位在编辑器侧就是一次拖动或一次框选删除，用户很可能不知道那个位置上有人。把清单摆出来让他先去解绑再回来，是唯一不丢信息的路径。

### 位置被禁用时（同样要拦）

`enabled: true → false` 且该位置有生效分配，**和删除同等处理**：整次保存被拒，进 `blocked` 清单。

漏了这条会出现：A 座已分配、B 座空着，把 A 禁用后"启用位置数 1 ≥ 分配数 1"照样成立，人却实际坐在一个禁用位置上。所以确认时的容量校验不能只比数量，必须**逐条**查每条分配指向的位置仍然有效（§7）。

### 归并键按"场地/方案"而不是"区域"

`unique(venueId, externalId)`，不是 `unique(zoneId, externalId)`。编辑器生成的元素 id 本来就全局唯一，按场地建键换来一个实际好处：把一个位置从 A 区拖到 B 区，是同一行的 `zoneId` 变了（id 保持不变），而不是"删一个再建一个"。

### 编号唯一性守在应用层，不建数据库约束

同区域内编号不重复这条规则要守，但**不能**建 `unique(zoneId, label)`：把 A1 和 A2 两个位置的编号对调是完全合法的操作，而 Postgres 的唯一约束默认逐语句检查，两条 UPDATE 里的第一条就会撞上。

之所以敢只靠应用层：`venue_seat` 只有 `saveLayout` 一条写入路径，那条路径 100% 会过校验。**出现第二条写入路径时，这个判断要重新做。**

## 6. 数据模型

命名和风格跟 `modules/agenda/schema.ts` 一致：bigint identity 主键、`text` 存枚举加 `$type<>()`、jsonb 存整份重写的结构、软删用状态列不用物理删除。

### venue 模块

```
venue                  场地库主记录
  id / name / address / description
  status               enabled | disabled          ← 只有这一个状态，不做 draft/published
  audit                createdBy/At, updatedBy/At

venue_layout           场地画布 blob（与 venue 一对一，单独表：大字段，列表页不查）
  venueId (unique) / rendererKind / rendererVersion
  data                 jsonb —— 核心不解析

venue_zone             区域
  id / venueId / externalId / name
  kind                 seating | function | checkin | material
  ordinal
  unique (venueId, externalId)                      ← 归并键
  unique (id, venueId)                              ← 给 venue_seat 的复合外键当靶子

venue_seat             物理底图位置（固定座位场馆才有；自由场地这张表可以是空的）
  id / venueId / zoneId / externalId / label
  kind                 seat | standing —— 只有能分配给人的位置进表
  rank / ordinal
  unique (venueId, externalId)                      ← 归并键，按场地不按区域（§5）
  fk (zoneId, venueId) → venue_zone(id, venueId)    ← 区域必须属于同一场地，cascade
  ※ 没有 enabled：哪些位置这次不用是环节的决定（§3.3）
  ※ 没有 unique(zoneId, label)：编号对调是合法操作，会撞逐语句检查（§5）

activity_venue         活动引用的场地
  id / activityId / venueId
  name                 快照，场地改名不影响历史
  note / status
  unique (activityId, venueId)
  unique (id, activityId)                           ← 靶子

activity_venue_zone    活动区域（只快照区域，不快照位置）
  id / activityVenueId / activityId / sourceZoneId
  name                 快照
  purpose              mainSeating | breakout | checkin | standby
  capacity             可用点位；规划数字，不是权威座位集合
  status               active | disabled
  fk (activityVenueId, activityId) → activity_venue(id, activityId)
  unique (id, activityId)                           ← 给 plan 的复合外键当靶子
```

### seating 模块

```
segment_seating_plan   环节排位方案
  id / segmentId / activityId / activityVenueZoneId
  status               pending | confirmed | rejected | voided
  version              第几次确认发布，确认时 +1
  savedBy/At  confirmedBy/At  rejectedReason
  partial unique (segmentId) where status <> 'voided'   ← 一个环节最多一个当前有效方案
  unique (id, segmentId)                                ← 靶子
  fk (segmentId, activityId)          → activity_segment(id, activityId)
  fk (activityVenueZoneId, activityId) → activity_venue_zone(id, activityId)

segment_seating_layout 方案画布 blob（一对一，理由同 venue_layout）
  planId (unique) / rendererKind / rendererVersion / data jsonb

segment_seat           方案位置（从 venue_seat 复制而来，之后独立演化）
  id / planId / externalId / sourceExternalId(nullable，文本快照不是外键——
                             底图位置是物理删除的，存外键会悬空)
  label / kind / rank / enabled / groupLabel / ordinal / removedAt
  unique (planId, externalId)
  unique (id, planId)                               ← 靶子
  partial unique (planId, label) where removedAt is null

seat_assignment        分配
  id / planId / segmentId / segmentSeatId / segmentMemberId
  assignedBy/At  revokedBy/At
  fk (segmentSeatId, planId)     → segment_seat(id, planId)
  fk (planId, segmentId)         → segment_seating_plan(id, segmentId)
  fk (segmentMemberId, segmentId) → segment_member(id, segmentId)
  partial unique (segmentSeatId) where revokedAt is null          ← 一座一人
  partial unique (planId, segmentMemberId) where revokedAt is null ← 一人一座

segment_seating_log    操作留痕（一张表够了）
  id / planId / action / payload jsonb / operatorId / createdAt
  action: saveLayout | assign | unassign | swap | resync | confirm | reject | void
```

### 三条复合外键各挡住什么

评审列的三种越界组合，靠上面的键在**数据库层面**就不成立，不依赖 handler 记得校验（做法照抄 `agenda/schema.ts:200` 的 `fk_segment_line_activity`）：

| 越界组合 | 挡它的键 |
| --- | --- |
| A 活动的环节 + B 活动的场地区域 | `plan(segmentId, activityId)` 和 `plan(activityVenueZoneId, activityId)` 同时锚在 `plan.activityId` 上 |
| P1 方案的分配 + P2 方案的座位 | `assignment(segmentSeatId, planId) → segment_seat(id, planId)` |
| A 活动的方案 + B 活动的人 | `assignment(planId, segmentId)` 和 `assignment(segmentMemberId, segmentId)` 同锚在 `assignment.segmentId`；再往上 `segment_member` 自己的 `fk_segment_member_segment` 把 segment 和 activity 焊死 |

第三条因此**不需要**在分配行上再冗余 `activityId` / `memberId`——活动一致性是传递保证的。这跟 `activity_member` 那句"不需要在这里再挂一条 `memberId → member.id`"是同一个判断。

### 需要改动已有模块

`segment_member` 目前只有 `unique(segmentId, activityMemberId)`，**没有** `(id, segmentId)`。挂 `assignment(segmentMemberId, segmentId)` 需要补一个靶子键：

```ts
unique("uk_segment_member_id_segment").on(table.id, table.segmentId)
```

这跟该模块已有的 `uk_activity_member_id_activity_member`、`uk_segment_id_activity` 是同一套做法（注释原话："给 segment_member 的复合外键当靶子"），不是新模式。

### 为什么位置要落成关系行，而不是留在 blob 里

旧系统把座位和 assignee 都塞在 `plan_json` 里，于是「这个人坐哪」只能整份反序列化后遍历（`FashionParticipantPortalServiceImpl.findSeatLabel()`）。新系统有四个必须按人或按位置反查的场景：

1. 人员从环节/活动移除 → 级联解绑
2. 确认后生成座位通知名单
3. 逐条校验分配指向的位置仍有效
4. 将来 H5 查本人座位

这四个都是 SQL 一行的事，只要位置是行。几何留在 blob 里，因为它天然整份读写、没人按它检索。

## 7. 状态机

```
未开启排位（派生：segment.seatingEnabled = false）
    │ 打开开关
未配置（派生：开关开了 + 没有 plan 行）
    │ 第一次 saveLayout
pending ──confirm──▶ confirmed
   ▲  │                  │
   │  └──reject──▶ rejected
   │                     │
   └─────任何写操作───────┘

pending / confirmed ──void──▶ voided
```

- **两个派生态不落库**（`未开启排位`、`未配置`）。落成状态行会立刻产生"开关关掉后这行算什么"的垃圾状态。
- **没有草稿**（BR-DEV-010）。第一次 `saveLayout` 直接建 `pending` 的 plan 行。
- **已确认方案被写 → 打回 pending，`version` 不变**（version 只在 confirm 时 +1，语义是"第几次确认发布"）。这一步要给前端返回警示：该方案已发过座位通知，改了要重发。
- **confirm 的校验是逐条的，不是比数量**：每条生效分配指向的 `segment_seat` 必须 `removedAt is null` 且 `enabled`。唯一索引已经保证了一座一人、一人一座。
- `activity_venue_zone.capacity` 超出时**只提示不阻断**——它是规划数字（§3.3）。
- confirm 成功时写一条 `action = confirm` 的 log，payload 装**完整快照**（位置 + 分配 + 当时的 label）。通知名单和历史编号都从这份快照读，不依赖当前分配行。

## 8. 人员来源

**分配指向 `segment_member.id`**，不是活动人员。这是 `member/schema.ts:355` 已经写死的决定，那段注释明确说它是对文档 §8.5 字面清单（"活动人员ID + 人员ID"）的刻意偏离：照文档建，就能把非本环节的人排进本环节座位，环节人员层在数据上完全旁路。

由此得到的行为（2026-08-25 起，候选人列表按当前环节收敛）：

| 场景 | 行为 |
| --- | --- |
| 从环节人员里选人排座 | 直接用现成的 `segmentMemberId` |
| 活动人员尚未关联当前环节 | 不出现在排位候选列表；先在环节人员管理中建立关系 |
| 环节人员开关是关的 | 仍只读取已有的当前环节人员关系；这个开关本期只是声明（`agenda/schema.ts` 原话："没有下游功能接上"） |
| 删除环节人员 | 数据库拦住（`assignment(segmentMemberId, segmentId)` 外键），必须先解绑 |
| 从活动移除人员 | member 侧发起级联，seating 提供"查引用 + 批量解绑"两个接口 |

这样可以保证排位候选列表和当前环节人员关系一致；旧版曾保留的
`assignActivityMember` 服务端入口仅为兼容旧客户端，当前 Web 管理端不再调用。

## 13. 编辑器落地方案

### 13.0 先说结论：旧编辑器没有用任何三方绘图库

`../ruoyi-antdp/package.json` 里 konva / fabric / tldraw / excalidraw / pixi / xyflow 一个都没有（`d3` 只被 dashboard 的地图用）。那是一套**从零手写的 SVG 编辑器**：自定义世界坐标系 1600×1000，手写 pan/zoom、命中测试、框选、套索、多边形、自由画笔。

**规模前提：单个环节 300–1000 个位置**（已确认）。

### 自研 SVG vs Konva：结论是自研

先把账算清楚。那 2144 行画布代码按函数边界拆：

| 归类 | 行数（粗算） | 自研 | 换 Konva |
| --- | --- | --- | --- |
| 纯几何/数学 | ~270 | 留 | 留（命中检测约 35 行作废，Konva 内置） |
| 状态 + 交互 handler | ~930 | **必须重写** | **必须重写** |
| SVG 渲染（含 12 种家具图形 332 行） | ~930 | 留 | **全废，要重画** |

中间那行是关键：**状态+交互两个方案都要重写**（undo 和拖拽性能已定要做，§13.3），这笔账两边一样。真正的差异是那约 930 行渲染代码：自研可以照着移植，换 Konva 要新写等价物，外加一个自定义 reconciler 依赖。

> ⚠️ **旧代码本身也是 AI 生成的 demo，从未被真实业务验证过。** 所以它不带任何"经过验证"的信用——移植它省的是**从零构思的时间**（有一个具体的目标形状可照着写），不是省下正确性风险。它必须按**全新代码**对待：该补的测试一条不能少，该审的边界一处不能跳。这条同时限定了下面每一格的判断。

四个维度，放在**代码由 AI 编写**这个前提下评估：

| 维度 | 判断 |
| --- | --- |
| 稳定性 | **Konva 略胜**。它的变换、命中、拖拽是经过验证的；我们这边全是未验证的 AI 代码。但要看清风险分布：低风险的是声明式渲染那 930 行（画错了肉眼立刻可见），真风险在几何 270 行和交互 930 行——而交互层两边都要重写，Konva 恰好能覆盖其中的 transform / hit / drag。抵扣项：`react-konva` 是自定义 React reconciler，与 React 版本强耦合（我们是 19.2），React 大版本升级时它是阻塞项 |
| 开发难度 | **Konva 略胜，但 AI 范式下这一维权重最低**。它省的 Transformer / 内置拖拽 / 命中检测约 100–150 行，人力范式下值钱，AI 范式下不构成理由；undo、吸附、套索两边都得自己写 |
| 迭代效率 | **偏自研，但没有我最初说的那么决定性**。SVG 是 DOM，仓库现成的 vitest + @testing-library/react + happy-dom 能断言**渲染结果**——座位画在哪、什么样式、点击绑了什么；Canvas 在 DOM 里只有一个 `<canvas>`，这类断言完全无从下手（happy-dom / jsdom 都不提供真实 2D 上下文）。但**手势和拖拽的端到端正确性两边都测不了**：happy-dom 不做布局，`getBoundingClientRect()` 返回全零，而 `toWorld()` 依赖它。那部分只能在真浏览器里验。调试上 SVG 仍然占优：结构可读，Canvas 对任何工具都是位图 |
| 交付可靠性 | 打平偏自研。1000 座位约 5000 个 SVG 节点，静态渲染没问题，平移缩放是根 `<g>` 一个 transform 走 GPU 合成；真正的瓶颈是"每帧全量提交"这个实现缺陷，不是技术上限。Konva 在这个量级也不自动更快——它任何变化都重绘整层，不做分层和 `cache()` 反而可能更慢，优势要到万级图元才显现 |

另一条 AI 范式特有的考量：AI 对"纯 React + SVG + 几何数学"的掌握度高于对某个库特定版本 API 的掌握度。库有版本漂移和 API 变更，生成的调用容易是过时或不存在的 API，且这类错误多是运行时行为错、最难发现。自研代码 100% 在仓库里，每次都能读到完整实现。

### 什么时候重新评估 Konva

不写成永久结论。出现任一信号就重新算：

1. 单方案位置数稳定超过 2000
2. 需要在画布上叠底图照片再摆大量元素
3. §13.3 全做完，首次挂载仍超过 500ms

### 自研的真实风险与缓解

真实风险是**整份代码（移植来的 + 新写的）都没有被任何真实使用验证过**，而其中手势交互那部分自动化测试覆盖不到。防法分三层：

1. **几何纯函数必须补单测**——射线法命中、相对顶点缩放、画笔采样、框选/套索命中判定。这 270 行是未验证 AI 代码里风险最高的部分，同时也是最好测的（纯输入输出）
2. **渲染结果补 DOM 断言**——座位画在哪、什么样式、点击绑了什么
3. **手势必须真浏览器验**——happy-dom 不做布局，拖拽、缩放、框选、多边形闭合这些只能人工或用浏览器自动化过一遍。列一份边界清单去逐条试：拖出区域边界、缩放到极值、快速双击闭合多边形、拖拽中途松开、多指触控

移植时下面几处**看起来**是对的，值得保留，但理由是"这些做法本身正确"，不是"它们被验证过"：`setPointerCapture`（拖出画布不丢事件）、`HANDLE / scale`（缩放时手柄视觉大小恒定）、位置 `clamp` 到区域边界、多边形顶点存相对 bbox 坐标。逐条确认它们确实按预期工作，不要因为"旧代码这么写"就跳过。

### 13.0.1 不是"自研 vs 换库"的二选一

上面那张表把问题框成了非此即彼，这个框法本身是错的。正确做法是**按能力拆开逐块判断**：手势（跨设备差异繁琐、与领域无关）用 `@use-gesture/react`，撤销用 `immer` 的 patches，blob 校验用已有的 `zod`；几何原语、布局生成、选择模型自研加单测。净新增两个小依赖，不引接管一切的 SDK。

编辑器内部的模块拆分、Command 模型、工具策略化、测试策略、移植清单，都在 **[场地排位编辑器设计.md](场地排位编辑器设计.md)**。下面 §13.1–13.5 只保留结论。

### 13.1 从旧代码取什么（均不 import antd）

### 13.2 重写（全是 antd 6，我们是 shadcn + Tailwind）

`Toolbar` / `PropertyPanel` / `ParamPanel` / `LayoutPicker` / `SeatAssignDrawer` / `FurniturePalette`。

其中 `SeatAssignDrawer` 不只是换 UI：它现在直接改 `SeatItem.assigneeId`，按 §3.2 要改成调 `assign` 接口，不再经过画布保存。

### 13.3 状态层重写：undo 和性能是同一个改动

现状：拖拽的 `onPointerMove` 里直接 `onItemsChange(seats.map(...))`，造新数组提到父组件 setState；座位组件**没有 `React.memo`**，每个座位 4–8 个 SVG 节点。600 个座位就是每帧 diff 三四千个节点。

改成：

1. 画布内部持有一个**可快照的 store**，拖拽期间只改被拖元素的 transform，不触发全量 React 更新
2. `pointerup` 时提交一次——**这一次提交既是"交给父组件"，也是"压一个 undo 快照"**
3. 座位组件加 `React.memo`，按 item / selected / groupColor 比较

**一次拖拽 = 一次 commit = 一个 undo 步。** 撤销栈深度 50，`Ctrl+Z` / `Ctrl+Shift+Z`。

**undo 的边界只到画布内**（位置的增删改、布局重新生成），**不包括人员分配**。分配是另一条写路径，走服务端、有 `segment_seating_log`，撤销它是"再调一次 unassign"，不是画布的事。这条边界是 §3.2 那条不变量在前端的直接体现——如果 undo 能跨过去撤销分配，说明两条写路径又粘上了。

### 13.4 第一版不做的编辑器改造

| 项 | 为什么先不做 |
| --- | --- |
| 吸附对齐、参考线 | 旧系统只有多边形闭合吸附，网格是 `<pattern>` 背景装饰、不参与吸附。自由摆放时会不好用，但大部分位置由布局预设生成，先看真实使用反馈 |
| 变换改用 `viewBox` / `getScreenCTM()` | 现在手算 `(clientX - rect.left - pan.x) / scale`，只支持平移+等比缩放。够用；要加旋转视图时再改 |
| 工具策略化拆分 | 七八种工具挤在同一组 pointer handler 里按 `effectiveTool` 分支。加新工具时才痛，现在不加 |

这三项都不影响 §4 的编辑器契约，任何时候改都不动底层。

## 14. 明确不做的，和已知残留风险

**不做并发控制。** 不加 `lockVersion`，不做写事务 CAS 协议，不做协同编辑。

残留风险照实记下来：`saveLayout` 查到某位置无分配、到软删它之间，另一个事务给这个位置插了分配，两边都提交后会留下一条指向已软删位置的分配行。窗口在同一次请求的事务内、以毫秒计，触发条件是两个人同时编同一个环节的排位。内部运营工具、几个操作员，为它建一套写事务协议不划算。真出现了，`confirm` 的逐条校验（§7）会把它拦在发布之前，不会流到通知里。

**不做 blob 版本迁移。** 编辑器契约里只有 `safeParse`，没有 `supports(version)`、没有迁移链。换编辑器时老 blob 不迁移，靠 `rendererKind` 共存 + 降级视图（§4、§9）。

**不做活动层座位编辑。** 见 §3.3。

**不做现场签到、临时换座、导出打印。** 见业务梳理 §8。

**不换三方绘图库，不做吸附对齐 / viewBox 重构 / 工具策略化。** 见 §13.0、§13.4。

## 17. 第 2–5 步：`activityVenue` + `seating` 落地

### 17.1 拷贝而不是关联，是用户明确要求的

§2.2"快照，不是外键"原本只针对"活动场地空间引用场地库"这一层要不要活引用，
没有明确到"引用"这个动作在 UI 上算不算创建了一条持久关联。用户在这一步开工前
把它钉死了：**选择现有场地时只做一份拷贝，不是关联**——`activity_venue` 的
`sourceVenueId` 只是可空的出处标记（`set null`，场地库删掉源场地不影响这份拷贝），
不参与任何读取路径，页面上显示的每一个字都来自这一层自己的行和自己的 blob。

拷贝的范围是**主记录 + 画布 blob + 全部区域**，在 `activityVenue/import` 一个事务里
做完（`routes.activity.ts`）。区域的 `capacity` 用源区域**当前的座位数**当初值——
这是个规划数字，不是权威集合（§3.3），给初值只是不让"可用点位"一栏开局全是 0。

### 17.2 `ZonePurpose` 是活动层唯一真正新增的语义

场地库的 `ZoneKind`（座席区/功能区/签到区/物料区）说的是"这块地方是什么"，是
场地的固有属性；活动区域新增的 `purpose`（主线环节排位/分论坛洽谈/签到物料/
备用区域）说的是"这场活动拿它干什么"，同一个主会场 A 区这场当主席台、下场当
媒体区。两者不能合并、不能互相推导，导入时按 `kind` 给一个 `purpose` 默认值
（`DEFAULT_PURPOSE_BY_KIND`），之后完全独立。

`ActivityZoneDialog` 因此把 `kind` 和"来源场地区域"都做成只读——能改的只有
名称、用途、可用点位、状态、说明，几何完全不在这层碰（§3.3 不做活动层座位编辑）。

活动空间里后来新画的区域并没有场地库区域出处，`sourceZoneId` 留空；这列故意不设
外键，源区域被删也不会反向改写快照，所以空值的准确含义是“本活动新建”，不能显示
成“来源已删除”。弹窗里的字段因此用兼容两种情况的“区域来源”：导入区域显示原
场地/区域，活动内新增区域追加“本活动新建”。

### 17.3 `venue` 不认识 `seating`，靠前端拼两次请求

`activityVenue/list` 的返回里没有"这块区域被几个环节排位引用"这个数——它要
数 `segment_seating_plan`，而 venue 模块不能 import seating（§2 的单向依赖）。
这个数改由 `seating/zoneUsage` 提供，场地空间页对同一个活动多发一次请求、
前端拼起来显示。宁可多一次往返，也不能为了省一次请求把依赖方向弄反。

同理，"排位" 按钮（从场地空间页跳到某个区域的排位）、区域列表的"引用环节"列，
读的都是这份 `zoneUsage`，不是 venue 模块自己算的。

### 17.4 排位方案的座位怎么从活动区域"切"出来

`segment_seat` 是核心表的关系行，但活动区域的座位躺在 `activity_venue_layout.data`
那份不透明 blob 里——**只有前端的编辑器认识它的格式**，服务端不解析。所以
"建方案时把某块区域的座位复制过来"这件事必须发生在前端：`buildPlanDoc`
（`features/venue-editor/plan-doc.ts`）从活动场地的画布里挑出一块区域，把它的
`shape.x/y` 归零（区域自己的尺寸就是方案的世界，跟 `zone-seating-editor.tsx` 那套
"局部坐标"是同一个技巧），连同它下面的座位一起打包成一份新的 `CanvasDoc`，
投影出服务端要的座位清单。`createPlan` 接口因此和 `venue/saveLayout` 收到的是
同一种东西——一批已经投影好的位置，服务端只管落库，不管它是从哪来的。

### 17.5 两条写路径在同一个页面上，靠"要不要等保存"分开

排位画布页（`$planId.tsx`）把 §3.2 那条不变量做成了用户能感知的两种交互：

- **画布改动**（拖座位、导入模板、启用/停用）攒在本地 `EditorState`，点"保存
  画布"才提交，走 `saveLayout`
- **排人**（右侧 `SeatAssignPanel`）点了立即生效，走 `assign`/`unassign`/`swap`，
  不经过保存按钮

"启用/停用"单独说一句：它是**方案层**的语义，`CanvasSeat` 上没有这个字段（§1
的分界线），所以没有走 Command、不进 undo 栈，而是页面自己维护一个
`enabledOverrides` 覆盖表，跟画布的 `dirty` 一起决定保存按钮亮不亮，保存时
和几何一起提交——这样它也享受 `saveLayout` 那套"位置上有人就整次拒绝"的保护
（真的验证过：把一个已排人的座位标记停用再保存，服务端正确挡下并报出人名）。

`assign` 系列走的每一次写操作都会把方案打回 `pending`（若之前是 `confirmed`，
前端弹一条"需要重新确认"的提示），`version` 不跟着动——跟 `saveLayout` 是完全
一样的状态机反应，验证了 §3.4"状态机只认发生了写操作，不认写的是什么"在
两条路径上确实对称。

### 17.6 座位视觉状态是叠加的，不是编辑器认识的

排位画布里一个座位除了"选中"，还要能看出"有没有人坐""本环节停没停用"——
这两个状态来自核心表，编辑器的 `CanvasSeat` 里没有它们。`SeatNode` 因此新增
两个可选 prop（`occupantName`、`planDisabled`），由页面按 `externalId` 从查询结果
拼一张表传进去；场地库画布（不存在"人"）和方案画布（有人）用的是同一个组件，
只是后者多传两个 prop。有人的座位实心主色、VIP 空位警示色、普通空位卡片色，
停用再叠一道斜杠——不靠单一维度（比如只调透明度）表达状态，色觉障碍或
小尺寸下都分得出来。

### 17.7 与用户确认过的两个范围裁剪

开工前用 `AskUserQuestion` 确认了两条，避免过度设计：

- **排位方案里的座位可以继续编辑**（不是活动区域座位的只读镜像），所以
  `segment_seating_layout` 这张几何表要建，是真实需求不是预留
- **团体相邻分组本期不做**（旧系统的 `SeatGroup`：给几个人打同一个组名、
  画布同色显示）——`segment_seat` 因此没有 `groupLabel` 列，跟设计草案里
  §6 数据模型的 `segment_seat` 描述有意不同，理由是这个功能本身只是人工
  着色、没有任何自动约束，真需要时再加一列不贵。

  > ⚠️ 第一条在 §17.8 被**收窄了一层，但没有推翻**：`segment_seating_layout`
  > 这张表、`seating/saveLayout` 这条接口都还在，数据模型层面"排位方案自己
  > 一份独立可编辑的几何"这个判断没有变。变的是**这次不再从排位画布这一层
  > UI 把编辑功能露出来**——见 §17.8。

### 17.8 排位阶段收回几何编辑权，只留入座

第一轮把 `activityVenue` + `seating` 落地时，排位画布（`ZoneSeatingEditor`）是
**全功能**的——工具栏有点放位置、撤销/重做、导入模板，跟活动空间那份编辑器
一模一样，唯一的区别是多了一个"启用/停用"开关。用户看着这个画布纠正了方向：

> 排位时，不应该再可以编辑场地和座位的布局了，应该只可以入座。场地空间这边
> 应该可以复用编辑器的功能进行编辑修改。

两句话对应两处调整：

**排位画布收成"只能选、不能改"。** `ZoneSeatingEditor` 新增一个 `assignOnly`
prop：传了之后工具栏只剩"选择"和"适配"，`点放位置`/`撤销`/`重做`/`导入模板`
整组不渲染；`onDragStart` 里如果算出来的拖拽意图是 `moveSeats`，直接降级成
`{kind:"none"}`——纯点击（tap）判定照常走，选中和换选完全不受影响，只是
"拖一下挪动座位"这个动作被吃掉。键盘快捷键（Ctrl+Z、Delete）同理，在
`assignOnly` 时整段跳过，不是只在按钮层面隐藏。

排位画布因此**不再需要"保存"这个动作**——geometry 是只读的，唯一还需要提交
的两件事（排人、启用/停用）本来就该是即时操作，不该攒着等一个几何保存按钮。
"启用/停用"原来跟画布保存捆在一起走 `saveLayout`，现在拆成独立的
`seating/setSeatEnabled` 接口，跟 `assign`/`unassign` 是同一类：点了就提交，
校验规则不变（有人坐的位置不让停用，理由同 §5）。`seating/saveLayout` 这条
接口本身没有删——排位画布现在不调它了，但它是不是彻底没用了、要不要连服务端
一起收掉，留给以后：现在没有已知的第二个调用方，删不删都不影响正确性，
先按"没人用但没坏处"处理。

**活动空间接手全功能编辑。** 新增一个专门的编辑页
（`/project/$projectId/activity/$activityId/venue/$activityVenueId`），
**原样复用**场地库那一整套画布组件（`CanvasEditor`、`ZoneSeatingEditor`、
`ZonePropertyPanel`、`SeatPropertyPanel`）——真正意义上的"复用编辑器的功能"，
不是照着抄一份改改。两处跟场地库编辑器的差异都是活动层自己的性质决定的：

- 保存不带座位——活动层不落座位行（§3.3），`saveLayout` 的载荷里只有区域
  投影，没有 `seats` 字段，服务端对应的合并逻辑（`applyActivityLayout`）
  也只处理区域一种关系行
- 区域属性面板多一截"活动用途 / 可用点位"入口，点开的是已有的
  `ActivityZoneDialog`——这两个字段从来不在 blob 里，编辑器根本不认识，
  硬塞进编辑器的属性表单不如留一个插槽从外面接。为此 `ZonePropertyPanel`
  加了一个 `extra` 渲染插槽和 `enterLabel` 文案覆盖（"进入排位"在这里
  改成"布置座位"，跟真正的环节排位分开叫，别让人以为这里也是排人的地方）

区域和活动区域业务字段（`purpose`/`capacity`/`status`/`note`）是两条独立的写
路径，互不干扰——`saveLayout` 的归并只碰 `name`/`kind`/`ordinal`，新增区域时
才按 `kind` 给业务字段一份默认值；已验证：改一次名字保存，另外两个区域的业务
字段原样不动。

**一个真实踩到的路由坑**：活动空间概览页原来是一个扁平的 `venue.tsx` 文件，
新加的编辑页 `venue.$activityVenueId.tsx` 作为兄弟路由挂在同一层。TanStack
Router 在这个仓库的文件路由约定下，扁平的父文件 + 子路由文件并存时**不会**
按嵌套匹配——访问 `/venue/4` 会仍然命中父路由 `venue.tsx`，子路由形同虚设。
排位模块早先就踩过同一个坑（当时把 `seating.tsx` 挪成了 `seating/index.tsx`
才修好），这次照抄同一个修法：把 `venue.tsx` 挪成 `venue/index.tsx`，父子关系
才生效。**这个仓库里"父文件 + 子路由"必须用目录 + `index.tsx` 的写法，不能用
扁平文件**，以后再加子路由时应该一开始就按这个约定建。
