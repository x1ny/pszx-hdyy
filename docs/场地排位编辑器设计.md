# 场地与排位：编辑器设计

> 底层数据设计见 [场地排位底层设计.md](场地排位底层设计.md)，本文只谈编辑器**内部**怎么拆。编辑器对外只暴露 §4 那个 `LayoutEditor` 契约，本文的一切都在契约背后，可以整体替换。
>
> 前提校正：旧系统（`../ruoyi-antdp/src/pages/venue`）是 **AI 生成的 demo，未经真实业务验证**。它的**视觉产出已经过人工确认可用**，所以图形部分是资产；但它的结构、边界处理、正确性都不带任何信用，必须按全新代码对待。

---

## 1. 出发点

"完全自研"和"换 Konva 接管一切"都是错的框法。正确的做法是**按能力拆开，逐块判断该自研还是该用库**，判据统一为一条：

> **这块能力是不是"跨设备/跨浏览器差异繁琐、与我们的领域无关、且有成熟实现"？是就用库，否则自研 + 单测。**

因为代码由 AI 编写，这条判据还要加一个副条件：**自研的部分必须能被自动化测试彻底覆盖**。测不到又没人验证过的手写代码，是这个项目最大的质量风险源。

---

## 2. 能力清单与逐块判断

| 能力 | 判断 | 理由 |
| --- | --- | --- |
| 手势：pan / zoom / drag | **用库** `@use-gesture/react` | 鼠标滚轮、触控板双指、`ctrl+wheel` 缩放、触屏捏合、pointer capture、阻止浏览器默认缩放——全是跨设备差异，与我们的领域零关系，且手写代码正是在"某人的触控板上不对"这种地方翻车。库来自 pmndrs，核心与框架无关，只输出手势数据、不碰渲染 |
| 撤销 / 重做 | **用库** `immer` 的 `produceWithPatches` | 直接产出 forward + inverse patches，undo 栈是白拿的，比自己存全量快照精确也省内存。附带好处：命令写成 `draft => { draft.seats[i].x += dx }`，AI 写这种代码比写不可变展开更不容易出错 |
| blob 解析（契约里的 `safeParse`） | ~~用库 `zod`~~ → **自研守卫** | 原本打算用仓库已有的 zod，落地时发现**在 `bun --bun vitest` 下 zod 整体不可用**，而这个模块必须能被单测覆盖。详见 §8 末尾那条环境约束 |
| 几何原语 | **自研 + 单测** | 只需要五六个函数（点在多边形内、包围盒、线段距离、矩形相交、相对/绝对顶点换算），每个 10 行上下，且是纯输入输出、单测能 100% 覆盖。`@turf` 是地理库带坐标系概念不合适，`flatten-js` 功能远超需要。引库反而多一层抽象 |
| 布局生成（9 种预设） | **自研 + 单测** | 领域特定，"圆桌宴会座位环绕""秀场双边留 T 台"没有任何库会做。参考旧代码的 `layoutEngine.ts`，纯函数 |
| 家具目录与图形 | **移植** | 视觉已确认可用，且我们继续用 SVG，图形可以 1:1 搬过来，不存在走样风险 |
| SVG 渲染 | **自研** | React 直接渲染 SVG，不需要中间层 |
| 选择模型（单选/多选/框选/套索） | **自研** | 命中判定就是几何，可单测 |
| 工具切换（矩形/多边形/画笔/座位…） | **自研** | 领域特定的编辑语义 |
| 吸附对齐 | **暂不做** | 见底层设计 §13.4 |

**净新增依赖两个：`@use-gesture/react`、`immer`。** 都是小而精、职责单一、与渲染解耦的工具库，不是接管一切的 SDK。`zod` 复用已有。

> 不引 `zustand`：编辑器文档状态是**局部的**（活在一个画布组件的生命周期里），`useReducer` + immer 就够。仓库至今没有全局状态库，这是刻意保持的简单，不为一个组件破例。
>
> 不引 `Konva`：判断和依据在底层设计 §13.0，那里也写了什么信号出现该重新评估。

## 3. 模块拆分

核心原则：**`core/` 不认识 React，也不认识 DOM。**

这条不是洁癖，是直接对着"未验证的 AI 代码"这个风险来的——不碰 DOM 的代码能被 vitest 完整覆盖，所以把尽可能多的逻辑压进 `core/`；碰 DOM 的部分压到最薄，且其中最难的手势交给库。

```
apps/web/src/features/venue-editor/
  core/                     零 React / 零 DOM，目标 100% 单测覆盖
    geometry.ts             点、矩形、多边形原语
    catalog.ts              家具目录：尺寸、是否可入座、计数权重
    layout/
      theater.ts  banquet.ts  runway.ts  ushape.ts  ...
      index.ts              generateLayout(preset, params, area) → Seat[]
    document.ts             EditorDoc 模型
    commands.ts             所有文档变更（immer）
    history.ts              patch 栈
    project.ts              契约的 project()：EditorDoc → Zone/SeatDraft
    serialize.ts            契约的 safeParse()：unknown → EditorDoc（zod）

  react/                    薄层：把 core 接到屏幕上
    use-editor.ts           useReducer(commands) + history + 选择态
    use-viewport.ts         @use-gesture 驱动的 pan / zoom
    tools/
      types.ts              EditorTool 接口
      select.ts  rect.ts  polygon.ts  pen.ts  seat.ts
    render/
      Canvas.tsx            SVG 根 + viewport transform
      ZoneShape.tsx  SeatShape.tsx  FurnitureGlyph.tsx   （memo）
      Overlay.tsx           选择框、手柄、绘制草稿预览
    panels/                 shadcn 重写的工具栏 / 属性面板 / 参数面板

  adapter.ts                导出符合 LayoutEditor 契约的对象
  fallback/                 降级视图（底层设计 §9），不依赖 core 以外任何东西
```

对照旧代码：它把这一整棵树塞进了两个文件（`VenueCanvas.tsx` 979 行 + `SeatCanvas.tsx` 1165 行），七八种工具挤在同一组 pointer handler 里按 `effectiveTool` 分支。这是"能跑的 demo"和"能改十年的模块"之间的差别。

## 4. 三个关键设计

### 4.1 一切变更走 Command

```ts
type EditorDoc = { zones: Zone[]; seats: Seat[] };
type Command = { label: string; apply: (draft: Draft<EditorDoc>) => void };

// 执行
const [next, patches, inverse] = produceWithPatches(doc, cmd.apply);
```

交互不直接 `setState`，而是**产出一个 Command**。这一条同时解决四件事：

1. **undo 白拿**——`inverse` 压栈即可
2. **命令可单测**——"把选中的 3 个座位右移 10px"是一个纯输入输出，能断言
3. **commit 边界显式**——一次手势 = 一个 Command = 一个 undo 步
4. **操作留痕有出处**——`label` 直接可以喂给底层设计的 `segment_seating_log`

### 4.2 工具是策略对象，且在类型上禁止拖拽中途改文档

```ts
interface EditorTool {
  id: ToolId;
  cursor: string;

  onTap?(ctx: ToolContext, p: Point): Command | null;
  onDragStart?(ctx: ToolContext, p: Point): void;
  onDrag?(ctx: ToolContext, p: Point): void;          // ← 没有返回值
  onDragEnd?(ctx: ToolContext, p: Point): Command | null;

  renderPreview?(state: ToolState): ReactNode;        // 拖拽中的视觉反馈走这里
}
```

注意 `onDrag` **没有返回值**，只有 `onDragEnd` 能产出 Command。这就把底层设计 §13.3 那两个需求（拖拽期间不提交、一次拖拽一个 undo 步）**焊进了类型系统**——工具想在拖拽中途改文档也没有那个接口。拖拽过程中的视觉反馈由 `renderPreview` 画临时图形，不进文档。

约束写进类型，而不是靠注释提醒下一个人（或下一次 AI 生成）记得遵守。这是这份拆分里最重要的一处。

加一种新工具 = 加一个文件 + 注册一行，不动任何已有代码。

### 4.3 渲染层 memo 到座位粒度

`SeatShape` 按 `(seat, selected, groupColor)` 做 `React.memo`。配合 4.2 的"拖拽不改文档"，拖动时只有 `renderPreview` 那几个临时图形在变，1000 个座位的 `<g>` 一个都不重渲染。

旧代码在这两处都是反面：每帧 `onItemsChange(全新数组)` 提到父组件，且座位组件没有 memo。

## 5. 测试策略

直接对着"代码没人验证过"这个风险排：

| 层 | 怎么验 | 覆盖目标 |
| --- | --- | --- |
| `core/geometry` | vitest 单测，重点是退化用例：点正好落在多边形顶点上、零宽矩形、三点共线、自相交多边形 | 100% |
| `core/layout` | 给定参数断言座位数、编号序列、全部落在区域内、不重叠 | 100% |
| `core/commands` | 输入 doc + command → 断言输出 doc；且 `inverse` 能精确还原 | 100% |
| `core/project` | 断言投影结果；**外加幂等性测试**：同一份 doc 两次 `project()` 的 `externalId` 必须一致（底层设计 §4 的硬要求） | 100% |
| `core/serialize` | zod schema 的正例 + 反例（缺字段、类型错、多余字段） | 100% |
| `react/render` | `@testing-library/react` 断言 DOM：座位画在哪、什么样式、点击调了什么 | 主路径 |
| `react/tools`、`use-viewport` | **真浏览器**。happy-dom 不做布局，`getBoundingClientRect()` 返回全零，而屏幕↔世界换算依赖它 | 见下清单 |

手势部分自动化测不到，列一份清单人工（或浏览器自动化）逐条过：

- 拖拽超出区域边界 → 位置被 clamp，不飞出去
- 拖拽中途松开 / 焦点被抢走 → 不留下卡住的拖拽态
- 缩放到极值（最小 / 最大）→ 不翻转、不除零
- 触控板双指平移 vs `ctrl+wheel` 缩放 → 两种手势不串
- 多边形：快速双击闭合、点回第一个点闭合、Esc 取消
- 框选与套索在缩放后仍然命中正确的座位
- 触屏单指拖拽、双指缩放

## 6. 移植清单

从旧代码取什么、怎么取：

| 旧文件 | 取法 |
| --- | --- |
| `config/types.ts` 的几何函数 | 移植进 `core/geometry.ts`，**逐个补单测再采用**，退化用例照 §5 列的写 |
| `config/types.ts` 的类型定义 | 参考形状，按新模型重写（`SeatStatus` 要拆成 `rank` + `enabled`，见底层设计 §10） |
| `config/seating/layoutEngine.ts` | 按预设拆成 9 个文件进 `core/layout/`，每个配单测 |
| `config/seating/furnitureCatalog.ts` | 目录数据移植进 `core/catalog.ts`；`separateOverlapping` 进 `core/geometry.ts` 并补测 |
| 12 种家具的 SVG 图形 | **1:1 移植**进 `react/render/FurnitureGlyph.tsx`。视觉已确认，继续用 SVG 所以不走样 |
| `VenueCanvas.tsx` / `SeatCanvas.tsx` 的渲染 JSX | 照着写进 `render/`，拆成 memo 化的小组件 |
| 两个画布的 pointer handler | **不移植**。按 §4.2 的工具策略重写，手势交给 `@use-gesture` |
| `PropertyPanel` / `ParamPanel` / `Toolbar` / `LayoutPicker` / `FurniturePalette` | UI 用 shadcn 重写，交互语义参考旧的 |
| `SeatAssignDrawer` | 重写，且改成调 `assign` 接口——不再改 `SeatItem.assigneeId`、不再经过画布保存（底层设计 §3.2） |
| `exportMap.ts` | 本期不做导出，先不移植。将来要做时它仍可用，因为我们还是 SVG |

下面这几处旧代码的做法**看起来是对的，值得保留**，但理由是"这些做法本身正确"，不是"它们被验证过"——移植时逐条确认确实按预期工作：

- 用 `setPointerCapture` 而不是往 document 挂全局 listener（`@use-gesture` 内部也是这么做的）
- 手柄尺寸 `HANDLE / scale`，缩放时视觉大小恒定
- 位置 `clamp` 到区域边界
- 多边形顶点存相对包围盒左上角的坐标，缩放时按比例重算

## 7. 实施顺序

编辑器在底层设计 §12 的第 5 步，内部再拆：

1. `core/geometry` + `core/layout` + `core/catalog` —— 纯函数，连同单测一起。**这一步产出的东西不依赖任何渲染决策**，即使将来换 Konva 也全部保留
2. `core/document` + `commands` + `history` + `project` + `serialize` —— 编辑器的"模型层"，同样纯函数可测
3. `fallback/` 降级视图 —— 不用画布也能改分配，验证契约完整（底层设计 §9）
4. `react/use-viewport`（`@use-gesture`）+ `render/` —— 先只读渲染，能看不能改
5. `react/tools/` 逐个加：select → rect → seat → polygon → pen
6. `panels/` shadcn 重写
7. 手势边界清单人工过一遍（§5）

第 1、2 步做完就能跑单测，此时还没有一行 UI 代码——这是把"未验证风险"压在最前面的排法。第 3 步做完业务已经可用。

## 8. 已落地：`structural-v1`

第一个编辑器实现不是 SVG 画布，是一个**表单式编辑器**。它不在原计划里，是第 1 步落地时
被一个具体问题逼出来的：画布排在第 5 步，那在此之前场地的区域和位置怎么录入？

如果按原设计把降级视图做成只读列表，第 1 步交付的模块就是空的。反过来，如果让降级视图能写，
又会破坏"blob 是唯一真值、区域和位置是它的投影"这条不变量——除非**降级视图本身就是一个
合法的编辑器**。于是就这么做了。

| | 内容 |
| --- | --- |
| `kind` | `structural-v1` |
| 文档模型 | `{ schemaVersion: 1, zones: [...], seats: [...] }`，没有任何几何信息 |
| `project()` | **恒等映射**——文档本身即投影，没有呈现信息要剥离 |
| `safeParse()` | 手写类型守卫，见下面那条约束 |
| UI | 左侧区域列表，右侧该区域的位置表格，支持按前缀 + 起始序号 + 数量批量生成 |
| 代码 | `apps/web/src/features/venue-editor/{contract.ts, structural/}` |

它同时是**降级视图**：blob 为空、是别的渲染器写的、或者解析失败时，页面从服务端返回的
区域和位置反推出文档（`docFromProjection`），照样能看能改。§9 那条"降级视图能用"的验收
标准因此不是将来某天要补的东西，它现在就在跑。

**接 SVG 画布时的衔接规则**：`rendererKind` 一经写入不再更换，唯一的例外是
`structural-v1` → 画布。结构里没有任何几何信息，画布可以用布局引擎从零布局它，属于
"从没有几何升级到有几何"，不是两套几何格式互转。反向不允许。

### 一条环境约束：这个模块里不能用 zod

web 的测试脚本是 `bun --bun vitest run`（在 Bun 运行时下跑 vitest），在这个组合下
`import { z } from "zod"` 拿到的是 `undefined`——一个只断言 `typeof z.enum` 的最小探针
也会失败。此前没人踩到，是因为现有 web 测试没有一个 import 过 zod（路由文件里的 zod
都不在测试覆盖范围内）。

`structural/model.ts` 按 §5 属于"必须 100% 单测覆盖"的第一档，所以那里的 blob 校验
改成了手写类型守卫——**可测性压过用库**。这不影响别处：表单校验（`venue-form-dialog.tsx`）
和路由 search schema 照常用 zod，它们不在测试覆盖里。

这是个仓库级的问题，值得单独解决（要么给 web 的 test 脚本去掉 `--bun`，要么查清 zod 在
Bun 运行时下的解析为什么失败）。在那之前，**任何要写单测的 web 模块都不能 import zod**。

## 9. 已落地：`svg-canvas-v1`

第二个编辑器实现，就是 §1–§7 规划的那套 SVG 画布。和 `structural-v1` 并存，
页面按场地的 `rendererKind` 决定用哪个打开。

### 做了什么

| 层 | 内容 | 代码 |
| --- | --- | --- |
| 几何原语 | 矩形规范化、命中、包围盒、缩放搬运、屏幕↔世界换算、视口适配 | `canvas/core/geometry.ts` |
| 布局生成 | 剧场直排 / 圆桌宴会 / 秀场双边 / 自由摆放，三种编号规则 | `canvas/core/layout.ts` |
| 文档模型 | `CanvasDoc` + 投影 + blob 解析 + 从核心表反推 | `canvas/core/document.ts` |
| 命令 | 区域增删改缩放、布局套用、座位增删改拖动 | `canvas/core/commands.ts` |
| 撤销栈 | immer patches，深度 50 | `canvas/core/history.ts` |
| 交互判定 | 按下时开始哪种拖拽、框选、手柄命中 | `canvas/core/interaction.ts` |
| 视口 | `@use-gesture` 驱动的平移缩放 | `canvas/react/use-viewport.ts` |
| 渲染 | SVG，座位 `memo` 到单个粒度 | `canvas/react/canvas-view.tsx` |
| 交互壳 | 手势 → Command，工具栏、快捷键 | `canvas/react/canvas-editor.tsx` |
| 属性面板 | 区域属性 + 布局参数 + 座位属性 | `canvas/react/property-panel.tsx` |

core 层 78 条单测全覆盖，写完 core 时还没有一行 UI 代码——就是 §7 定的顺序。

### 相对规划的收窄

- **只有矩形区域。** 多边形/画笔在模型里留了位置（`shape` 是可辨识联合），
  但交互没做。场馆平面图里矩形覆盖绝大多数情况。
- **只有四种布局预设。** 旧系统另有课堂纵列、U 型围合、董事会长桌、酒会散座、
  弧形看台，形状都在那份代码里，补的时候照抄参数即可。
- **没有家具陈设。** 桌台、舞台、绿植这些不进核心表（§1 的判据：没有任何东西
  引用一张桌子），所以它们纯粹是 blob 里的装饰。第一版先不做，模型不受影响。
- **没有吸附对齐。** 同 §13.4 的判断。

### 落地时踩到的三个坑

都跟 `@use-gesture` 有关，值得记下来：

1. **`target: ref` 配置下监听器根本没挂上**，控制台一声不吭——滚轮和拖拽全无反应。
   改成把 `bind()` 展开到元素上就正常了。
2. **`movement` 在某些事件路径下恒为 0**（合成事件必现）。而草稿框用的是自己算的
   当前点、照画不误，于是表现成"框能拉出来、松手却什么都没发生"，极难定位。
   现在位移完全由"按下点 → 当前点"自己算，不碰库给的 `movement`。
3. **`filterTaps: true` 让纯点击不触发 drag**，`onDragStart` 不跑、拖拽状态是空的，
   于是"点一下选中"整个失效。tap 判定自己按位移阈值做，这个选项要关掉。

第 2、3 条都是**真 bug**（不只是测试环境的问题），而且都属于"渲染看着正常、
行为却不对"那一类——正是 §5 里"手势必须真浏览器逐条过"想拦的东西。

## 10. v2 重做：两级架构（顶层区域分布 + 进入区域后排位）

第一版把画区域和摆座位揉在同一张画布、同一套工具里。参考旧系统的真实截图后
发现这不对——旧系统是**两级**的：

1. **场地规划**（顶层）：只管区域怎么分布。矩形/圆形/椭圆/多边形/自由画笔
   任选形状，每块区域自己的颜色，不在这一层摆任何座位。
2. **排座**（进入某个区域之后）：左边是排位模板卡片（剧场直排/课堂纵列/
   圆桌宴会/U 型围合/董事会长桌/秀场双边…），右边是这块区域自己的座位画布。

这不是锦上添花的美化，是**编辑范围的重新划分**：顶层的可选对象是区域，
排位层的可选对象是座位，两层从来不会同时选中一区域一座位。原来的单层设计
把两种选择状态、两套工具、两套快捷键全挤在一个组件里，"双击区域进入排位"
这种操作在原设计里根本没有容身之处。

### 10.1 数据模型的变化

- `ZoneShape` 从只有 `rect` 扩成 `rect | ellipse | polygon` 的可辨识联合。
  三者共享同一组包围盒字段（x/y/width/height），这不是巧合——TypeScript
  允许在联合类型上直接访问所有分支都有的字段，所以"读 `zone.shape.width`"
  这类代码不用因为加了新形状而改一遍，只有真要读 `points` 的地方才需要
  判别 `type === "polygon"`。
- `CanvasZone` 加 `fill`/`stroke` 两个十六进制颜色字段。**新建时**按 `kind`
  取一个默认值（`ZONE_KIND_DEFAULT_COLOR`，取自 `styles.css` 的
  `--chart-1..4`），之后跟 kind 脱钩，用户可以在属性面板用原生
  `<input type="color">` 单独改——原生颜色输入天然产出 `#rrggbb` 格式，
  跟存储格式、跟 blob 序列化的往返格式是同一套，不用额外转换。
- `projectCanvas()` 依旧不带出任何坐标或颜色——这条不变量没变。

### 10.2 交互层拆成两套，不共用一个状态机

`resolveDragSubject`（顶层）和 `resolveSeatDragSubject`（排位层）是两个
独立的纯函数，不是一个函数里塞两套分支。顶层没有"座位"这个可选对象，
排位层没有"区域"这个可选对象，硬合并只会多出一堆恒假分支——跟 §4.2
"工具是策略对象"是同一个判断，只是这次拆分的粒度是"整个交互状态机"，
不只是"一种工具"。

排位层能这么薄，关键在坐标系的选择：座位的 x/y 本来就存**相对区域左上角**
的坐标（这条从 v1 就有），所以进入某个区域之后，"这块区域的大小"可以直接
当成画布的世界尺寸，座位坐标原样使用——不需要再处理"区域在世界里的位置"
这层换算。`zone-seating-editor.tsx` 里那个"零点区域"文档（`localDoc`，把
`zone.shape.x/y` 都置零）就是靠这条性质，让顶层写的 `hitSeat`/`marqueeSelect`
两个通用函数原样在排位层复用，不用重写一遍命中判定。

### 10.3 落地时抓到的两个真 bug

都是"渲染看着正常、行为不对"那一类——跟 v1 的 `@use-gesture` 三个坑
（§9）性质相同，都不是自动化测试能覆盖到的层面。

**1. `onDragStart` 对多边形工具提前 return，导致点击整个失效。**

最初的想法是"多边形是点击累加顶点，不需要进拖拽状态机"，于是在
`onDragStart` 里对 `tool === "polygon"` 直接 `return`，不建立 `dragRef`。
后果是 `onDragEnd` 里 `if (!dragRef.current) return` 会把每一次点击都吞掉，
`handleTap` 根本没机会跑——浏览器里点 5 下画布，一个顶点都不出现。

实际上完全不需要特殊处理：`resolveDragSubject` 对 `tool === "polygon"`
本来就返回 `{ kind: "none" }`，走正常流程建一个"什么都不做"的拖拽状态，
`onDragEnd` 照样能用同一套 tap 阈值判定识别出这是一次点击。**特殊情况
往往应该让通用逻辑自然覆盖，而不是加一个提前退出**。

**2. 快速连续点击时，React 18 自动批处理让中间的顶点全部丢失。**

多边形草稿最初存在 `useState` 里，`handleTap` 里读 `live.current.polygonPoints`
（一个"每次渲染刷新一遍"的 ref 快照）来算下一个点该插到哪。这在正常手速下
测不出问题，但快速点 5 下（脚本里在同一个事件循环内连发 5 组
`pointerdown`/`pointerup`，用户手速快、或者双击闭合时的最后几击也会撞上）
会被 React 18 自动批处理合并到同一轮更新——这一轮里每次 `handleTap` 读到的
`live.current.polygonPoints` 都是**同一份旧值**，`setPolygonPoints([...旧值, 新点])`
连调 5 次，最后只有最后一次生效，5 个顶点点下去只剩 2 个。

修法是把多边形草稿的真值挪进一个 `useRef`（`polygonPointsRef`），state 只是
渲染用的镜像——ref 的读写是同步的，不受 React 批处理影响。这正是旧系统
`polyPointsRef` 的做法（§6 移植清单里"看起来对但没被验证过"的一条，这次
真的验证过了：浏览器里用脚本模拟同一事件循环内的 5 连击，5 个顶点全部
正确出现）。

**教训**：任何"点击累加状态"（不只是多边形，将来要加自由画笔的话也一样）
都不能把真值放在 `useState` 里再靠一个每渲染刷新的 ref 快照去读——两次
写入之间如果没有一次真实的重渲染做间隔，后写的会吃掉先写的。真值要么
放纯 ref，要么用 `setState(prev => ...)` 的函数式更新形式。

### 10.4 相对 v1 的收窄

- **多边形只支持"点击加点 + 点回起点/Enter 闭合"**，不支持自由画笔
  （拖拽连续采样）。旧系统两者都有，画笔在模型里天生就是"很多个点"，
  跟多边形共用 `type: "polygon"` 这个 shape 完全够用，缺的只是"怎么产生
  这些点"的另一种交互，需要时加一个新工具、复用同一个 `polygonShapeFromPoints`
  即可。
- **一个色板输入同时控制 fill 和 stroke**，不是旧系统那种可以分开调的两个
  颜色。分开调的收益在这批场景里不明显，先按一个色板做。
- **排位模板卡片还是 4 种**（剧场/宴会/秀场/自由），没有跟着这次重做顺带
  扩到旧系统的 6 种——`LayoutPicker` 已经是数据驱动的卡片列表，加一种预设
  只需要在 `core/layout.ts` 补生成器、在 `layout-picker.tsx` 补一条
  `PRESET_META`，不用碰任何交互代码，留到真需要时再加。

### 10.5 区域属性面板：空态改成区域列表

`ZonePropertyPanel` 原本没选中区域时只有一句"选中一个区域"的提示，这块
288px 宽（`w-72`）的面板大半时间在场地已经有区域之后就是纯浪费——用户
其实更想一眼看到"这个场地目前有哪些区域、排了多少座位"。改成：

- **默认态**：`doc.zones` 的一张小表（颜色色块 + 名称 + 座位数/"—"），点一行
  选中该区域并切到编辑表单；行上还有一个 hover 才显示的"进入排位"图标
  按钮，不经过表单直接跳进该区域的排位画布。
- **选中态**：还是原来的编辑表单（名称/类型/颜色/进入排位/删除），顶上加了
  一条"返回区域列表"，不用清空选中再点空白画布才能回列表。
- **两态共用同一个 `PanelShell`**（`w-72 shrink-0`），切换时只换内容、外框
  尺寸不变——这是用户明确要求的："注意固定宽度"。

列表没有用 `shared/components/ui/table.tsx` 那套——那是列表页级别的密度
（单元格 `px-4 py-3`），套进 288px 宽、只有两列数据的侧栏会太挤，改成自己
写一份更紧凑的 `<table>`（无边框、行高更矮）。选中逻辑复用了已有的
`selection` 状态——`onSelectZone` 就是 `setSelection({zoneIds:[id],seatIds:[]})`，
跟画布上点一个区域走的是同一条路径，不需要额外的状态分支。

### 10.6 排位模板：从"区域的持久属性"改成"一次性操作"

用户提出的判断：所有排位底层都是自由排座，模板只是快速生成座位的一种手段，
不该是要保存的数据。这条判断被采纳，理由不是"模板功能不重要"，而是原来的
存法本身有个真实隐患——`CanvasZone.preset`/`params`（v2 刚落地时加的两个字段，
见 §10.1）存的是"上次生成用的参数"，纯粹给排位画布左侧常驻的 `LayoutPicker`
下次进这个区域时预选一个默认值。可是 `CanvasSeat` 从一开始就是纯自由坐标，
跟模板毫无耦合——用户一旦手动拖过几个座位，这两个字段就变成一句不再准确的
"记忆"：重新进这个区域，选择器还是显示"剧场直排/10 排 8 列"，像是提醒"这
区域仍然是这个模板"，其实早就不是了。存一份跟真实状态可能脱节、又没有任何
机制保证同步的元数据，这本身就是隐患，不是"锦上添花"。

改法：`CanvasZone` 去掉 `preset`/`params` 两个字段（`document.ts`），
`applyLayoutToZone`（`commands.ts`）不再把这两个值写回区域，只拿它们当纯粹的
生成器输入。排位画布左侧常驻的 `LayoutPicker` 整个撤掉，换成工具栏一个
「导入模板」按钮，点开是个 `Dialog`（`template-dialog.tsx`）：三张模板卡片
（剧场/宴会/秀场，**不再包含"自由排座"**——不点这个按钮、直接用「点放位置」
本来就是自由排座，没必要在对话框里假装选中它）+ 参数输入 + "生成 N 个位置"
确认按钮，点一下生成、对话框关闭，除了新增的座位，什么痕迹都不留。对话框
每次打开都重置回默认选择（`useEffect` 监听 `open`），不"记住上次选的模板"——
这是刻意的：模板选择器不是在恢复一份状态，是在发起一次新的操作。

顺带把 `applyLayoutToZone` 注释里一直没兑现的承诺（"用户手工调过的位置会丢，
调用方要二次确认"）在这次重做里补上了——已有座位时，对话框底部会提示
"当前已有 N 个位置，导入模板会整体替换，手动调整过的位置也会丢失"。这不是
这次改动额外加的范围，只是原来的意图第一次有了落地的地方。
