# h5 座位定位图

2026-09-08 逐项确认。行程行上的「座位图」按钮推上来的那张图。

个人座位图回答的是**我这个位置在这片区的哪个方位**；团体座位图回答的是**我所在
团体占用了这片区的哪些位置**。两者都不回答"邻座是谁"；"哪边是舞台"只靠运营
显式画的[场地标注](#场地标注)回答，不从座位推断。下面每一条都是从这句话推出来的。

## 业务区域可包含多个分区

历史单分区方案仍是一张图。新建的业务区域方案保存多个独立座席分区；H5 只返回嘉宾本人所在分区的灰点、定位钉及分区名称，绝不把其他分区拼进同一坐标系。个人有多个分区座位时，按座位选择切换对应分区；团体座位跨分区时提供分区切换。坐标仍不附带其他人的编号或身份信息。

## 只有一个区，不是产品选择而是数据事实

参考原型里是四个区并排 + 一颗"您在这里"。**我们的模型构不出那张图**：一个环节
最多一个有效方案（`uk_seating_plan_segment`），方案锚在单个 `activityVenueZoneId`
上，建方案时 `plan-doc.ts` 按 `zoneExternalId` 从上游画布切出一块，`doc.zones`
只留那一个。所以"只显示这个人所在区"不需要任何过滤逻辑——方案文档本来就只有
那一个区。

## 坐标怎么到 h5

**座位坐标只在画布 blob 里，而 blob 不是权威。** `segment_seat` 表有
label/kind/rank/enabled/removedAt 但没有 x/y；反过来 `enabled` 和 `removedAt`
只在表里、blob 里没有。**画一张对的图必须把两边 join 起来**，单靠任何一边都不行。

（confirm 快照救不了这件事：`segment_seating_log` 里那份"完整快照"的"位置"是
`{id,label,kind,rank}`，没有坐标。）

于是解析放在服务端 `shared/seat-canvas.ts`，这是**全仓唯一一处服务端认识
`svg-canvas-v1` 的地方**。它破的是 venue / seating 两个 schema 上写着的"服务端
一个字节都不解析"，边界是：

- **只读。** `saveLayout` / `createPlan` 的写路径继续不解析——归并靠前端投影好的
  `externalId`，不依赖 blob 结构。
- **只取 H5 必需字段。** 座位图取坐标；团体范围取 `rows[].seatIds` 的显式顺序，
  不读 zones、颜色、world 尺寸。
- **失败返回 null，不抛。** 为一张示意图让整个行程页 500 不划算。

让 h5 自己解析（字面上保住那条不变量）是个假选择：耦合一样存在，只是从服务端
搬到了 h5，代价是多一份手写解析器（web 已有一份，两个前端还不许共享代码）外加
把整份 blob + 整份座位行都发下去让前端 join。

## 三个接口

`getItinerary` 的每条议程多一个 `hasSeatMap`：**便宜判定**——只 join
`segment_seating_layout` 取 `renderer_kind`，**绝不取 `data` 列**。一位嘉宾可能
有三五个带排位的环节，为了三颗按钮的显隐把几百 KB 的 jsonb 全拉出来反序列化，
首屏就废了。那一路是 `left join`：没画过图的方案，座位号照给。前提是环节的
`seating_enabled` 仍为 true；开关关闭后，即使历史方案仍是 confirmed，也不返回区域、
座位号或座位图入口。

`getSeatMap`（按需，点开才请求）出参：

```
{ zoneName, seatLabel, map: { seats: [{x,y}], mine: [{x,y,label}], pitch, tables, marks } | null }
```

`tables` 是圆桌/方桌的家具外框（`{shape:"circle",x,y,radius}` 或
`{shape:"rect",x,y,width,height,angle}`），2026-09-16 随"桌"这个概念一起加的，
决策见 [ADR](architecture-decisions.md#桌是排的两种-shape不是新的顶层概念)。
它是下面"明确不做的"里"不画其他形状"这条唯一的例外：桌子数量是"几十"这个
量级，不是座位的"上万"，多画几十个 `<rect>`/`<circle>` 不会碰到单路径换来的
性能上限；服务端 `shared/seat-canvas.ts` 的 `parseTableShapes` 只读桌面的
形状/位置/尺寸，跟圆桌半径同一份公式（`rowRadius`/`tableGeometry` 的服务端
移植），不带名称、种类或人员，跟座位图"没有一个字段属于别人"的边界一致——
这张图回答的仍然是"哪片区域"，不是"哪张桌"，所以不显示桌名。没有 `rows`
的历史画布按"没有桌子"处理，返回空数组，不影响座位号和降级路径。

- `zoneName` / `seatLabel` **恒定有值**，`map` 才可能为 null——降级不需要第二种
  响应形状，图画不出来时前端照样有话说。
- 一人可占多座，`seatLabel` 按位置顺序连接全部座位号。`mine` 包含本人全部座位
  的坐标和标签；前端提供座位按钮逐个定位，避免相邻定位钉挤在一起。任何本人位置
  缺坐标或已软删时整张图降级，全部座位号仍保留。其他位置继续只给坐标。
- 行程查询将同环节座位聚合成一行，座位图查询聚合本人座位后只读取一份方案画布。
  多座分配及统计规则见 [座位分配](seating-assignment.md)。
- **载荷里没有一个字段属于别人**：只有坐标，没有编号、没有种类等级、没有人名。
  这个页面的凭证只是一个手机号，隐私靠"根本不发"，不靠前端拿到了不渲染。
- **越权挡在查询形状上**：`seatMapQuery` 从 `segment_member` 出发并锚死
  `memberId`，传任何 `segmentId` 都只查得出他自己有座位的那个环节。探测别人的
  环节和环节不存在返回**同一个** NOT_FOUND，不区分是有意的。
- `getSeatMap` 与行程查询保持同一条 `seating_enabled` 和 confirmed 口径；排位关闭
  后从旧页面或旧链接请求也返回 NOT_FOUND，不重新暴露历史座位图。

`getOrganizationSeatMap` 同样按需取，但入口不是个人 `segmentMemberId`：它从当前
嘉宾的 `segment_member` 出发，以该行的 `organizationId` 环节快照匹配同环节、已确认、
未撤销的团体占位。没有个人排座的议程行才会露出入口。出参形状仍是
`{ zoneName, seatLabel, map }`：`seatLabel` 已由服务端按 `rows[].seatIds` 合并为范围，
例如 `5排03–05座、6排01–03座`；`aisleEvery` 只控制画布间距，**不切断范围**。图里
所有团体占位均标红，其他位置只给无标签灰点；没有排关系的历史 blob 退回逐个座位号。

`pitch`（典型座距）在服务端算，不让 h5 重算：算法要和管理端画布严格一致，否则
同一片座位在两端会得出两种密度判断。

## 怎么做到"多少座位都刚刚好"

实际长宽比跨度很大（间距取自画布模板：座 48 / 排 64 / T台 160）：

| 形态 | 内容长宽比 |
| --- | --- |
| 秀场双侧 6排×10座 | **≈ 3.2 : 1**（时尚周主场景） |
| 剧场 6排×10座 | ≈ 1.65 : 1 |
| 宴会 6桌×8座 | ≈ 1.6 : 1 |
| 剧场 20排×30座 | ≈ 1.2 : 1 |
| 单排领导席 | ∞（包围盒高度为 0） |

**所以盒子不能是固定纵横比**：3.2:1 的图塞进 4:3 上下空掉六成、座位点小到看不
见，而那恰好是最常见的一种。做法是 `高度 = clamp(宽度 / 内容长宽比, 6rem, 45dvh)`，
然后两端各夹一次：

- **座位少**：屏幕座距上限 44px。八个座位不会被放大成八颗球，到顶就居中留白。
  管的是**座距**不是缩放倍率——世界单位是 48/64，`scale ≤ 1` 在 343px 宽的手机上
  一排只放得下 7 个座位，管理端画布那条上限搬不过来。
- **座位多**：定位钉是**固定屏幕尺寸**、画在 SVG 外面。一千座的图上圆点只有
  两三个像素，红点跟着缩就彻底看不见了。

**viewBox 的长宽比做成和盒子完全一致**，于是 `preserveAspectRatio` 不产生
letterbox 偏移，世界坐标到屏幕坐标是一次纯缩放，定位钉的位置能用一行乘法算准。
被夹住时多出来的空间进 viewBox，表现为内容居中留白。**viewBox 的四个数不许
四舍五入**——省不出东西，却会让长宽比偏千分之一，钉子整体错位。

全部座位重合时包围盒是零矩形，靠留白（`pitch × 0.9`）救回来，加完宽高都是
`2 × pad`，后面所有除法都安全。

## 一条 path

一万座也只有**一个 DOM 节点**：所有座位并进一条 `<path>`，`M x y h0` 是零长度
子路径，靠 `stroke-linecap="round"` 渲染成圆点，`vector-effect="non-scaling-stroke"`
让描边宽度按屏幕像素算。比逐点写圆弧短三倍（一千座实测 10 KB）。

**这个性能特征和"定位图"这个形态是同一个决定的两面**：能并成一条路径，是因为
所有座位长得一模一样——没有编号、没有姓名、不分种类等级、不响应点击。哪天想给
邻座加个编号，先想清楚一万座怎么办。

## 场地标注

2026-09-17 加入，决策见 [ADR](architecture-decisions.md#场地标注是画布对象h5-放不下的文字进图例)，
画法见 [座位画布](seating-canvas.md#场地标注)。`marks` 是运营在管理端画的主题板、门口、
舞台等：`{shape: "rect"|"ellipse"|"polygon", x, y, width, height, points?, color, label}`。
服务端 `parseMapMarks` 把多边形的相对顶点换成绝对坐标，多分区按分区过滤，单条坏数据
只跳过它自己；没有 `marks` 的旧画布给空数组。文字和颜色是场地信息，不属于任何嘉宾，
不破坏"载荷里没有一个字段属于别人"。

- **不从座位推断方向。** 模板生成的图 y 最小侧确实靠台，但手工补座或整体拖动之后
  就不是了，猜出来的方向指反了没人能发现。所以方向只来自运营显式画出的标注。
- **包围盒包含标注。** 画在座位外侧的门口、主题板要完整露出来；座距仍只按座位算。
- **文字固定屏幕字号、不加底色。** 形状随图缩放，文字用 `text-caption`（按根字号换算
  实际像素）画在 SVG 外，与定位钉同一套一行乘法定位。放得下就写在形状里：先横排
  （字高可超出形状 2px，扁长的主题板也能写），瘦高形状再竖排（门、柱子）。算法与
  管理端 `markLabelLayout` 相同，两个前端各有一份。
- **放不下的进图上方图例。** 色块画成标注自己的形状，同色、同形、同名只列一次。图例
  在图外，不挡座位也不改变图的尺寸。
- **形状有最小显示尺寸。** 屏幕上小于 10px 的形状绕中心放大，大场里的小门、洗手间
  照着图例也能找到。
- 标注颜色是运营的数据色，只用于形状和图例色块，不是 H5 的语义色；预置色把红色放
  最后，避免和定位钉、团体占位的主题红混淆。

## 明确不做的
- **不高亮"我这一排"。** `genRunway` 把 T 台左右两侧放在**同一个 y** 上，按 y
  高亮会把对面那一侧一起点亮，而那是完全不同的一排人。
- **不缩放不平移。** 图要一屏看全；而它装在 `Drawer` 里，那层已经吃掉了"向下拖"
  的手势。
- **停用的位置照画，不做视觉区分。** `enabled=false` 是"这次不安排人坐"，椅子
  还在，后台画布上也是画出来的。软删（`removedAt`）的才不画。多一档灰就需要
  图例，而定位图上没有地方放图例——h5 只有主题红一种强调色（见
  [h5-itinerary.md](h5-itinerary.md)）。

## 验证

服务端 `shared/seat-canvas.test.ts` 覆盖解析（版本不认、脏坐标只跳过它自己、
空画布返回 `[]` 而不是 `null`）、座距（单排、中位数、全重合）和桌面外框
（圆桌半径内缩、方桌宽高取四侧跨度较大值、没有 `rows` 时按"没有桌子"处理、
单条排缺字段只跳过它自己）；`modules/h5/routes.test.ts` 覆盖越权的查询形状、
`data` 列没被拉进行程页、停用的位置没被过滤掉、`tables` 不带名称。标注由
`parseMapMarks` 的用例覆盖多边形绝对坐标、旧画布空数组、单条坏数据跳过和分区过滤，
路由用例覆盖 `marks` 只带形状、颜色和文字。

**`apps/h5` 这次装上了测试**（`bun test`，跟 `apps/server` 一样，不引入
vitest——在深路径 worktree 下 `bun install` 是已知的脆弱环节，能不加依赖就不加），
`-components/seat-map-layout.test.ts` 覆盖上面所有排版规则。

浏览器里逐个跑过：秀场扁条（126px 高，T 台通道可辨）、单排（撞下界 96px）、
1000 座（SVG 子节点数 = 1，d 属性 10 KB）、8 座（座距正好 44）、全部重合
（viewBox 有限、钉子居中、无 console 错误），外加三条降级路径。

标注在 375 宽手机视口下跑过五种布局：截图宴会（扁主题板横排、窄门竖排）、剧场
600 座（椭圆舞台、梯形控台写在里面，小出入口进图例）、秀场 T 台、圆桌宴会（两扇同名
门在图例里只列一次）、1600 座大场（小标注放大到最小尺寸、四项图例）；另从管理端活动
空间画标注、建方案、确认后在 H5 看到同样的标注。
