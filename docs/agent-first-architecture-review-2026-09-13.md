# Agent-first 工程体系评审

评审日期：2026-09-12—13。代码基线：`7e72b28`。状态：**优化建议，尚未采纳为项目规范**。

评审对象是架构、技术栈、知识组织、skill、开发与交付流程。判断标准是：一个 Agent 从接到需求到交付可接受变更，需要付出多少阅读、澄清、实现、验证和返工成本。

本文是一次阶段性评审的归档材料，不建议加入每次任务的默认阅读清单。采纳的结论应分别进入当前规范、对应 skill 或自动检查；本文保留当时的依据与实验结果。

后续结合官方指导、开源工程与社区经验形成了[第一轮优化建议修订版](C:/Users/Administrator/.codex/worktrees/6f8a/pszx-hdyy/docs/agent-first-round-one-plan.md)，补充跨 Agent 的 skill 适配、文档发现入口与轻量效果评估；第一轮实施顺序以该建议为准。

## 1. 总体判断

**值得安排一轮工程体系优化。现有主技术栈和部署架构可以继续承担后续迭代，优先改造知识入口、共享契约、类型编译边界、复杂功能的变更边界和验证工作流。**

项目已经具备不少有利于 Agent 的设计：单仓库的端到端类型检查、真实认证链路下的开发登录、每个 worktree 的一次性数据库、固定种子、集中权限映射、迁移漂移检查，以及相当具体的业务经验记录。这些设计减少了猜测和人工准备工作，应继续保留。

当前的主要制约来自规模变化：早期依赖“读完约定、照着 supplier 写、做完全量检查”就足够的开发方式，已经承载了大量不同形态的业务。项目积累了规则，却还没有同等成熟的规则更新、按需加载、自动执行和效果评估机制。

建议按以下顺序投入：

| 顺序 | 优化对象 | 对 Agent 的直接收益 | 判断把握 |
| --- | --- | --- | --- |
| 1 | 缩减并校准默认上下文；恢复可信的检查入口 | 少读过期内容，少判断冲突规则，减少重复检查与误报 | 高，有直接仓库证据 |
| 2 | 建立共享纯契约；落地真正的客户端声明边界 | 减少前后端重复维护；缩短前端反馈时间 | 高；声明边界已有本机实验 |
| 3 | 按功能形态建立开发范式，整理复杂功能边界 | 改动范围更可预测，降低长文件和跨模块任务的理解成本 | 中高，需要真实任务试点 |
| 4 | 把重复工作流做成少量项目 skill 和薄脚本 | 减少重复决策、环境探测和遗漏 | 中高，现有排序 skill 已提供好样例 |
| 5 | 建立任务评估集和交付证据 | 用实际结果判断规范、工具、模型与流程是否更有效 | 方向明确，收益幅度需测量 |

## 2. 技术栈：保留主干，调整边界

| 现有选择 | 建议 | 理由与重审条件 |
| --- | --- | --- |
| Bun workspaces + TypeScript | 保留；把经过验证的工具版本固定下来 | 一个仓库完成开发与验证很合适。当前 Bun 范围、镜像标签和部分 `@latest` 工具入口过宽，应减少环境漂移。无需为当前规模引入 Nx/Turborepo |
| React + Vite + TanStack Router 的 SPA | 保留 | 管理端与现有 H5 的交互需求可以继续由 SPA 支撑。当前没有证据证明引入 SSR、服务端组件或 TanStack Start 能提高这些任务的交付效率 |

| Hono + `hc` + 业务结果信封 | 保留；预展开并编译客户端类型 | 已有类型通道有效。业务全部 POST、结果通过 `code` 表达，是明确取舍；当前不足以构成迁移 tRPC/oRPC 或改造全部 HTTP 语义的理由 |
| Drizzle + PostgreSQL | 保留 | 当前数据关系、事务和显式 SQL 都适合这套工具。主要应加强业务事务接口与数据库验收，缺少更换 ORM 的收益证据 |
| `apps/server` 内部的 DB 实现 | 继续保留 | 没有因为“目录更完整”拆 `packages/db` 的必要。出现独立 worker、CLI 服务等实际运行时消费者时再评估 |
| 管理端 Base UI + shadcn，H5 独立视觉体系 | 保留 | 两端视觉和交互目标不同。共享纯业务契约与共享 UI 是不同决策，可以实施前者，同时继续各自维护组件和主题 |
| Better Auth 管理端认证 | 保留；对齐运行库与生成工具的版本策略 | 当前运行库是 1.6.26，CLI 锁定版本为 1.4.21。不能据此直接判定不兼容，但 schema 生成应有固定版本和差异审阅机制 |
| 单个镜像、同一服务提供两个端 | 保留；改善可观测性和制品来源记录 | 当前不需要微服务和独立发布平台。先让 Agent 能确定运行实例、数据库、构建提交和失败原因 |

关于前端资源体积，本次构建已经验证自动路由拆分生效。文档预览有约 1.28 MB 的独立 JS chunk，不应直接把它算成每个页面的首屏成本。后续应按实际进入路径、首次打开预览的等待时间决定是否再延迟加载，避免围绕单个构建告警进行无收益改造。

## 3. 默认上下文应当更短、更准确

### 3.1 根 AGENTS.md 已没有有效余量

当前文件为 **32,766 字节**，距离 32,768 字节只有 2 字节。Codex 官方说明的默认限制是项目指令发现链的合计预算，并非每个文件都能独立获得 32 KiB；发现链还与任务的工作目录有关。因此，只把内容挪到子目录 `AGENTS.md`，同时让根文件保持满额，并不能可靠解决加载问题。[官方 AGENTS.md 说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

更大的问题是：每个任务都默认携带大量只与特定模块、历史环境或特殊交互有关的内容。

建议把根文件压到 **6—10 KiB 的团队目标**。这个范围是本报告建议的工程预算，不是平台的官方要求。根文件只保留：

1. 可以直接执行的开发、验证入口。
2. 少数跨全仓、违反后代价很高的边界。
3. 按任务类型查阅当前文档与 skill 的索引。
4. 用户决策、当前规范、上游资料冲突时的处理规则。

特殊业务保存顺序、排序算法、H5 适配原理、Windows 历史排障过程应通过明确触发条件加载。自动检查可保证根文件预算、链接有效性、关键命令与包脚本一致；文档语义是否过期仍需要在相应功能改变时审阅。

### 3.2 当前状态与历史理由需要分开维护

已有几处能直接增加 Agent 判断成本的证据：

| 记录中的前提 | 当前仓库状态 | 对开发的影响 |
| --- | --- | --- |
| H5 身份体系未实现，H5 没有测试脚本 | 已存在 H5 守卫、接口和 `bun test` 脚本 | Agent 可能重复设计、跳过已有验证，或误判任务无法开展。应准确描述现有简化方案及仍待决定的部分 |
| 类型性能讨论以模板只有 2—3 个接口为前提 | 当前规模已明显增长，前端类型检查有实际成本 | 早期“暂不需要”的结论被继续当作当前判断 |
| CRUD 校验暂时手抄，因为只有一个模块 | supplier、venue、member 等多个表单均有本地 schema | 当初承诺的重审条件已经出现，却缺少触发机制 |
| 页面本地文件名只有四类 | 复杂编辑器已存在 `-draft.ts` 等有明确职责的文件 | Agent 被迫在清晰命名和旧白名单之间做额外解释 |
| `hcWithType` 已完成预编译 | exports 仍指向源码，构建没有客户端声明边界 | 对真实类型成本形成错误预期 |

定位依据：[AGENTS.md](C:/Users/Administrator/.codex/worktrees/6f8a/pszx-hdyy/AGENTS.md)、[架构决策](C:/Users/Administrator/.codex/worktrees/6f8a/pszx-hdyy/docs/architecture-decisions.md:47)、[CRUD 指南](C:/Users/Administrator/.codex/worktrees/6f8a/pszx-hdyy/docs/crud-page-guide.md:248)、[H5 包脚本](C:/Users/Administrator/.codex/worktrees/6f8a/pszx-hdyy/apps/h5/package.json:9)。

建议将知识分为四类，每类只有一种主要职责：

| 类别 | 回答的问题 | 更新方式 |
| --- | --- | --- |
| 当前契约 | 现在必须成立的行为和边界是什么？ | 功能语义改变时一起改 |
| 工作流 skill | 这类任务应该如何定位、实施、验证？ | 完成同类任务后更新可复用流程 |
| 架构决策 | 为什么采用这个取舍，何时应重审？ | 保留历史；标注已替代、仍适用或待重审 |
| 执行记录/评审 | 某次任务做了什么，有什么证据？ | 归档，默认不加入新任务上下文 |

每个重要决策补充“适用范围、依赖前提、重审触发条件、当前状态”。例如，固定版本的拖拽库经验与过去某个 Agent 工具的密码输入限制，都应带环境范围，避免升级后变成全项目永久定律。

### 3.3 让经验有退出机制

推荐的经验沉淀流程是：

```text
实际遇到问题
  → 留下最小案例和适用范围
  → 能自动检查的进入工具或测试
  → 需要判断的进入对应 skill / 当前契约
  → 历史排查过程归档
  → 自动机制稳定后，删除根指令中的重复提醒
```

例如，“不要跨路由引用本地文件”已经足够明确，应该由导入图检查执行；根文件保留一句原则和检查入口即可。反过来，“这个抽象是否值得提取”依赖具体消费者，适合保留判断框架。

## 4. Skill：重点建设项目工作流

### 4.1 排序 skill 是值得沿用的模式

[table-ordering/SKILL.md](C:/Users/Administrator/.codex/worktrees/6f8a/pszx-hdyy/.agents/skills/table-ordering/SKILL.md) 有几项有价值的设计：触发范围明确，排除普通列排序；先定位当前任务；按章节读取资料；引用实际实现；区分真实第二个消费者与多个读取出口；分别报告自动测试、数据库和浏览器证据。

它减少的是重复决策。建议继续维护，但把“当前稳定行为契约”从长期计划和执行记录中提炼出来，避免每次接入仍需在多份历史文档中找最终结论。

### 4.2 上游 skill 应有项目适配说明

[shadcn/SKILL.md](C:/Users/Administrator/.codex/worktrees/6f8a/pszx-hdyy/.agents/skills/shadcn/SKILL.md) 同时提供 API 用法和很强的 UI 风格规则。它的 Base UI toast 建议、颜色与样式覆盖要求，与本仓库使用 Sonner 和 CRUD 配色约定存在差异；动态 `npx ... info` 片段也依赖具体宿主是否支持解释执行。

建议保留上游组件 API、可访问性与组合规则，同时提供一份很短的项目适配说明：只适用于 `apps/web`，明确 Base UI、Sonner、Bun runner、本地视觉约定与上游版本。升级时审阅差异。避免把上游文件改成无法更新的长期 fork，也避免每次让 Agent 临场调解相同冲突。

### 4.3 Intent 的发现范围需要收窄

本次安装依赖后，`intent list` 发现 10 个包、33 个 skill，其中包括由可选 peer 依赖带入的 TanStack Start 相关能力。本项目是 SPA，装进依赖图并不代表应采用它的架构建议。当前命令也提示未来将要求显式的 `intent.skills` 配置。

建议固定经过验证的 Intent 工具版本，并显式选择实际使用的 skill。普通任务读取锁定版本对应的资料；工具和 skill 更新作为独立依赖维护任务。不要把每次大改前的 `@latest` 发现过程同时变成一次不可控的工具升级。

官方 skill 机制强调先暴露名称与描述，再按需加载正文；这与仓库需要的低默认上下文成本相符。[官方 skills 说明](https://learn.chatgpt.com/docs/build-skills)

### 4.4 优先新增的项目 skill

建议逐个试点，先做最常出现的工作流：

| Skill 方向 | 主要内容 | 应避免包含的内容 |
| --- | --- | --- |
| CRUD 纵向开发 | 契约、路由、权限登记、查询键、表单、种子、验收入口，引用 supplier | 完整重述 React、Hono、TanStack 文档 |
| 跨模块写入 | 业务范围、事务所有者、增量意图、写入顺序、冲突反馈、数据库用例 | 给每个简单模块强制增加 service/repository 层 |
| Schema 与迁移变更 | 表结构、迁移生成、种子、空库和升级路径、回滚/补救说明 | 默认执行持久环境迁移或发布 |

复杂表格、画布的交互工作流可在后续重复任务足够多时再独立成 skill。

每个 skill 应有几道真实任务作为评估案例，包括应该触发、容易误触发、普通完成、需求改变的情况。验收指标是是否定位正确文件、是否少读无关材料、是否减少遗漏与澄清，而不是 skill 文档是否足够长。

## 5. 代码架构：让任务的变更边界更清楚

### 5.1 保留现有目录分层，补上自动约束

静态扫描中，后端 `infra/shared/modules` 的主要依赖方向总体成立，未发现文件级静态运行时导入环。这说明现有分层可以继续用。

前端扫描到 6 处业务代码跨路由引用 venue 的本地 `-queries` / `-utils`。这说明对应能力已经有多个消费者，适合提升到 `features/venue`，也说明仅靠文字规则不足以持续约束全仓。无需借此重排所有目录。

建议使用一份小型 AST 导入检查，覆盖以下高价值边界：前端禁止跨路由引用本地目录、feature 不回引 routes、shared 不依赖业务、两端不直接互引、服务端基础设施不依赖业务模块、浏览器运行时只允许明确的安全导出。

检查要区分类型导入、运行时导入、测试和生成文件，并支持带理由的有限例外。`@repo/server/client-type` 是有意设计的浏览器客户端适配器，不能因为是运行时导入就误报为数据库代码泄漏。

### 5.2 简单 CRUD 与复杂业务需要不同参考实现

supplier 是好的 CRUD 范式，但不能承担所有功能的示例职责。当前活动人员页面约 1,789 行，seating 路由约 1,919 行；活动人员页面同时负责筛选、多个表单、导入/添加、排序草稿、拖拽事件、变更反馈和详情渲染。单纯规定文件不得超过某个行数，无法解决这些职责之间的关系。

建议建立三类纵向样例：

1. **简单 CRUD**：保留直接路由处理、页面本地 queries、表单和查询键。
2. **跨模块命令**：参考 `agenda/segment-config.ts` 和 `project/activity-delete.ts`，显式定义事务与业务编排入口。
3. **复杂编辑器/交互表格**：区分页面组合、草稿状态、纯计算、交互适配和保存命令。

对于活动人员页面，可把排序编辑状态与拖拽适配、人员增改操作、详情展示分别放入页面本地模块。提取标准是“一个任务能否只理解这一块便完成修改”，而非组件长度或文件数量。

页面本地命名规则宜从四个固定名字扩展为语义规则：仍然强制 `-` 前缀避免生成路由，允许 `-draft.ts`、`-validation.ts` 等明确职责的本地模块。消费方由两个降到一个时，也无需仅为数量达标立刻搬家；结合边界是否稳定、后续变化是否可预见决定，减少来回移动制造的改动噪声。

### 5.3 跨模块事务应成为显式架构能力

`agenda/segment-config.ts` 已有很好的基础：复用人员、资源和环节写入逻辑，集中表达写入顺序与临时 ID 解析。可以把这种模式提升为复杂写入的范式：

```text
route：输入校验、身份/权限、结果信封
  → 业务命令：确定事务、作用范围、写入次序、冲突结果
      → 模块操作：接收同一个 tx，维护所属数据的规则
      → 纯计算：差异、排序、布局、字段归一化
```

简单操作继续就地实现。复杂操作才需要这个分解。尤其要清楚标明谁开启事务、哪些函数要求已有事务、事务失败如何返回给 UI，避免每个 Agent 从调用链反推。

模块目录之间存在双向依赖不必一概重写：读取另一个模块的表类型和调用另一个模块的业务命令，其耦合程度不同。应优先稳定跨模块的命令入口，保留有说明的级联编排，避免为满足图形上的单向箭头增加大量转发层。

### 5.4 为高频领域建立小型当前契约

人员主档、项目人员、活动人员、环节人员的 ID 与作用范围，以及排序意图、整页保存意图，值得有少量明确词汇和示例。每份契约写出：输入对象、所属范围、允许变化、必须保留的关系、调用出口和一个关键验收案例。

对于容易混淆的内部 ID，可在纯规划器和业务命令入口小范围试用带品牌的类型；API 仍使用普通 JSON 数字并由服务端验证归属。不要把所有数字全仓包装成名义类型。这项优化应以减少跨层对象混用和理解时间为目标。

## 6. 共享纯契约的重审条件已经出现

CRUD 指南明确接受手抄前端 schema，并以第三个模块出现重复作为重审条件。当前 supplier、venue、member 等均已满足需要重新评估的范围。TypeScript 从 API 推导出的字段类型，无法表达手机号正则、字符串最大长度等全部运行时规则，因此类型一致也不能替代这些规则的共享。

**建议建立浏览器安全的共享契约边界，先以 supplier、venue、member 的纯字段和输入规则为试点。** 独立 `packages/contracts` 已有前后端两个真实运行时消费者，具备讨论价值；它与暂不拆 `packages/db` 的理由不同。如果先采用 `@repo/server/contracts/<domain>` 的明确子路径，也必须建立同样的依赖边界和检查，目录名本身不是收益来源。

契约层只允许纯 Zod、类型、枚举与纯函数，不依赖 Drizzle 表、数据库连接、环境变量、认证对象和文件系统。现在散落在 `schema.ts` 中、前端也需要的枚举可由契约层持有，再由数据库 schema 引用。

共享范围应保持明确：

| 内容 | 是否共享 |
| --- | --- |
| 字段长度、格式、领域枚举、通用字段归一化 | 适合共享 |
| 创建/修改命令的传输输入 | 按实际语义共享，明确遗漏、空值、清空的区别 |
| 前端 touched、空输入展示、分步表单状态 | 留在前端，可扩展共享字段规则 |
| 数据库唯一性、对象归属、权限、事务规则 | 留在服务端执行 |
| 所有接口的输出 Zod schema | 不要求补齐；继续推导明确投影，外部数据边界按需验证 |

前端表单原始值与服务器归一化后的值可以不同。试点必须确认默认值、空字符串和 `z.input` / `z.output` 的区别，避免为复用一个 schema 损害交互体验。

试点验收：修改一个共享字段规则，只需改一个权威位置；前后端相应行为有明确验证；浏览器构建不引入服务端依赖；类型检查和调试步骤的总成本没有明显倒退。通过后再扩展到其他模块。

## 7. 类型边界：有实测收益，也有构建代价

### 7.1 当前封装尚未形成独立编译边界

[client-type.ts](C:/Users/Administrator/.codex/worktrees/6f8a/pszx-hdyy/apps/server/src/client-type.ts:1) 导出 `ReturnType<typeof hc<AppType>>`，而 [server/package.json](C:/Users/Administrator/.codex/worktrees/6f8a/pszx-hdyy/apps/server/package.json:5) 仍将该导出指向 `.ts` 源码。现有构建只生成服务端 JS，没有供前端消费的声明构建阶段。

实验在忽略目录及仓库外进行，没有修改业务接口、正式 tsconfig 或导出配置。步骤为：用 `const client = hc<AppType>("")` 先展开客户端形状，生成声明文件，通过临时前端 tsconfig 改用声明；连同其引用的服务端类型一起使用声明版本。

| 指标 | 当前源码边界，复测 | 声明边界，复测 |
| --- | ---: | ---: |
| 管理端 tsc 总时间 | 14.66 秒 | 9.07 秒 |
| Check time | 12.00 秒 | 6.58 秒 |

首次源码检查为 17.32 秒，声明边界另一次为 9.21 秒，说明时间存在本机波动。按复测对比，前端检查时间约减少 38%，类型实例化约减少 70%，报告内存约减少 32%。这是本机原型结果，不能直接等同于所有任务的交付提速。

额外类型探针确认了供应商输入字段、成功响应字段与成功码的精确类型，错误的字符串 ID 仍会被编译器拒绝。声明版前端的服务端源码引用只剩独立的权限与字典数据模块。这些验证尚不等于所有接口的类型等价证明。

### 7.3 实施时必须计入的成本

原型全量服务端声明生成约 8.42 秒，客户端声明约 558 KB。原型还粗粒度产生了服务端其他声明，不是可以直接提交的最终包设计。

因此，**全新环境第一次生成声明再检查一个前端，总时间可能增加**。收益主要来自两个前端和编辑器复用已编译类型，尤其是只改前端的日常迭代。

正式方案需要同时完成：

1. 精确的公共声明出口和浏览器安全的客户端运行时代码。
2. 首次安装/启动的自动生成，以及后端变更的 watch 更新。
3. 防止声明陈旧的合并检查和类型契约探针。
4. 比较前端单独修改、后端契约修改、干净全量构建三种工作负载。

建议先落实这个边界，再根据新的性能数据考虑管理端/H5或业务域级客户端拆分。当前不需要为所有模块立刻生成独立客户端。

## 8. 工作流：缩短反馈时间，维持可信门禁

### 8.1 保留隔离开发环境，增加可读取的运行状态

本次 `bun run dev` 能在约 3 秒量级完成临时库准备与种子导入，并自动协调被占用的端口。固定种子和真实登录链路对 Agent 的作用很直接：可以从明确业务状态开始验证。

下一步建议增加薄的 `dev:status` / `doctor` 能力，输出工作区身份、进程和实际端口、数据库容器标识、当前迁移版本、健康状态与登录入口，支持 JSON。不要在输出中包含密码或完整连接凭据。

Agent 应从这份运行状态获取地址，不再从终端历史、默认端口和多个 `.env` 片段反复拼接。数据库用例也应复用现有临时库设施，减少第二套环境编排代码。

### 8.2 建立语义明确、默认不写文件的 verify 入口

当前根 `check` 实际执行全仓 `biome check --write`，而日常规范要求按改动文件执行只读检查。脚本名字与真实用途不一致，反复增加 Agent 的操作成本。

本次只读全仓检查得到 460 个 error，大量来自 CRLF/LF 格式差异；禁用 formatter 后仍有 29 个 error。这些不是 460 个功能缺陷，但说明当前全仓格式门禁不能直接作为可信绿灯。`.gitattributes` 对 SQL 和 shell 明确了 LF，TS/TSX 尚未与 Biome 默认对齐。

建议定义统一入口：`verify --changed` 提供任务内反馈，`verify --full` 提供合并证据，`format` 明确表示写文件。具体命令名可以调整，但读写行为必须直观。

跨平台换行修复应作为一次独立、可审阅的仓库维护变更。不要让每个业务任务顺手处理一遍格式差异。验收标准是在干净 Windows worktree 与构建环境中得到一致的只读检查结果。

### 8.3 按改动性质选择验证

| 改动 | 任务内主要验证 | 合并前补充 |
| --- | --- | --- |
| 文档、低影响样式 | 链接/格式或相关页面检查 | 按实际影响决定，不机械新增单测 |
| 普通 CRUD | 类型检查、受影响单测、关键交互 | 全仓门禁 |
| 跨模块写入 | 纯逻辑用例、真实数据库原子性与业务范围 | 全仓门禁 |
| 草稿、拖拽、画布 | 状态/算法测试，实际指针和键盘交互 | 全仓门禁 |
| schema/迁移 | 漂移检查、空库建库、已有数据升级用例 | 构建与迁移验收 |
| 身份/权限或公开入口 | 实际请求链路与不同身份边界 | 全仓门禁 |

“按改动检查”不能仅根据文件目录选择测试：共享契约、公共 UI、权限入口、工具链的变更应扩大影响集合；不确定时回退全量。当前检查规模还没有大到必须引入复杂任务图系统，一份透明的 Bun 编排脚本足够起步。

### 8.4 让测试证据与它能证明的事相匹配

本次各包最终结果合计为 836 个通过、3 个已登记的 invitation 模板失败；类型检查和生产构建通过。三个既有失败涉及产品模板口径，不能通过此次架构评审擅自修改期望。

现有权限映射覆盖检查和 schema 漂移检查非常适合 Agent：漏登记、漏迁移可以立即得到明确修法。应扩展这种机制。

另一方面，后端相当一部分测试是纯逻辑、SQL 生成或源码结构检查，它们不能证明真实事务执行、并发行为或 HTTP 守卫链路。补充测试应围绕这些缺少的反馈能力，而不是增加重复断言来追求总数。

既有红灯需要有最终处理路径。产品口径确定前，如采用临时隔离清单，应精确记录测试名、原因、负责人/决策人和复审时间；失败消失或新增失败都要被发现。输出必须分别显示通过、已知失败和新增失败，不能将测试退出码无条件吞掉并标为“全绿”。

### 8.5 让交付证据可以复用

仓库内未发现已跟踪的 CI workflow；本地 Git hooks 主要维护线性历史，发布脚本也没有关联类型/测试通过的证据。这不排除仓库外存在流水线，但从仓库本身无法复现完整门禁。

建议让全量验证输出一份小型机器可读记录：HEAD、依赖/运行时版本、命令、结果、时长、已知例外；有未提交内容时还要记录工作区差异的身份，避免只凭 HEAD 复用已经过期的结果。CI 或合并检查消费同一入口。

镜像构建应明确校验所用提交与版本标签的关系，并记录提交和镜像 digest。`build-push.ts` 当前以工作目录为构建上下文，指定版本或最近 tag 不自动代表内容就是该 tag。此处的优化目标是让 Agent 与人能够准确回答“这个环境跑的是哪份被验证的代码”。

继续保持现有由用户编排 master 合并的流程；本评审不建议扩大 Agent 的发布授权。

### 8.6 日志首先服务于定位

建议在请求日志中增加 requestId、业务路径、业务 `code`、耗时和异常关联信息，并提供可区分进程存活与依赖就绪的健康信息。业务结果使用 HTTP 200 的项目，单看 HTTP 状态无法解释业务失败。

初期无需接入完整观测平台。结构化日志和运行状态文件已能帮助 Agent 把浏览器现象关联到具体请求与实例。

## 9. 规范中哪些要严格，哪些可以放松

| 应严格执行，并优先自动化 | 允许结合任务做判断 |
| --- | --- |
| 权限覆盖、真实身份边界、业务对象范围 | 是否提取一个只在本页使用的组件 |
| schema、迁移、种子的一致性 | 文件长度与主导出数量 |
| 跨路由本地目录、客户端运行时依赖边界 | 页面本地辅助文件的具体名字 |
| 增量意图、事务原子性、关键写入顺序 | 复用消费者减少后是否立刻搬回本地 |
| 生成物来源、验证结果与提交对应 | 是否需要独立 workspace 包 |
| 关键契约的兼容行为 | 是否在某个复杂模块增加业务命令文件 |

规范也有维护成本。越是高后果、可判定的规则，越适合工具执行；越是涉及设计判断的规则，越应该提供反例、边界与重审条件，而非不断扩充“绝对不许”。

例如，新增菜单修改四处已有测试兜底，这是可理解的显式接线。可以通过薄生成脚本提示所需文件；没有必要为了把“四处”变成“一处”，创建同时控制服务端授权、前端图标和路由行为的庞大元数据系统。

## 10. 用真实任务衡量优化效果

建议从历史任务中选择 6—10 个代表案例，固定起始提交、需求和验收条件。例如：新增一个 CRUD 字段、增加一种筛选条件、调整一个跨层人员规则、给第二张表接入人工排序、改变草稿保存行为、执行带已有数据的 schema 升级。

比较优化前后：

- 首次提交验收通过率。
- 从开始到被接受变更的总时间与总成本，包含返工。
- 需要用户澄清的次数及原因。
- 阅读的无关文件/历史材料，以及重复工具调用。
- 检查等待时间、环境恢复时间、类型反馈时间。
- 非预期改动文件数与验收遗漏。

在相同起点与验收条件下，重复若干次再比较趋势，记录缓存、机器负载和 Agent 工具差异。每次主要验证一项改进，避免同时改 skill、模型、架构和测试后无法归因。

模型选择也应使用这组任务衡量：能以更低总成本通过同样验收的配置适合常规实现；影响契约、事务和架构的任务可以分配更多推理与独立审阅预算。当前没有本项目的数据支持给出某个模型固定“更适合”的结论。

## 11. 建议实施顺序与完成标准

### 第一轮：整理知识与检查入口

交付内容：缩减根 AGENTS；校准 H5、类型边界等当前状态；为主要 ADR 标注重审条件；明确 Intent 范围与版本；提供项目 shadcn 适配说明；统一只读 verify 入口；解决换行与既有红灯的可见性。

完成标准：新任务能通过短索引找到当前契约；同一事项只有一个当前规范来源；干净 worktree 的检查结果可复现；检查输出能明确区分通过、已知例外与新增失败。

### 第二轮：两个有边界的架构试点

交付内容：共享 supplier/venue/member 的纯契约试点；正式客户端声明边界与更新链路；高价值导入边界检查；整理活动人员页面或一个复杂写入入口，建立第二类纵向样例。

完成标准：字段规则变更减少重复修改；浏览器依赖检查通过；前端类型检查有可重复收益，声明不会静默陈旧；复杂任务的影响范围更容易预测。分别记录首次构建和日常迭代成本。

### 第三轮：固化反复有效的工作流

交付内容：CRUD、跨模块写入、迁移三个方向中最常用的项目 skill；复用临时库的集成验收；机器可读开发状态和验证记录；仓库内可复现的合并/构建门禁；一组 Agent 任务评估案例。

完成标准：实际代表任务的验收遗漏、重复阅读、环境排查和返工减少。只有这些数据改善后，再扩展生成脚本、抽象层或更细的客户端分包。

## 12. 当前不建议安排的工程

整体迁移 Next.js/TanStack Start、替换 Hono/ORM、拆微服务、强行统一两个前端 UI、为所有模块生成 service/repository 四件套、引入通用 CRUD DSL、给每种依赖都增加一个 skill、仅按文件行数开展全仓拆分，目前都缺少与 Agent 效率相称的收益证据。

项目接下来最有价值的能力，是让 Agent 能迅速知道当前规则、找到真正的变更入口、复用稳定契约，并用较短的反馈链证明任务完成。上述三轮优化围绕这些能力展开，保留已经有效的工程基础。
