## 前后端类型安全

### 目标

三条诉求，都要同时满足：

1. 后端显式定义输入/输出 schema（不是靠 handler 返回值反推）
2. 端到端类型安全，改了 handler 前端编译期就能发现
3. 业务语义和 HTTP 协议解耦——不遵循 REST 那套"路径表达资源、动词表达操作、状态码表达结果"

### 为什么不是 oRPC / tRPC

这是最先被考虑、也最贴合"业务语义脱离 HTTP"这条诉求的方案——procedure 按业务域组织成树，`.errors()` 声明的业务错误码天然跟 HTTP status 无关，`isDefinedError` 提供编译期收窄。技术上完全成立。

最终没选，是因为用户明确要求"前后端衔接这块有框架保障就行，不想再多引入一层 RPC 框架"——衡量下来，Hono 自己已经能做到同样的三条诉求（见下），多引入 oRPC 换来的增量是路由从 procedure 树自动派生、以及更精致的错误收窄语法，但这不是必须的，模板要保持精简。

### 最终方案：纯 Hono + Zod + 一份共享信封

**不是自己发明一套 RPC 协议**，是三个框架自带的机制拼起来：

- `hc<AppType>()`（Hono 官方 RPC 客户端）—— 端到端类型推断，不用 codegen
- `@hono/zod-validator` —— 输入侧的 schema 校验，官方中间件
- 一个 12 行的共享类型 `ApiResult<T>`（[`apps/server/src/shared/result.ts`](../apps/server/src/modules)）—— 输出侧的"business code, not http status"约定

三条诉求对照：

| 诉求 | 落地方式 |
|---|---|
| 显式 schema | 每个端点自己的 `schemas.ts`（Zod），handler 用 `c.req.valid("json")` |
| 端到端类型安全 | `hc<AppType>` 全自动推断，改 handler 前端编译期报错 |
| 脱离 REST 语义 | 业务路径是动作名（`getServerInfo`、`submitEcho`），全部 POST；业务结果放在 body 的 `code` 字段，不用状态码表达。文件二进制读取使用 `GET /api/file/:fileId` 作为传输层例外，以支持浏览器原生预览和下载 |

**状态码的边界**：只有两类响应会返回真正的非 200 —— 请求体不是合法 JSON（`zValidator` 的自定义 error hook 拦下）、handler 内部抛出未捕获异常（顶层 `app.onError`）。这两类是"传输层出了问题"，跟业务结果无关；除此之外一律 200，`code` 字段承担 `OK` / `UNAUTHORIZED` / `VALIDATION_ERROR` 等所有业务状态。文件读取成功返回原始二进制，读取失败仍返回 JSON 信封。前端**只看 `result.code`，不看 `res.status`** 做业务判断。

**曾经考虑过 `@hono/zod-openapi`**（Zod schema 同时驱动运行时校验和 OpenAPI 文档），最后没用：OpenAPI 文档的价值在于给"你控制不了的消费方"看（外部团队、非 TS 客户端），当前是同仓库同人维护前后端，`hc<AppType>` 已经提供了比文档更强、且不会过期的保障，为此把每个端点从 ~6 行加到 ~20 行不值。真需要文档/给外部消费方用的那天，`OpenAPIHono` 是 `Hono` 的父类，能平滑升级，不是单向门。

### 已验证：discriminated union 在同状态码下依然正确收窄

方案能不能成立，关键在一个具体的类型系统问题：`ApiResult<T>` 的两个分支（`{code:"OK",data}` 和 `{code:"ERR",message}`）返回的 **HTTP 状态码都是 200**，`hc` 客户端能不能仅凭 `code` 字段正确推出可辨识联合类型、并在 `if (result.code === "OK")` 里正确收窄？

写了最小复现验证过（两个分支都 `c.json(..., )` 默认 200），结果：**可以**。`result.code === "OK"` 分支内 `.data` 可访问、`.message` 编译报错；没收窄前两个字段都访问不到。这是 Hono 自己的类型系统能力（`c.json()` 返回值的联合来自 handler 函数返回类型的正常 TS 推断），不依赖任何额外库。

## AppType 的编译期性能

Hono 官方文档有一条警告："路由越多，IDE 越慢"——单个 Hono 实例链的路由数量增长时，`typeof routes` 这个类型的合并开销会增大，拖慢 `tsc` 和编辑器的类型检查。

**这条警告和"是否显式定义 schema"无关，也不会被"写清楚类型"绕开**——实测过，见下。

### 实测数据

用真实的 `apps/server` tsconfig 和依赖跑的（不是纸面推算），对比"handler 返回值靠推导"vs"`c.json<T>()` 显式声明、`T = z.infer<ZodSchema>`"：

| 条件 | 25 条路由 | 75 条路由 |
|---|---|---|
| 基线（这批路由不存在） | 1860 ms | — |
| 推导（`c.json({...})`，无类型标注） | 1975 ms | 2018 / 2054 ms（两轮） |
| 显式 Zod（`c.json<T>()`） | 1978 ms | 2088 / 2115 ms（两轮） |

结论：

- 两条曲线随路由数量**同步**上涨，显式类型没有改变 Hono 路由链本身的 scaling 特性——这条性能警告的根源是路由链的类型合并机制，不是"类型有没有名字"
- 显式 Zod 版本在 75 条路由时反而比推导版本多花 60~100ms——`z.infer<>` 把 Zod 自己的泛型体系翻译成 TS 类型，这本身有编译期代价，是社区里有据可查的问题。所以显式 schema 不是在"避开"这条警告，是在其之上又加了一层自己的、独立的开销
- 但两者的绝对数字都很小：75 条复杂路由，涨幅也就一成多。当前模板只有 2~3 个端点，这条警告离触发还差两个数量级，现在不用为此改设计

### 已经采纳的免费防御

`apps/server/src/client-type.ts` 用官方的 `hcWithType` 预编译技巧——把类型计算挪到 `tsc` 编译期算好，IDE 不用每次重新展开整棵类型树。零行为差异，纯包装，现在就用，不用等到规模变大。

真正的拆分手段（用 `.route()` 把大 app 拆成按业务域组织的子 app，见 [AGENTS.md](../AGENTS.md#后端目录结构基础设施--业务模块--共享逻辑) 的 `modules/` 结构）等路由数量明显增长、`tsc` 肉眼可感变慢时再做，不是现在的优先级。

## 排位候选人员按当前环节收敛

### 背景

排位方案按环节隔离。此前排位画布的候选接口从活动人员出发，再用左连接补充当前
环节关系，因此同一活动中只参加其他环节的人员也会出现在右侧列表；前端还允许点选
这类人员并在排位时自动补建环节人员关系。这个行为与排位画布“从环节人员选择”的
交互口径不一致，也容易把人员误排到不相关的环节。

### 决策

`listCandidates` 只返回已经关联 `segmentId` 对应环节的 `segment_member`。活动人员
必须先在环节人员管理中加入当前环节，才能进入排位候选列表。右侧页面只调用接收
`segmentMemberId` 的排位接口，不再提供活动人员直接排位分支。

服务端的 `assignActivityMember` 暂时保留为旧客户端兼容入口，但当前 Web 管理端不再
调用它；新交互和新代码不得依赖该入口。

### 影响

排位候选列表与当前环节人员关系保持一致，跨环节人员不会再被误展示。已有通过旧入口
排位的人员已经落成 `segment_member` 关系，仍会正常出现在对应环节的列表中。

## 团体主档与活动分组是两套概念

### 背景

人员需要一个可跨项目、跨活动复用的所属团体，用于后续团体批量排位。现有
`activity_member.groupName` / `segment_member.groupName` 看起来也叫“分组”，但它们
记录的是运营在某一场活动或某一个环节内临时填写的关系字段，同一个人换场活动后
完全可能属于另一个分组。

### 决策

- 新增独立的 `organization` 主档；代码不用 `group`，避免与现有 `groupName` 混淆。
- `member.organizationId` 是可空单值外键，一名成员当前最多属于一个团体；已有人员
  增加列后自然保持 `null`，不从历史 `groupName` 猜测或回填。
- `project_member`、`activity_member`、`segment_member` 各自保存可空的
  `organizationId` 范围快照。项目/活动关系新建时读取当时的人员主档；环节关系默认
  继承它实际挂载的活动关系快照。环节入口自动补齐缺失上层时，同一次主档读取沿链
  传播，避免三层在一笔事务里读到不同值。
- 范围快照一旦存在就不回写。再次 ensure 已有关系时保留旧值（包括旧 `null`）；
  若项目关系已存在而活动关系后来才创建，两层允许分别反映各自创建时点。这样主档
  换团体不会改历史，也不会为了“看起来一致”而猜测旧数据。
- 团体主档和活动/环节分组不复用表、不自动同步、不互相继承。修改成员所属团体不会
  改写任何历史关系分组，修改 `groupName` 也不会改变人员主档。
- 团体名称在主档中唯一。被成员引用的团体不得物理删除，外键使用 `NO ACTION`，不做
  级联删除或 `SET NULL`。后续项目/活动范围快照即使保存名称快照，也必须同时保留指向
  团体主档的 `NO ACTION` 外键，使历史范围仍能阻止主档被物理删除。

### 影响

后续排位功能必须明确选择数据来源：跨活动的团体规则读取 `organization`，活动现场的
临时编组读取关系表 `groupName`。两者名称碰巧相同也只代表业务输入相同，不代表同一个
数据对象。

## apps/h5 的移动端适配：根字号等比缩放

### 背景

`apps/h5` 是给嘉宾在手机（多为微信内置浏览器）上打开的公众端，实际视口宽度落在
320–430 CSS px。适配方案要在这个区间里保证"不出错"。

第一版做的是**自适应**：内容列 `max-w-[480px]` 居中，内部 flex + `min-w-0` +
`truncate`，字号写死 px。实测这一版在 320–480 全程零横向溢出、零元素跑出视口，
**没有结构性问题**，但 320px 上有 6 处文字被省略号截断。

### 决策

改为**根字号等比缩放**，`styles.css` 里一条 `html { font-size: clamp(...) }`：

```css
font-size: clamp(0.925rem, 4.2667vw, 1.28rem);
```

- `4.2667vw` = `16 / 375 * 100`——设计基准 375px 宽、根字号 16px。
- 原自适应布局（`flex` / `min-w-0` / `truncate` / `max-w-[480px]`）**全部保留**，
  缩放叠在它之上。撤掉这条规则页面照常可用，这个可逆性是选它的理由之一。

### 为什么是"改根字号"而不是 PostCSS 插件

Tailwind v4 的 spacing 和字阶**全是 rem**（`p-3` 编译成 `0.75rem`），官方设计就是
"改根字号 = 整个 UI 等比缩放"。所以内边距、间距、圆角、尺寸、字号一起缩，不需要
任何插件。

**不要引入 `postcss-px-to-viewport` 那一类插件**：它在 Tailwind v4 上配不好，且
不处理 `w-[50px]` 这种任意值——本项目当时有 40 处。结果会是"一半缩放一半不缩放"，
比两种纯方案都糟。`lib-flexible` 同理，且它已被阿里官方宣布由 vw 方案取代。

### 为什么等比缩放比自适应更"不容易出错"

固定 px 下，bug 是「内容长度 × 屏幕宽度」二维的：同一条数据在 320px 上截断、
430px 上正常，测试矩阵是 5 档宽度 × 所有数据。等比缩放把它压成一维——**在 375px
上验过就等于在所有手机上验过**。真实数据接入后文案长度不可控，这一条权重很高。

实测（320px）：议程页截断 2 → **0**，行程页截断 6 → **3**。

### 刻意不缩放的东西

按"**跟着兄弟元素对齐的要缩，物理渲染量不缩**"划线：

- `border-[1.5px]` / `h-[calc(100%+1px)]` / `w-[3px]` 等描边和细线——等比后变成
  分数像素，不同设备上会渲染成 1px 或**直接消失**，这正是老 flexible 方案要额外
  写 `hairlines` 检测的原因。
- `max-w-[480px]` 画布上限——它是缩放的封顶锚点，见下。
- `env(safe-area-inset-*)`、`100dvh`——物理量。
- 阴影——纯装饰，缩不缩看不出来。

`Icon` 组件的 `size` prop 在内部换算成 rem 并走 `style` 而非 `width`/`height`
属性（SVG 几何属性在部分浏览器里不吃 rem，会退回成 px），否则 20 处图标会成为
整页唯一不缩放的东西。

### clamp 两端的取舍

- **下界 `0.925rem`（14.8px）**：低于 347px 宽的屏停止缩小，保证正文不低于 12px
  ——中文在 11px 已经糊了。**代价是 320px 上不再严格等比**，长文案仍可能截断。
  也就是说等比缩放买到的是"大部分区间确定"，不是"全区间确定"。
- **上界 `1.28rem`（20.48px）**：正好在视口 480px 处达到，和 `max-w-[480px]` 同时
  封顶、一起冻结，没有 `lib-flexible` 那种 750px 硬跳变。**改其中一个必须改另一个**
  （`1.28 = 480 / 375`）。

上下界用 `rem` 而不是 `px`，是为了让它们仍然跟随用户的浏览器字号设置。

### 已知代价

等比缩放会覆盖用户的系统字号偏好，且浏览器缩放不放大 vw，理论上有 WCAG 1.4.4
（文字放大 200%）风险。上面的 rem 边界能缓解但不能消除。

判断是**可接受**：这是短时、一次性的活动行程页（图文卡片，不是长文阅读），
适老化检查主要盯管理端。如果将来 h5 要承载长文阅读或成为无障碍验收对象，
这个决定要重新评估。

### 加新样式时的规矩

- 新字阶写 `rem`，并同步加进 `apps/h5/src/shared/lib/utils.ts` 的 `FONT_SIZES`
  ——tailwind-merge 不认自定义字阶名，会把它当成文字颜色，`cn()` 里**静默丢掉字号**，
  不报错不告警。
- 新的 `[Npx]` 任意值先问一句：它是跟着别的元素对齐的（→ 写 rem），还是物理渲染量
  （→ 留 px）。

## 环节配置合并为单页：整页原子保存

### 背景

环节（`activity_segment`）的配置原先散在四个入口：议程页的「修改」弹窗（只有基础
字段）、行内的「环节人员」弹窗、「资源需求」弹窗，以及独立的排位页。运营配一个环节
要开一个弹窗填基础信息、关掉、再点人员、再点需求——一场活动几十个环节，每个都走一遍。
而且弹窗里还套弹窗（人员弹窗里再开选人弹窗）。

产品原型（`docs/新版H5_Demo/` 之外的管理端原型）给出的方案是一个独立页面，四块内容
自上而下排开，底部一颗「保存」。

这次改造**推翻了一条之前写明的决策**——`segment-demands-dialog.tsx` 顶部原本写着
「入口是议程页环节行的独立按钮，**不内嵌在环节表单里**……新建环节时不该被迫面对还
不确定的资源问题」。推翻的理由是：那条决策成立的前提是"环节表单已经有十来个字段"，
而现在的形态是一个整页而不是一个弹窗，纵向空间不再是稀缺资源；四块用可折叠的区块
分隔之后，"新建时不想管资源"通过把那一类需求关着就能满足，不需要靠拆成两个入口。

### 决策

**四块合并到一个路由页，整页原子保存。**

- 路由：`/project/$projectId/activity/$activityId/agenda/$segmentId`，`$segmentId`
  传字面量 `new` 表示新建。新建和编辑共用同一个页面组件——除了排位那一块（新建时
  还没有 id，显示占位），四块内容和保存路径完全一样，维护两份迟早长歪。
- 保存语义：基础信息 + 环节人员 + 资源需求 + 资源安排全部先落在**本地草稿**，点
  「保存」发一次 `/api/agenda/saveSegmentConfig`，服务端在**一个事务**里按顺序写完
  8 张表。中途任何一步失败整体回滚。
- 排位是例外：**只读展示**（`buildSeatingPlanSvg()` 渲染一张静态 SVG），调座位仍然
  跳到排位页。它有自己的「待确认 → 已确认」闸门，塞进这个事务会把两套状态机绞在一起。

四条派生规则：

1. **人员和绑定发"意图"，不发"目标状态"。** 请求体里是
   `{ add, addNew, remove, updateRoles }` 和 `{ bindTargets, unbindIds }`，
   不是完整名单。**这是新旧界面能并存的前提**——如果发完整名单让服务端改成一致，
   那么运营 A 开着页面去开会的 20 分钟里 B 用旧弹窗加了个人，A 一保存就会把 B 加的
   人静默删掉。资源需求是唯一的例外，它是四类矩阵，页面永远拥有完整视野，整体替换
   才是对的。
2. **草稿里没有真 id 的对象用 `tempKey` 占位。** 新建环节时"手动录入一个人 → 加进
   本环节 → 建一辆车 → 把这个人绑到车上"是一次提交，中间那些对象在提交的瞬间都还
   没有主键。`tempKey` 只存在于请求体里，从不落库。
3. **资源类型跟着需求走。** 用车需求下面只可能是用车记录，卡片里没有类型选择器。
   服务端的 `checkDemandsLinkable` 本来就拒绝跨类型关联，让前端传一个必然等于需求
   类型的值只是多给它一次传错的机会。
4. **离开拦截是「先保存再走」，不是「你的改动会丢失」。** 后者等于把"你刚填的半小时
   白填了"的选择权交给一个正在赶时间的运营。

### 两条不能动的写入顺序

写在 `agenda/segment-config.ts` 顶部，这里重复一遍，因为写错了**都不会报错**，只会
得到奇怪的结果：

1. **环节必须先写，人员才能加。** `ensureSegmentMembers` 会在事务里重新读
   `memberEnabled` 并在关着时拒绝（`member/ladder.ts`）。同一次保存里"勾上开关 +
   加人"是最普通的操作，顺序反了会被自己这道闸门拦住，用户看到的是"明明勾了开关
   还说未开启"。
2. **需求项必须先整体替换，资源安排才能挂。** 资源挂的是需求项 id，而这些 id 可能
   刚被 upsert 出来。

### 代价

要认下来的，不是遗漏：

- **并发覆盖没有防护。** 没加乐观锁。两人同时编同一个环节，后保存的赢。最危险的
  那处（人员绑定）已经被"增量意图"消掉了，其余部分本期接受——基础信息和资源需求
  声明**在改造之前就已经是后写覆盖先写**（`saveForSegment` 本来就是整体替换）。
- **测不了的部分只能靠手工路径。** `agenda` 和 `resource` 两个模块原先零测试，而
  整个仓库**没有真正的数据库集成测试**（`routes.test.ts` 那些是钉 SQL 字符串，不
  连库执行）。所以"8 张表一个事务、中途失败整体回滚"这件事，自动化验证不了，只能
  靠 dev 种子库手工走。已验证过的关键路径：校验失败后资源台账为空、需求数为 0，
  确认回滚干净。
- **「按团体添加」没进新页面。** 它的异团体冲突检测是服务端在写入事务里做的，草稿
  模式下预演不了；硬展开成一批个人会**绕过那道检查**。要按团体加，去活动人员页或
  旧的环节人员弹窗。
- **「地图选点」没做。** 原型的地点字段画了「自定义输入 / 地图选点」两个 tab，本期
  只做文本框。坐标现在没有任何下游在消费，而引地图 SDK 要连带处理 key 管理、加载
  失败降级和坐标系（高德 GCJ-02 和 GPS 差几百米，不记清楚用的哪套将来必然错）。

### 并存与回退

新页面和旧的四个弹窗**同时存在**，议程页每行多一个「新版配置」、顶部多一个
「新增环节（新版）」。这是有意的：新版先在真实数据上给一部分人试，稳定后再收敛。

两条路写的是**同一批表、过同一套约束**，所以并存本身是安全的——前提就是上面那条
"发意图不发目标状态"。

为了让回退干净，改动**刻意拆成两个提交**：

| 提交 | 内容 | revert 的影响 |
| --- | --- | --- |
| `refactor:` 抽出写入原语、提升议程域共享代码 | 行为零变化，接口清单照旧 | 一般不需要 revert；它对旧接口只有"少了一份重复实现"的好处 |
| `feat:` 环节配置单页 | 新页面 + 2 个新接口 + 2 个入口按钮 | revert 它即可完整移除本功能 |

回退之所以便宜，三个原因：

1. **零 schema 改动、零迁移文件。** 新页面写的是既有的 11 张表，没有新表新列。
   回退**完全不用动数据库**。
2. **数据不会变孤儿。** 新页面写的需求、资源、绑定用的是和旧弹窗完全相同的表，
   回退后旧界面照样读得到改得动。
3. 功能提交里除了两个入口按钮和 `SegmentTable` 的 `onConfigure` prop，其余都是
   新增文件（`segment-config.ts`、新路由目录），revert 基本是删文件。

收敛（删掉旧入口和四个弹窗）时要做的：删 `segment-form-dialog.tsx`、
`segment-detail-dialog.tsx`、`segment-members-dialog.tsx`、
`features/resource/segment-demands-dialog.tsx`，以及议程页里对应的 state 和按钮。
建议给收敛定一个明确条件（比如"新版跑满 2 周无人员数据异常"），否则这类"先并存、
稳定后收敛"的安排最常见的结局是旧入口一直留着，两年后没人敢删。
