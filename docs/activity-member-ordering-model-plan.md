## 3. 为什么统一选择 Luna Max

官方建议按任务从较低强度起步，并在需要更多规划、分析或检查时提高强度；Max 适合质量优先的困难任务。[GPT-5.6 推理配置指导](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6) 本次用户明确要求所有执行统一 Luna Max，所以不再为每个阶段单独调节强度。

对本功能，建议按任务调整：

| 工作形态 | 起始配置 | 理由 |
| --- | --- | --- |
| 纯排序函数、数据库、API、页面和拖拽 | Luna Max | 统一模型与强度，减少跨模型交接和重新解释契约 |
| 业务边界与独立审查 | Luna Max | 通过独立上下文和固定验收寻找遗漏，不换模型 |
| 已给定内容的文档／测试夹具整理 | 可选 Luna Max | 对产出有直接核对标准，不需要自行决定业务语义 |

Max 是本次用户指定的统一配置，不表示已经证明它在每一类任务上都比低强度更划算。成本控制来自任务边界、单一写入者和按验收停机，而不是再引入更多模型。

不同模型的同名强度并不是能力等价关系。也不能认为提高强度就能补足遗漏的需求或错误的业务绑定；完整契约和测试仍是必要条件。

Codex 的 Max 为单个任务增加推理投入；Ultra 会使用子代理处理可分离的工作。本任务的数据库和 UI 存在前置依赖，默认不启用 Ultra；Max 已满足统一单任务执行要求。[Max 与 Ultra 的区别](https://learn.chatgpt.com/docs/models)

以下路径已检查存在，未来新增文件在后文单独标注。

| 位置 | 当前事实 | 对排序实施的影响 |
| --- | --- | --- |

| [routes.relation.ts](../apps/server/src/modules/member/routes.relation.ts) 的活动人员 `/list` | `activityId` 范围，支持筛选和分页，目前按关系 id 升序 | 迁移需保留既有显示顺序；计算移动不能只读取当前页 |
| [ladder.ts](../apps/server/src/modules/member/ladder.ts) | `ensureActivityMembers` 和 `writeActivityOrganizationLayer` 都会创建活动关系 | 两个底层入口都要正确分配新位置，单改 `/add` 会漏写 |
| 同一 ladder 文件的环节入口 | 选人、按组织添加可自动补齐上层活动关系 | 环节操作后新增到活动名单的人，也必须正确追加 |
| [活动人员页面](../apps/web/src/routes/_authenticated/project/$projectId_.activity.$activityId.members/index.tsx) | 姓名、来源、分组、负责人筛选；默认每页 10 条 | 用已应用筛选判断能否移动，不能根据输入草稿判断 |
| [relation-queries.ts](../apps/web/src/features/member/relation-queries.ts) | 列表使用 `keepPreviousData`；还有名单快照和启用人员读取 | 翻页占位期间禁止操作旧行；检查受影响缓存和其他列表消费者 |
| [activity-member-edit.tsx](../apps/web/src/routes/_authenticated/project/$projectId_.activity.$activityId.members/-components/activity-member-edit.tsx) | 既有编辑包含活动字段和参与环节同步 | 排序使用独立意图，不把它混进整个人员编辑表单保存 |

当前名单主页面没有默认 `memberStatus="enabled"` 条件；另一个“全部启用人员”查询有该条件。不能把这两个视图误认为同一个排序范围。

当前 [人员导入服务](../apps/server/src/modules/member/import-service.ts) 面向人员主档，没有查到直接写入活动关系的逻辑。本次不为它新增活动排序；实施时仍需重新搜索所有 `insert(activityMember)` 和上述 helper 的调用方，以当前代码为准。

### 4.1 本次确定的业务绑定

| 项目 | 本次实施约定 |
| --- | --- |
| 排序对象 | `activityMember.id`，不是 `memberId`、`projectMemberId` 或环节人员 id |
| 完整范围 | 同一个 `activityId` 下的全部活动人员关系；组织、来源、分组、状态都是筛选条件，不是独立排序空间 |
| 可见数字 | 新增 `sortOrder`／`sort_order`；界面列名“排序”；映射到纯函数的 `order` |
| 数值范围 | 可为空；有值时是非负 PostgreSQL integer：0—2,147,483,647；这是本次新字段的边界，不继承议程的 0—999 限制 |
| 隐藏位置 | 新增 integer `sortIndex`／`sort_index`，不作为用户输入或页内索引 |
| 最终读取 | `sortOrder ASC NULLS LAST, sortIndex ASC, id ASC`；未设置值排在明确数字之后 |
| 固定项 | 当前没有议程“主线”那类固定行；不能复制其特殊分支 |
| 历史数据 | 首版曾用 0 代表“未设置”，迁移将这些旧 0 转为 NULL；按活动分区、旧 id 升序回填隐藏编号，保持原列表顺序 |
| 新增默认 | 新关系的 `sortOrder` 一律为 NULL，追加到未设置组末尾；批量只对真正新增的关系分配隐藏位置 |
| 重复添加 | 已存在关系不改变任何排序字段；保持原有组织补齐等业务语义 |
| 索引 | 增加 `(activity_id, sort_order, sort_index, id)` 查询索引；不为同值位置增加唯一约束 |
| 范围外模块 | 不给项目人员、环节人员、人员主档增加排序列；经这些模块进入活动的新增关系遵守活动排序。**只是不加列，不是不跟顺序**——凡是把活动人员摆成列表的读取出口都按本表最后一行的顺序读，见[执行记录的"读取出口统一"](activity-member-ordering-execution.md#读取出口统一2026-09-11) |

未设置的排序值在界面显示为 `-`，数据库使用 NULL；有值时数字越小越靠前。输入 0 会让该行排在所有未设置人员之前；清空输入可恢复为未设置。若界面还需要序号，另按分页位置显示，不将序号保存到 `sortOrder`。

### 4.2 保存与页面边界

已新增两个业务动作，遵守仓库 POST、Hono 链式注册、`jsonBody` 和结果信封规则：

```ts
// POST /api/activityMember/setOrder
{ activityId, id, sortOrder: number | null }

// POST /api/activityMember/move
{ activityId, id, targetId, placement: "before" | "after" }

// 两个动作的成功 data
{ id, sortOrder, changed: boolean }
```

后端在事务内校验活动及源／目标归属，读取完整活动范围的轻量排序字段，调用纯函数，保存实际差异。不能接收客户端提供的 `sortIndex`、表名或整页最终编号。无操作不写数据库；其他行仅隐藏编号变化时保留其业务审计字段，防止 ORM 自动刷新 `updatedAt`。

现有 `/update` 保持人员业务字段语义；列表投影增加可见 `sortOrder`。详情是否需要该字段按实际显示消费决定，不为拖拽扩大整个人员详情载荷。成功后等待相关查询刷新完成，再恢复移动；失败保留原服务端顺序并显示可重试反馈。

首版仅允许当前页内移动，提交稳定锚点 ID。当前页第一行只意味着“位于这行之前”，不意味着全活动置顶。生效筛选、分页占位、读取失败、排序保存中以及未保存的行编辑都禁用移动。页内没有可用锚点时不发送请求。

筛选时仍允许手填排序值或清空为 NULL；保存后该行可能离开当前页，应给出成功反馈并刷新，不额外实现自动追踪目标页。未改变可见值的提交是无操作。

拖拽复用了已核实兼容 React 19 的 `@dnd-kit/react@0.5.0`，并已在活动人员页验证手柄、鼠标和键盘事件。按 [原任务卡 T05](table-ordering-tasks.md#t05) 的库验证原则，只引用库和交互验证部分，不引用 agenda 业务路径；后续同类模块沿用这个版本和事件模型。

## 7. 怎样控制交接和模型成本

一次只派发一个明确任务，不让执行者自行重新设计所有策略。主开发继续使用自己的任务上下文；独立审查从精简证据和当前代码开始，不需要复制主开发的完整聊天。是否切换模型与是否另开任务是两个选择，不必绑定。

每次交接只保留这些信息：

```text
任务 ID 与完成目标：
当前代码基线／本次改动文件：
适用规则与业务绑定章节：
已固定接口和前置成果：
必须保留的业务行为：
已执行检查（命令、结果、是否真实 DB／浏览器）：
当前失败的最小复现：
下一步与完成标准：
```

即使统一使用 Luna Max，也保留有证据的停机和返工条件：

1. 普通类型或接线错误，由当前 Luna Max 修复并跑相关测试。
2. 同一个行为缺陷经过两轮针对性修复仍失败，先整理最小反例，暂停继续堆改动，交由主 agent 重新核对契约和范围。
3. 出现未定义的业务语义或相互冲突的规则，先修改具体契约，再继续实现；不要让执行者靠猜测补齐。
4. 同一任务反复失败时，优先缩小任务或回滚到最近的可验证停点，不再通过增加模型种类解决。

记录总完成成本：实际可获得的用量、总耗时、修复次数、审查发现数、业务行为遗漏和新增回归。不要求用户人工估算 token，也不把多次请求的最大单次窗口简单当成任务消耗。

成本控制来自任务边界、并行文件隔离和及时验收；不再引入第二、第三模型。即使测试夹具或文档任务，也使用 Luna Max，以保持执行记录简单一致。
