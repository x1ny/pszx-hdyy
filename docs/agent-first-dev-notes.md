# agent-first 开发框架：本次踩出来的经验

> 这份文档不是某次改动的说明（那份在 [dev-workflow-refactor-review.md](./dev-workflow-refactor-review.md)），
> 而是把 2026-08-24 那次开发工作流改造里**可以迁移到下一套模板**的部分抽出来。
> 每条都配了当时的实测数据或失败现场——脱离现场的原则很容易被下一次的"这次不一样"绕过去。

## 0. 前提：agent-first 与 human-first 的三条硬差别

设计模板之前先认清这三条，否则会把大量精力花在错误的地方。

**一、agent 不能替你输入密码，这是它的硬性安全规则，不是配置问题。**
「代替用户输入密码进行认证」属于无条件禁止项，规则里明确写了**即使用户显式要求、提供了全部凭据、声明授权，也依然拒绝**。
所以「把测试账号写进 AGENTS.md」这个直觉动作是反效果的——写得越清楚，越是正面撞在这条上，agent 越不敢动手。
模板必须把「免密进入登录态」当成一等公民能力来设计。

**二、并行 worktree 是常态，而且 worktree 会被建了删、删了建。**
人类开发者一个仓库一个工作区；agent 是每个任务一个 worktree，跑完就删。
任何"退出时清理"的逻辑都会被硬杀路径绕过（会话中断、编辑器关掉终端、任务管理器），
而且**孤儿资源的产生速度远高于人类工作流**。

**三、不止一个 agent 工具。**
这个仓库同时被 Claude Code（`.claude/worktrees/`）和 Codex（`.codex/worktrees/`）使用，
共 12 个 worktree。任何写进 `.claude/settings.json` 的规则只覆盖一半，
却会造成"已经防住了"的错觉——比不做更糟。

## 1. 隔离要落在物理层，不能靠清理逻辑

**现场**：改造前每个 worktree 各自 `docker compose up -d`，compose 按**目录名**派生 project，
于是机器上躺着 4 个 postgres 容器（3 个抢 5432 抢输了、端口没发布但继续跑了三天）和 10 个卷约 490MB。
更要命的是所有 worktree 的 `.env` 都写死 `localhost:5432`，**实际全连同一个库**——隔离是假的。

**做法**：一次性容器 + `--rm` + 数据目录挂 **tmpfs**。
「不持久化」因此是物理事实，不是一段需要正确执行的清理逻辑。

**否掉的方案**：常驻容器 + 每个 worktree 一个 database + 退出时 `DROP`。
它的干净程度取决于最后一次退出是否正常，而上面那三个僵尸容器已经证明了这个前提不成立。

**成本比想象中低**：实测 tmpfs 容器冷启动到可查询 **1.5s**，`drizzle-kit/api` 的 `pushSchema()`
建完 38 张表 **403ms**。所以"复用容器省时间"这个论证只值约 2 秒，不足以换来
"需要回收器"和"schema 改了但容器是旧的"这两个新问题。

**先量再定**：这一条的方向就是被这两个数字改掉的。凭直觉估的是 5~10 秒，实测是 2 秒。

## 2. 身份用完整路径的哈希，不要用目录名

**现场**：容器名一开始取 `basename(repoRoot)`。Claude 的 worktree 叶目录带任务名，看不出问题；
但 Codex 的 worktree 长成 `.codex/worktrees/<hash>/pszx-hdyy`——**7 个 worktree 加主仓库，叶目录全是 `pszx-hdyy`**。
而启动第一步就是 `docker rm -f <容器名>`，等于任何一个 worktree 起 dev 都会杀掉别人的数据库。

**做法**：`前缀 + sha1(规范化绝对路径)`。路径要先规范化（Windows 大小写不敏感、两种分隔符都合法），
否则同一个 worktree 会因为写法不同拿到两个容器。

**教训**：这个 bug 我在会话早期就把 `git worktree list` 打出来看过，路径就在眼前，仍然漏了。
**凡是"每个 X 一个 Y"的设计，都要拿真实的 X 全集跑一遍唯一性检查**，而不是看两三个样本。
这条现在有 6 条单元测试守着。

## 3. 端口交给运行时分配，不要自己探测

自己探测端口（listen 一下、关掉、再让 docker 去绑）之间有窗口，
两个 worktree 同时启动可能选中同一个端口。
直接 `-p 127.0.0.1::5432` 让 Docker 分配、再用 `docker port` 读回，竞争窗口消失。

## 4. "连错数据库"是这类系统的头号静默故障

**现场**：临时库端口随机，而 `.env` 写死 5432。不处理的话，
`bun run dev` 起的是临时库，但 `bun run db:studio` 会连到持久库——
**没有任何报错**，agent 看到一堆真实数据，然后得出完全错误的结论。

**做法**：dev 启动时把真实连接串写进一个 gitignored 的运行时文件，
数据库工具按 `.env` → 运行时文件的顺序读（后者覆盖前者），文件不存在时自动回落。

**这个 bug 我自己复现了一次**：第一版认为"硬杀后运行时文件指向已死端口，是响亮失败"。
错的——`docker run -d --rm` 的容器在父进程被硬杀后**照样活着**，
于是 `dev:persist` 时应用连持久库、数据库工具连那个还活着的临时库，两边都不报错。
更难堪的是：我在同一次会话里亲眼见过 `docker ps` 显示容器仍是 `Up`，却没据此修正结论。

**模板层面的规则**：任何时候必须保证**应用、数据库工具、迁移脚本连的是同一个库**，
并且这件事要有自检——子进程建表前先比对期望值，再用 `select current_database()` 核一遍实际连上的库名。

## 5. 种子数据的可迭代性靠类型系统，不靠纪律

用户的原话是要「可迭代的、自主按需更新的种子脚本」。落地成三条机制，
**没有一条依赖人记得做什么**：

1. **一律用 ORM 的 typed insert，禁止裸 SQL** —— 字段改名、加非空列，`typecheck` 当场报错。
   裸 SQL 要等运行时才炸，而那时通常已经过了几周。
2. **每次启动都跑全量种子** —— 坏了立刻暴露，不需要额外的检查工序，
   也不会出现"半年没人跑过种子脚本"。
3. **种子失败 = 启动失败** —— 在灌了一半的库上调试得出的结论全是错的，比启动失败难查十倍。

**组织方式**：一个目录、数字前缀定序、runner 就是 glob + sort + 依次 await。
唯一不能放弃的性质是**新增种子不碰任何已有文件**——多 worktree 并行时，
任何中心文件（大 seed.ts、顺序清单数组）都是固定的合并冲突源。

**否掉的方案**：每个模块 `seed.ts` + `dependsOn` + 拓扑排序。
被判定为过度设计：依赖只有 10 个模块、最深 4 层，数字前缀足以表达；
而写错 `dependsOn` 时报错是"循环依赖"这种间接信息，不如"外键报错 + 看文件名顺序"直观。
**但要强制文件名规则**（`^\d{2}-[a-z0-9-]+\.ts$` 且序号不重复）——
文件名排序是字典序不是数值序，混进 `5-` 或 `100-` 会让实际顺序和肉眼读到的不一样。

**种子该埋什么**：不是"把表填满"，而是**埋下能触发功能的最小数据**。
这次埋了两个时间重叠且挂同一个人的环节，于是"人员时间冲突提示"这个功能
不用手工造数据就能验；人员灌到 24 条（默认每页 10）让分页真的能翻页。
**只灌 2~3 行的种子，等于分页、筛选、冲突检测这些功能一条都测不出来。**

## 6. 免密登录要走真实认证链路，不能短路守卫

**做法**：一条 dev 专用路由，内部调用认证库自己的服务端 API 签发真 session，
原样透传它生成的 cookie 再 302。agent 一次导航即进登录态，全程不碰密码框。

**否掉的方案**：dev 模式下让 session 中间件直接注入用户。
那样 `_authenticated` 守卫、会话过期、"登录后必须清缓存否则被弹回登录页"这类坑
在开发环境**永远不执行**，只会在生产环境露头——等于用测不出 bug 换来省两行代码。

**种子建账号要用认证库自己的注册 API**，不要手写 user/account 两张表：
密码哈希的算法和参数归它管，手写一份必然在某次升级后悄悄失配，
而失配的表现是"登录返回 401"这种完全不指向种子的症状。

**三道闸，而且要用白名单不是黑名单**：
1. 开发形态白名单（如 `APP_ENV=development`），只有根 dev runner 会设
2. 显式开关（`DEV_AUTH_BYPASS=1`）
3. 请求来自回环地址

第一版写的是"看起来像不像生产"的黑名单，被评审指出**黑名单永远补不全**——
`bun run start` 两个判据都不设，前后端分域名部署也可能没有其中之一。
反过来只允许明确的开发形态，才是对的方向。

**两个连带的坑**：
- **服务端默认绑到所有接口。** Bun 报告的 `server.hostname` 是 `"localhost"`，
  但实测局域网 IP **可达**——只看 API 返回值会得出错误结论。开发时挂着免密入口，
  等于同网段任何人都能签出一个真实 session。开发编排要显式绑回环，
  且前端代理目标要同步改成 `127.0.0.1`（Windows 上 `localhost` 可能先解析成 `::1`）。
- **重定向白名单挡不住反斜杠。** URL 标准把反斜杠当路径分隔符，
  `/\evil.example` 会解析到外站 origin，而 `startsWith("//")` 拦不住它
  （查询参数会被框架解码，所以百分号编码形式最终也会变成字面反斜杠）。
  正解是 `new URL(raw, 固定base)` 后比对 origin，别枚举可疑前缀。
- **接口文档会泄露这条路由。** 如果文档生成器遍历的是运行时路由表，
  而 dev 路由挂在同一个实例上，只要生成文档时环境里恰好有那个开关，
  后门就会被写进公开可访问的文档。要在生成器里把该前缀声明为保留命名空间。

## 7. 规则要落在工具无关的层面

**现场**：用户此前每次让 agent 提交代码都得手动提醒"别产生交叉合并"。

**做法**：`merge.ff=only` + `pull.ff=only`（仓库级 git config，**所有 worktree 共享**）
加上版本化的 `.githooks`，由 `postinstall` 落地——新 worktree 必然要装依赖，
所以必然被执行到，不依赖任何人记性。

**为什么不用 agent 工具自己的 hook 机制**：只覆盖一半的工具，见前提三。

**要覆盖所有绕过路径**：`git merge` 撞上冲突时**不走** `pre-merge-commit`，
而是等你解完冲突再 `git commit`——那一步触发的是 `pre-commit`。
只装前一个的话，最常见的那条路径（有冲突的合并）是漏的。
这条是靠**逐个场景实测**发现的，不是读文档读出来的：

| 场景 | 拦截层 |
| --- | --- |
| 分叉后 `git merge` | `merge.ff=only` |
| `git merge --no-ff` 显式绕过 | `pre-merge-commit` |
| 有冲突 → 解完 `git commit` | `pre-commit`（检测 `MERGE_HEAD`） |
| `rebase` → `merge --ff-only` | 放行 |
| 普通提交 | 放行 |

**报错文案要给出下一步命令。** git 原生的 "Not possible to fast-forward, aborting"
会让 agent 去猜；而且钩子拒绝之后仓库会停在**未完成的合并状态**，
文案里必须写 `git merge --abort`，否则 agent 会卡在一个看不懂的状态里。

**Windows 上钩子会提交成不可执行。** `core.fileMode=false` 让 `chmod` 进不了索引，
而 Unix 的 git **会静默忽略不可执行的钩子**——最坏的失败形态：规则看起来装好了，
一条都不生效。要 `git update-index --chmod=+x` 记成 `100755`，
并让 setup 脚本每次校验模式。同理 `.gitattributes` 的 `*.sh` 覆盖不到无扩展名的钩子文件。

**明确边界并写下来**：`core.hooksPath` 是相对每个 worktree 的路径，
还没 rebase 到该提交的分支里没有这个目录，钩子层要等它们 rebase 后才生效。

## 8. 交付门禁不能带着既有红灯上线

**现场**：仓库里有 3 个既有失败的测试（与本次改动无关）。
如果直接规定"agent 干完活要跑通 `typecheck && test`"，结果只有两种：
agent 被永久卡住，或者**逐渐学会"红灯可以忽略"**——后者让整条门禁失去意义。

**处理**：在能修的时候修；不能修（比如它编码的是别的模块的产品口径）就
**精确记录已知红灯清单 + 根因 + "除这些之外必须全绿"**，
而不是留一句"与本次无关"让后来的 agent 自行判断。

**顺带一个自己犯的错**：把新测试挂在 `既有测试 && 新测试` 的后半段，
而前半段因为既有红灯恒定 exit 1——新测试**永远不会执行**。顺序要反过来。

## 9. 方法论：怎么核对结论

这次经历了两轮评审，方法上有三条值得带走：

**一、拿到证据要回头修正结论。** §4 那个 bug 的关键证据（容器硬杀后仍 `Up`）
我早就打印出来了，却没有据此推翻自己"是响亮失败"的判断。
**收集证据和更新结论是两个动作，后者不会自动发生。**

**二、评审的依据可能错但结论对，反之亦然。** 评审说"Bun 默认监听 `0.0.0.0`"，
而 API 报告的是 `"localhost"`——依据对不上。但改测实际连通性后，
**结论成立**。既不能因为依据错就否定结论，也不能因为结论对就接受依据。

**三、破坏性工具的候选集必须按"证明得了归属"定义，不能按命名模式。**
清理脚本一开始按"所有 postgres 镜像的非 canonical 容器"和"所有 `_postgres_data` 结尾的卷"筛选。
本机当时恰好只有一个项目，看起来没问题——但这个论证站不住。
改成：能证明归属的才自动删（自己写的 label、compose 的 `working_dir` 落在本仓库 worktree 里、
卷名前缀对应 worktree 目录名），证明不了的只列出来交给人，正在使用的单独保护。
**默认 dry-run 只降低误操作概率，修不了候选集越界。**

## 10. 模板检查清单

给下一套 agent-first 模板用，每条都能直接落成一个验收项：

- [ ] 一条命令起一个**与其他工作区物理隔离**的开发环境，退出即销毁
- [ ] 隔离的身份来自**完整路径哈希**，并有一条"拿真实路径全集验唯一性"的测试
- [ ] 端口由运行时分配，不自己探测
- [ ] 应用、数据库工具、迁移脚本**保证连同一个库**，且有启动自检
- [ ] 资源创建后立刻进入 `try/finally`；另有一条针对硬杀路径的开机自清
- [ ] 种子：typed insert、每次全量跑、失败即启动失败、新增不碰已有文件、文件名规则有校验
- [ ] 种子内容埋的是**能触发功能的最小数据**（冲突、跨页、多状态），不是填满表
- [ ] 免密登录走**真实认证链路**，三道闸且是白名单，开发端口只绑回环
- [ ] 开发后门不出现在任何公开产物（接口文档、构建产物）里
- [ ] 流程规则落在 **git / 包管理器**这类工具无关层，不写在某一个 agent 的配置里
- [ ] 每条规则的**所有绕过路径**都实测过，报错文案给出下一步命令
- [ ] 交付门禁当前**确实能变绿**；不能则精确记录已知红灯与根因
- [ ] 破坏性操作默认 dry-run，且候选集按"证明得了归属"定义
- [ ] AGENTS.md 里给出**可直接导航的固定 URL**（种子 ID 写死换来的）
