## 1. 结论与修订

**第一轮应交付一套更容易找到知识、更容易执行验证、能跨 Agent 使用并能测量效果的开发环境。现有 Bun、React、Vite、TanStack、Hono、Drizzle、PostgreSQL 主干继续保留。** 外部材料没有提供足够依据，证明此时替换主框架、迁移微服务或增加重型任务编排系统，会优于修整现有工程反馈链路。

此前建议的方向大体成立，但需要五处修订：

| 此前的侧重点 | 本轮修订 | 原因 |
| --- | --- | --- |
| 将根 AGENTS 压到 6—10 KiB | 保留为软目标；验收以准确性、可发现性和实际加载预算为准 | 公开工程中也有较长且具体的指令文件，行数本身不能判定质量 |
| 细节搬到文档与 skill | 根文件保留少量明确的“任务 → 资料/skill”入口，细节按需加载 | skill 已安装不代表会被调用，普通链接也不等于实际读过 |
| 整理已有 skill | 加入 Codex / Claude Code 的原生发现与调用验证 | 两端默认目录和扩展语法不同，同名 SKILL.md 不能证明跨端行为相同 |
| 统一检查命令 | 同时明确检查范围、日志、既有失败、退出码和 CI 复用方式 | Agent 需要知道检查证明了什么，以及失败后下一步怎么做 |
| 最后再建设任务评估集 | 第一轮就选少量真实任务做前后对照 | 外部研究结论存在分歧，必须尽早验证本仓库的收益 |

衡量目标是：**交付同等可接受变更所需的总时间、人工介入和返工是否减少。** 不把文档字节数、skill 数量或首次生成代码速度单独当成成功指标。

## 2. 官方指导中，哪些机制直接影响本项目

### 2.1 指令文件的加载机制需要分别设计

Codex 在任务开始时沿项目根到工作目录发现项目指令，项目指令链共用默认 32 KiB 预算。不能假定从仓库根启动后，随后修改任意子目录文件都会自动加载那个子目录的 AGENTS。当前根文件已达 32,766 字节，因此“根文件基本不动，只往子目录再拆文件”不是可靠方案。[Codex 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

Claude Code 支持祖先目录指令、访问子目录时加载对应指令，以及路径限定的规则。`@文件` 导入会展开加载；把一本大文档拆成多个 `@` 导入，不能达到按需读取的目的。官方建议 CLAUDE.md 保持简洁，约 200 行是建议，不是本项目应机械执行的硬门槛。[Claude Code 官方说明](https://code.claude.com/docs/en/memory)

**本项目建议：** 保留 `CLAUDE.md → @AGENTS.md` 的单一公共入口；根文件仅承载全局高价值规则与简短索引。专题使用普通路径和明确的阅读条件。只有验证宿主实际加载行为后，才增加宿主专属配置。

### 2.2 通用 skill 内容与宿主适配应分开

Codex 的仓库 skill 默认通过 `.agents/skills` 发现；初始上下文主要包含名称和描述，选择后才读取正文。Claude Code 的项目原生目录是 `.claude/skills`，并提供动态上下文、调用控制等宿主扩展。两者都支持一定形式的链接目录，但实际接线仍需在本机与 worktree 中验证。[Codex skills](https://learn.chatgpt.com/docs/build-skills)、[Claude Code skills](https://code.claude.com/docs/en/skills)

本仓库两个 skill 在 `.agents/skills`；已跟踪的 `.claude` 目录只有 `launch.json`。这说明仓库缺少显式的 Claude 原生接线证据，**不等于所有 Claude 环境都无法使用它们**：用户级配置、插件或手动读取也可能提供入口。本次没有可用的 Claude CLI，未完成该宿主的运行验证。

**本项目建议：** 正文只维护一份，宿主目录只做适配；将名称、描述、正文与宿主专属语法分开检查。适配可以是经验证的链接，或由脚本生成并检查一致性的镜像，选定一种即可。Windows 深路径 worktree 下必须验证后再固定方式。

### 2.3 规则、skill、脚本和 hooks 各自解决不同问题

OpenAI 的工程案例强调简短入口、仓库内可检索知识、机械化约束和可观测开发环境；这是团队实践报告，不能将其中效率数字直接承诺给本项目。[OpenAI：Harness engineering，2026-02-11](https://openai.com/index/harness-engineering/)

Claude Code 的官方实践强调明确验收条件与可运行的验证，并根据任务复杂度决定是否先规划。它并不要求每个小修改都经过完整设计流程。[Claude Code：Best practices](https://code.claude.com/docs/en/best-practices)

截至本次核验，**Codex 和 Claude Code 都有生命周期 hooks**。2025 年部分文章关于 Codex 没有 hooks 的描述已不适用。两个宿主的配置和事件协议有差异，共用能力应优先落在仓库脚本中，再由薄适配调用。[Codex hooks](https://learn.chatgpt.com/docs/hooks)、[Claude Code hooks](https://code.claude.com/docs/en/hooks-guide)

本项目可以采用以下职责划分：

| 载体 | 主要内容 | 示例 |
| --- | --- | --- |
| AGENTS / CLAUDE 公共入口 | 每类任务都可能需要的少数约束、入口 | 工具链、前后端运行时边界、检查命令、专题阅读条件 |
| 当前专题文档 | 某个领域当前成立的契约与例子 | 增量保存意图、人工排序、H5 认证现状 |
| Skill | 有明确触发条件、需多步判断的重复工作 | 接入人工排序、按项目范式实现 CRUD |
| 脚本 / lint / 测试 | 可以确定性判定的步骤和边界 | 禁止跨路由引用私有目录、生成物漂移、检查范围 |
| Hook | 在合适时机调用现有能力 | 编辑后运行便宜且相关的检查，输出修复入口 |
| CI | 与具体宿主无关的交付验证 | 执行同一套验证脚本、保留失败日志 |
| ADR / 历史记录 | 为什么这样决定、什么条件下重审 | 当初不拆包的理由、实验结果、已完成任务记录 |

## 4. 博客、社区与研究如何互相校验

### 4.1 Skill 触发问题有直接实验依据

Vercel 针对 Next.js 16 新 API 的评估中，默认 skill 有 56% 的用例未被调用；显式指引提高了表现，压缩文档索引表现更好。实验范围是特定框架与测试集，不能推导出“任何 AGENTS 都优于任何 skill”。它对本项目最直接的启发是：**在默认上下文保留明确的发现入口，针对触发与漏触发单独验收。** [Jude Gao，2026-01-27](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)

本项目的 `table-ordering` 已经有明确的适用与排除条件、真实消费者、分段读取和验收证据，是值得保留的局部实践。下一步应验证 Agent 能否在相关任务中找到它，以及在“按姓名升序”这类任务中正确跳过它。

### 4.3 研究结论不同，所以第一轮就应测量

Gloaguen 等人的研究 v2（2026-06-23）报告：在其任务与 Agent 设置中，上下文文件总体没有改善成功率，且平均推理成本增加超过 20%；项目特有实践比泛化的仓库概览更有价值。[论文 v2](https://arxiv.org/abs/2602.11988v2)

Lulla 等人的另一项研究 v2（2026-03-30），基于 10 个仓库、124 个 PR 任务，观察到有 AGENTS 的条件下运行时间与输出 token 的中位数下降，完成表现接近。[论文 v2](https://arxiv.org/abs/2601.20404v2)

两者任务设计、上下文文件、模型和指标不同，不能把百分比相加或择优承诺收益。我们应把“精简入口、显式索引、按需 skill 会提高效率”作为**有依据但仍需本地验证的方案假设**。

## 5. 第一轮实施范围与验收

建议按四个可独立审阅的提交推进。第一轮以文档、开发工具和验证路径为主；涉及共享契约、业务模块拆分、客户端声明包的改造保留到第二轮。

### 提交 A：校准知识入口，保存初始基线

文件级迁移映射、AGENTS 候选正文及索引验收见[知识入口修改方案](C:/Users/Administrator/.codex/worktrees/6f8a/pszx-hdyy/docs/knowledge-entry-change-plan.md)。

**交付物：** 精简且准确的 AGENTS；保留一行导入的 CLAUDE；当前专题文档的必要更新；一个轻量 `docs:list`；首批任务评估定义与环境记录。

具体处理：

1. 修订 H5 认证、测试装置等已经变化的陈述；把历史事实与当前限制分开。对尚未决定的产品问题保留明确边界。
2. 根文件保留高价值约束、真实命令与任务索引。6—10 KiB 是初始压缩目标，可依据评估调整；必须给宿主的总加载预算留余量。
3. 为少量当前工程文档添加 `summary`、`read_when`。研究报告、历史交接和静态原型不进入默认索引；不要求批量改写所有历史文件。
4. 生成一个“路径＋何时读”的索引供查询；根文件只保留高频入口与索引命令，避免再维护一份完整手写目录。
5. 在改造前保存同一代码基线、工具版本、已知失败与任务表现；记录不包含凭证或原始敏感会话。

**验收：** Codex 从根目录启动能定位目标资料；CLAUDE 的展开入口没有重新把专题全文加载回来；当前入口与代码、命令一致；历史报告不被误认成已采纳规则。内容迁移后的重要业务不变量仍可被相关任务发现。

### 提交 B：现有 skill 治理与两端适配

**交付物：** 单一内容源、可检查的宿主适配、明确的上游版本与本地覆盖说明、固定版本的 Intent 调用入口及适用范围。

具体处理：

1. 对 `table-ordering` 做正反触发用例，保留其实际业务绑定和验收区分。
2. 校准 shadcn 上游通用指导与本项目 Sonner、CRUD 视觉和 Base UI 使用方式的关系；本地例外在一个明确入口维护，避免两份正文反复冲突。
3. 盘点并固定 Intent 工具版本；按当前包和 SPA 用途设置加载范围。发现可用 skill 不等于全部启用，React Start / SSR 的间接依赖指导不应进入普通 SPA 任务。
4. 检查 Claude 专属动态语法是否在其他宿主被当作普通文字；必要时用公共脚本替代，宿主配置只负责接线。
5. 在 Codex、Claude Code 分别验证发现、显式调用、自然任务触发及资源路径；记录实际宿主版本。暂时无法运行的一端明确标为待验收。

**验收：** 同一 skill 只有一份权威正文；两端相关任务读到相同规则，排除任务不误触发；安装与 worktree 路径变化后引用仍有效；升级上游 skill 的差异可审阅。不要将仅创建目录记为“跨端支持完成”。

### 提交 C：换行和格式基线的独立整理

**交付物：** 明确的跨平台换行策略、正确的 Biome 作用范围、必要且独立的格式变更。

本次评审的全仓检查噪声主要来自换行，但关闭 formatter 后仍存在实际 lint 问题，所以不能把所有红项都归为 Windows 环境。应先缩小到应用与工程脚本，再按文件类型确定 LF 与工具配置的一致性；排除交接原型中的示例源码。

**验收：** 相关配置在干净工作区验证；格式化只产生预期路径的 diff；Windows 下重复执行不会重新污染未改业务文件。批量格式变更独立提交，与语义调整分开审阅，不在有未整理修改的工作区直接全仓 `--write`。

### 提交 D：可信检查入口与小规模对照

**交付物：** 命名清楚的检查/修复入口、相关范围与全量验证模式、有限输出与完整日志、CI 的同一入口调用，以及第一批任务对照记录。

建议命令语义如下，具体名称实施时可沿用项目习惯：

| 入口 | 语义 |
| --- | --- |
| `check` | 检查格式与 lint；不自动修复源码 |
| `format` / 明确的 fix 入口 | 显式修改格式或执行可审阅修复 |
| `verify:fast` | 根据改动执行足够便宜的相关检查；显示本次范围和未覆盖项目 |
| `verify` | 交付所需检查；涉及共享基础层、schema 或边界时扩大到相关消费者 |
| `docs:list` | 输出当前工程资料摘要与阅读条件 |

第一轮无需建立完整依赖图引擎。可以从明确的路径分类开始：页面局部变更、服务端模块变更、公共契约变更、schema 变更、纯文档变更。遇到无法可靠判断的影响范围，使用较大的已知检查集合。

验证报告至少包含代码版本、命令、范围、退出状态和日志位置。完整输出保存一次，后续查询日志；不要为了截取不同报错重复跑昂贵命令，也不要只保留“通过”两个字而丢失证据。

当前 3 个 invitation 测试已有失败基线。实施时应保留原始失败与退出信息，用精确的既有失败清单和新增失败区分；不能通过放宽产品期望、宽泛忽略测试文件或吞掉退出码制造全绿。清单包含复现基线及待决问题，后续解决后删除。

CI 调用同一仓库脚本。若托管平台不同，选对应 CI 实现即可；有条件时覆盖 Windows 与部署目标环境。宿主 hooks 在命令稳定后最多先接一个便宜、范围明确的检查，不把全量测试挂在每次编辑或每次 Stop 上。

**验收：** 正常收尾不会自动重写全仓；相关检查与全量检查的差异清晰；新失败能阻断；既有失败准确可见；生成物需要更新时有明确修复入口；无必要的重复测试减少。

## 6. 评估怎样保持足够轻

先选两个代表任务打通记录，再扩充到 4—6 个任务。对同一个宿主比较优化前后，保持模型、推理配置、代码基线、工具权限和验收条件尽量一致。Codex 与 Claude Code 的结果分别记录，不混成模型优劣排名。

| 候选任务 | 要检验的能力 | 关键观察 |
| --- | --- | --- |
| 普通 CRUD 增加筛选条件 | 找到项目范式并完成接线 | 是否读取当前指南；查询、分页、类型与测试是否按约定衔接 |
| H5 局部展示调整 | 区分两个前端的规范 | 是否误用管理端 shadcn 或旧的“没有 H5”前提 |
| 接入人工顺序的一个明确小任务 | skill 正触发与业务边界 | 是否实际读取 table-ordering；是否保留意图写入与业务范围 |
| 普通列升降序 | skill 负触发 | 是否正确排除人工排序 skill，避免不必要的算法改造 |
| 修改后端输入字段 | 生成物与验证范围 | 是否发现迁移、种子、类型和相关消费者需要检查 |
| 跨两个模块的受控改动 | 计划和交接质量 | 是否先明确不变量与验收；新会话能否凭简短事实继续工作 |

这些是待准备的评估任务，不是本次已执行结果。任务应有固定输入与结果验收，避免将唯一实现方法写进评分标准。优先使用匿名化的真实历史任务或隔离试点，避免更改共享测试环境。

记录四组数据就够：

- **质量：** 验收通过、遗漏规则、新失败、返工次数。
- **人的负担：** 必要与不必要澄清、人工纠正、审阅时间。
- **Agent 成本：** 总耗时、工具调用、可获得时的 token / 费用；包括失败尝试与返工。
- **行为证据：** 读过哪些入口、skill 是否触发、检查覆盖了什么、是否重复执行。

小样本用于找出明显回退和触发问题，不能证明长期提高了某个精确百分比。若只是多读了一份文档，却没有减少遗漏或返工，就继续压缩或撤回该规则；保留实际帮助任务的部分。

复杂任务才使用简短任务卡：目标、业务不变量、涉及边界、验收方法、未定问题。长任务交接记录当前代码状态、已验证事实、剩余事项与下一条可执行命令；不复制整段会话，也不为小改动强制建立完整设计文档。

## 7. 本轮完成后再推进的架构工作

1. **共享纯契约与客户端声明边界。** 当前已有重复校验和前端类型成本证据；第一轮建立稳定的测量与验证入口后，再用真实模块试点。可参考 OpenCode 对协议与生成客户端的约束，但不照搬其包结构。
2. **复杂业务事务与前端草稿边界。** 围绕环节配置、人员和资源等真实变更传播范围整理，不按文件行数机械拆服务层。
3. **少量新 skill。** 先看评估中重复发生的阅读、接线和验收遗漏，再决定是否补 CRUD、数据库变更或复杂编辑流程 skill；不以 skill 数量作为建设成果。

本项目已有的独立 worktree 数据库、确定性种子、真实开发登录、权限映射测试和迁移检查，是这一轮改造的基础。让这些能力更容易发现、稳定调用并留下证据，预期比同时更换技术栈与引入整套外部 Agent 框架更可控。

本文证据分为当前官方机制、固定提交的源码实践、作者经验和特定任务的研究结果。官方功能已按研究当日核验；公开仓库只检查了上表列出的文件；博客及社区收益没有在本项目复现。第一轮对照评估和 Claude Code 宿主运行验证仍是建议中的待实施工作。
